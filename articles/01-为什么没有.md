为什么你的内核里没有 sched_ext

—— 我在 openEuler 24.03 上敲了四条命令（第 1/6 篇）


一、我想干的事

我想换掉 Linux 的调度器。

不是调参数。nice 值、cpu.shares、sched_latency 这些我都试过，它们是在现有调度器内部拧旋钮。我要的是把整个策略换掉：不要 CFS 那一套按权重分时间片的算法，换成我自己写的。

网上说 sched_ext 能干这个。装一个 BPF 程序，一条命令切换，不用重启，不满意 Ctrl+C 就退回原来的。

听着很美好。那就先看看我这台机器支不支持。

我这台是 VMware 里的 openEuler 24.03 LTS SP4，4 核 8G，准备拿它当试验机。


二、第一条命令：先看内核版本

    $ uname -r
    6.6.0-159.4.3.154.oe2403sp4.x86_64

uname 是打印系统信息，-r 是只要内核版本（release）。不加参数会打一堆东西，加 -r 只留这一行。

这行字符串看着乱，拆开看就清楚了：

    6.6.0                    主线版本号
    -159.4.3.154             openEuler 自己打的补丁号
    .oe2403sp4               发行版标识：openEuler 24.03 SP4
    .x86_64                  架构

关键是前面那个 6.6.0。

sched_ext 是 6.12 才进主线的。6.6 和 6.12 差了六个版本，中间隔了一年出头。按常理，6.6 里不会有。

我当时的判断就到这儿：版本号不够，所以没有，得自己编一个新内核。

这个推理方式后来被证明靠不住。结论碰巧是对的，方法错了。第三节说完你就明白差在哪。


三、第二条命令：看内核配置

内核编译时有一份配置，决定哪些功能编进去、哪些不编。这份配置装完系统后留在 /boot 下，文件名是 config- 加内核版本。

    $ grep SCHED_CLASS_EXT /boot/config-$(uname -r)
    # CONFIG_SCHED_CLASS_EXT is not set

拆开看这条命令：

    grep                    在文件里找匹配的行
    SCHED_CLASS_EXT         要找的字符串，sched_ext 在配置里的名字
    /boot/config-$(uname -r) 配置文件的路径

$(uname -r) 是命令替换，shell 先跑 uname -r 拿到 6.6.0-159.4.3.154.oe2403sp4.x86_64，再拼成完整路径。这样写的好处是换内核之后不用改命令。

输出只有一行，而且带井号：

    # CONFIG_SCHED_CLASS_EXT is not set

这行的意思是：这个选项存在，但值是 n。

注意"存在"这两个字。它说明内核的配置系统里定义了这个开关，只是没打开。这跟"配置里根本没这一行"是完全不同的两件事：

    有这一行，值是 n      → 开关存在，代码可能在树里，打开重编就行
    根本没有这一行        → 开关都没定义，代码肯定不在，打开也没用

我第一次写检查脚本时就是在这里栽的。脚本里写的是：

    line="$(cfggrep "^${sym}=" )"
    if [[ -z "$line" ]]; then
        warn "${sym} 不存在于配置中"

cfggrep 是脚本里包的一层 grep，第一行拼出来的模式是 ^CONFIG_SCHED_CLASS_EXT=，意思是"以 CONFIG_SCHED_CLASS_EXT= 开头"。第二行判断有没有拿到结果，空的话就打"不存在于配置中"。

问题在第二行这个判断。关闭的选项在配置文件里长这样：

    # CONFIG_SCHED_CLASS_EXT is not set

前面有井号和空格，不是以 CONFIG_ 开头，所以第一行的模式匹配不到。于是第二行认为它是空，第三行打印"不存在于配置中"。

符号明明存在、只是关着，脚本却说它不存在。我照着这个输出判断"代码不在，只能重编"。判断错一次，后面路线选择就全错。

这个 bug 在提交 afde5ea 里修掉了，改法是加一层兜底：

    line="$(cfggrep "^${sym}=" )"
    if [[ -z "$line" ]]; then
        line="$(cfggrep "^# ${sym} is not set")"
    fi

逐行看。

第一行，先按 =y 的形式找。找到说明这行是 CONFIG_X=y 或 =m。

第二行，-z "$line" 判断上一步的结果是不是空串。是空，说明没找到 =y 形式。

第三行，换一种形式再找一次。^# CONFIG_SCHED_CLASS_EXT is not set，注意井号后面有一个空格，这是内核配置文件的实际格式，少这个空格照样匹配不到。

第四行，fi 结束判断。

改完之后，三种情况才分得开：找到 =y 是启用，找到 is not set 是存在但关着，两种都没找到才是符号不存在。改之前是把后两种混成一种，这就是错的根源。


四、第三条命令：看运行时有没有这个子系统

配置说有或没有，是编译时的事。系统跑起来之后有没有，看 /sys。

    $ ls -d /sys/kernel/sched_ext
    ls: cannot access '/sys/kernel/sched_ext': No such file or directory

ls -d 是"只看这个目录本身，不展开里面的内容"。不加 -d 的话，目录存在时会列出里面所有文件，很吵。

结果是这个目录不存在。

/sys 是内核暴露给用户态的接口。一个子系统如果初始化成功，就会在 /sys 下建一个目录，用户态通过读写里面的文件来操作它。目录不在，说明这个子系统压根没起来。

这一条和上一条是两个不同层面的事：配置是"编不编"，sysfs 是"起没起"。有可能编进去了但初始化失败，目录也不会有。所以这两条得分开看，不能互相替代。


五、第四条命令：看内核符号表

这条是我后来才想到加的，也是最有说服力的一条。

    $ grep -ci 'scx_' /proc/kallsyms
    0

两个参数：

    -c   不打印匹配的行，只打印匹配的行数
    -i   忽略大小写

/proc/kallsyms 是内核的符号表，列出内核里所有函数和全局变量的名字。你用 nm 看一个 .o 文件能看到符号，这里是同一个东西，只不过对象是整个跑着的内核。

sched_ext 的代码里，函数和变量基本都以 scx_ 开头，比如 scx_bpf_dispatch、scx_ops_enable。所以数一下有多少个 scx_ 开头的符号，就知道内核里有没有这段代码。

结果是 0。一个都没有。

这条为什么最有说服力？因为符号表跟"开关打没打开"无关。只要代码被编译进内核，符号就在表里，哪怕这个功能从没被启用过。

现在是 0，说明代码根本没被编译进去。不是"编了没开"，是"没编"。

后三条命令，三个层次：

    配置文件里有这个符号         → 开关存在，但关着
    /sys 下没有这个目录          → 运行时没起来
    符号表里 0 个 scx_ 符号      → 代码不在内核里

到这里结论明确了：这台机器的内核里没有 sched_ext 的代码，打开开关重编也没用，因为源码树里就没有这段代码可编。


六、为什么代码会"不在"：调度器是焊死的

要理解这件事，得看调度器在内核里是怎么组织的。

CPU 同一时刻只能跑一个线程。下一个该跑谁，这个决定由调度器做。听起来像个可以随时替换的模块，实际不是。

内核里每个调度器是一个 struct sched_class，也就是一组函数指针。定义长这样（kernel/sched/sched.h）：

    #define DEFINE_SCHED_CLASS(name) \
    const struct sched_class name##_sched_class \
        __aligned(__alignof__(struct sched_class)) \
        __section("__" #name "_sched_class")

四行，逐行看。

第一行是宏定义，name 是参数，比如传 ext 进去，name##_sched_class 就展开成 ext_sched_class。## 是 C 语言的记号拼接，把两个词粘成一个。

第二行声明一个 const struct sched_class 类型的变量。const 表示这个结构体在运行时是只读的，里面那些函数指针指向哪，编译时就已经填好了，跑起来改不了。

第三行 __aligned(__alignof__(struct sched_class)) 要求这个变量按结构体自身的对齐方式摆放。为什么在意这个？因为下面 for_each_class 里用的是指针加一，如果两个结构体之间被对齐插入空隙，加一就跳过头了。

第四行 __section("__" #name "_sched_class") 是关键。它把这个变量放进一个单独的段，段名是 __ext_sched_class。C 语言里变量默认被扔进 .data 或 .bss，这里强制指定另一个段。

为什么要单独一个段？因为接下来链接脚本要按段名排序。

include/asm-generic/vmlinux.lds.h 里：

    #define SCHED_DATA                \
        STRUCT_ALIGN();               \
        __sched_class_highest = .;    \
        *(__stop_sched_class)         \
        *(__dl_sched_class)           \
        *(__rt_sched_class)           \
        *(__fair_sched_class)         \
        *(__ext_sched_class)          \
        *(__idle_sched_class)         \
        __sched_class_lowest = .;

这是链接脚本的宏。它做的事，是把六个段按写死的顺序拼在一起。

STRUCT_ALIGN() 先做对齐，因为下一行要取地址。

__sched_class_highest = .; 里的点号表示"当前位置"，这行把当前位置存进一个符号 __sched_class_highest。后面 for_each_class 就从这儿开始走。

中间六行，每行收一个段。顺序就是优先级顺序，从高到低：stop、dl、rt、fair、ext、idle。

最后一行 __sched_class_lowest = .; 记下结束位置。

现在看怎么用这张表（还是 sched.h）：

    #define for_class_range(class, _from, _to) \
        for (class = (_from); class < (_to); class++)

    #define for_each_class(class) \
        for_class_range(class, __sched_class_highest, __sched_class_lowest)

for_class_range 是个普通的 for 循环，从 _from 开始，每次 class++，走到 _to 停。

class++ 是重点。它是对指针做加一，在 C 里等于"跳到下一个 struct sched_class"。也就是说，这六个结构体在内存里是紧挨着排的，像一个数组。

for_each_class 就是从这个数组的头走到尾。

所以内核每次要挑下一个任务，做的事是：从这个数组第一个开始，问"你有活干吗"，没有就 ++ 看下一个，谁先说有就听谁的。

这个数组的顺序，是链接脚本里那六行写死的。想在中间插一个调度器，得改链接脚本、改 Makefile、重新编译、重启。没有任何运行时接口能改它。

这就是"焊死"的具体含义。不是形容词，是链接脚本里六行硬编码的段顺序。

这里要纠正一个说法。我一开始以为 ext 的位置在 fair 之上，觉得它是"更高级的调度器所以排前面"。看了链接脚本才知道是反的：ext 排在 fair 后面、idle 前面，优先级比 fair 低。

那 sched_ext 怎么还能接管一切？因为它不靠优先级抢。它启用时会把 CFS 里的普通任务整体搬到 ext 类，fair 里就空了，自然没人跟它争。sched.h 里那个 next_active_class 函数干的就是这件事——当 scx_switched_all() 为真时，遍历直接跳过 fair。


七、sched_ext 怎么绕过这个焊死

sched_ext 的出发点不是"再写一个更好的调度器"，而是一个观察：

调度器里的"决策"和"执行"，可以分开。

执行部分是：把任务从队列摘下来、放到另一个队列、保存和恢复寄存器、切页表、通知 CPU。这部分必须在内核态、必须极快、必须绝对正确。它没有"因场景而异"的空间。

决策部分是：下一个该跑谁。这部分恰恰没有唯一正确答案。

编译服务器要吞吐，CPU 塞满就行，延迟高一点无所谓。游戏要延迟，一帧卡 20 毫秒玩家就有感觉。数据库要公平，不能有连接饿死。云厂商要隔离和可计费。

同一套 CFS 参数不可能同时满足这些，你调好这边，那边就塌。

sched_ext 就沿着这条缝切：执行留在内核，决策交给 BPF 程序。

内核那边负责记账、切换、保证不出事。BPF 程序只回答一个问题——这个任务该进哪个队列。

效果是：换调度器变成加载一个 BPF 程序。不用改链接脚本，不用重编内核，不用重启。

这就是它能绕过焊死的原因。它没有往那个数组里插东西，它插在 ext 这个固定的位置上，然后自己管自己。


八、为什么敢让用户的代码进内核

让普通用户往内核里塞代码，听起来就不靠谱。sched_ext 敢这么做，是因为它站在 BPF 上面。

BPF 程序在加载前要过 verifier。verifier 是个静态检查器，把你的字节码从头到尾走一遍，证明几件事：

    不会死循环，所有循环必须有可证明的上界
    不会越界访问内存，每个指针访问都要有边界检查
    只能调用白名单里的内核函数
    不会拿了锁不释放

过了才允许加载。过不了直接拒绝，机器毫发无伤。

那如果逻辑没问题、只是策略写蠢了呢？比如让所有任务都挤一个核上。

verifier 管不了这个。但内核也不会崩——sched_ext 有个看门狗，发现 BPF 调度器让某个任务太久没被调度，就把它摘掉，退回 CFS，同时在 /sys/kernel/sched_ext/nr_rejected 里记一笔。

最坏结果是你的调度器被开除，不是系统挂了。这条边界是整个设计能成立的前提。


九、跑起来就三步

先给骨架，第 3 篇拆细。

sched_ext 把自己注册成一个调度类 ext_sched_class，位置就是上面链接脚本里写死的那个——fair 之后、idle 之前。

任务需要 CPU 时，内核不自己决定放哪，而是调用你 BPF 程序里的回调。你的程序决定塞进哪个队列。

这个队列叫 DSQ，dispatch queue。它和传统 runqueue 不是一回事：DSQ 就是纯粹的任务容器，没有负载均衡、没有优先级树。每个 CPU 有一个本地 DSQ，另外还有全局 DSQ。

CPU 空了要挑活干，内核再调用你的 dispatch 回调，你的程序从 DSQ 里取一个交给它。

入队你定，队列你选，出队你定。内核只负责把选出来的任务真正切上去。

就这三步。


十、那为什么 6.6 里没有

时间线。

sched_ext 2022 年底开始做，Tejun Heo 主导。patch 集在邮件列表上改了七个大版本，两年多，2024 年 11 月随 6.12 发布。

中间卡了很久，争议集中在两件事：又多了一个能改调度的入口，维护负担谁背；BPF 程序出问题怎么兜底。最后靠看门狗和一堆约束谈下来的。

openEuler 24.03 LTS 的内核基线是 6.6，6.6 在 2023 年 10 月发布，比 sched_ext 进主线早一年。所以它没有。

这里有个坑，我一开始就掉进去了。

我当时的判断是："sched_ext 是 6.12 才有的，所以 6.6 一定没有。"

这话对上游成立，对发行版不成立。

发行版完全可以自己把特性回移进老内核。openEuler 在 26.09 就这么干了：它的 6.6 内核树里 kernel/sched/ext.c 真实存在，209 KB，但 openeuler_defconfig 里写着 CONFIG_SCHED_CLASS_EXT=n，默认关着。想用，要么装它单独发的 6.18 内核包，要么把这个开关打开重编。

所以正确的问法不是"这个特性是哪个版本才有的"，而是"我手上这个发行版的内核树里，到底有没有这段代码"。

这个问题只能用源码回答。不能靠搜索，不能靠博客，不能靠版本号推断。

第 2 篇会讲怎么查。


十一、路只有两条

代码不在，想用就得自己造。两条路。

路线 A：换内核。编一个 6.12，装在现有的 openEuler 24.03 上。用户态一个包都不用动，只是多一个内核。工作量一小时左右，主要是等编译。

路线 B：回移。把 sched_ext 那套代码搬进 6.6。ext.c 本体七千多行，还要动 task_struct、给 BPF 加 struct_ops 对调度器的支持、补一批 kfunc。参考实现是 Android 的 ACK android14-6.6，目前最完整的 6.6 回移。工作量以周计。

这个系列走 A。理由很实在：先把链路跑通，确认"在 openEuler 上能跑 sched_ext"这件事成立，再谈要不要投入回移。而且 A 产出的配置、脚本、观测手段，B 里全部能复用。


本篇对应提交

这一篇的每个判断，最后都固化成了能跑的检查。四条提交按顺序看，就是从靠版本号猜，到不再猜的完整过程。每一条下面都贴出当时的关键几行。

一、23c6656：先把"有没有"变成一条能跑的命令

为什么要有这一条：上面那四条判据如果只写在文档里，换个人还得重新猜一遍。写成脚本，退出码就是结论，不需要解释。

它做了什么：14 个文件 1432 行。其中 scripts/00-preflight.sh 159 行，分五段——发行版、内核版本、内核配置、运行时状态、工具链。

关键动作是"从内核配置里找一行"，它被包成一个函数：

    cfggrep() { grep -E "$1" "$CFG" || true; }

    line="$(cfggrep "^${sym}=")"

第一行的 || true 是关键。grep 找不到匹配时退出码是 1，脚本开头有 set -e，不兜住的话整个脚本会当场退出，读者看到的是"脚本崩了"，而不是"这一项没通过"。加 || true 让它"找不到"也算正常返回。

第二行用 ^CONFIG_X= 去匹配"以 CONFIG_X= 开头"的行。这就是那个 bug 的出生地：关闭的布尔选项在内核配置里不写成 CONFIG_X=n，而是写成

    # CONFIG_X is not set

前面有井号和空格。^CONFIG_X= 永远匹配不到它。脚本于是报告"符号不存在"，而我据此判断"代码不在，只能重编"——一步错，后面整条路线跟着错。

这一条提交里没有兜底，兜底是三条提交之后才补上的。

    https://github.com/qhc0609/openeuler-sched-ext/commit/23c6656

二、89dedef：改了文案，没改逻辑

为什么要有这一条：查到 26.09 的内核树里其实有 kernel/sched/ext.c，只是 defconfig 把它关了。这说明"没有 sched_ext"分两种情况——代码不在，和代码在但关着。既然分两种，提示语就得分开写。

它做了什么：加了各版本 × sched_ext 的对照表（docs/openeuler-kernel-matrix.md，156 行），把 preflight 的提示改成两种说法，README 同步更新。214 行新增。

问题在于：文案分开了，匹配逻辑还是坏的。is not set 那种行依然抓不到，所以脚本仍然只会输出第一种说法。两种情况的提示语都写好了，但永远只会走到其中一条。

这里有个容易忽略的点：改文案看起来像修好了，跑起来也确实「更清楚了」，但判据没变，结论就没变。

    https://github.com/qhc0609/openeuler-sched-ext/commit/89dedef

三、afde5ea：真正修掉匹配

为什么要有这一条：在真机上跑 preflight，输出和 24.03 SP4 的实际配置对不上，才发现上面那个匹配问题。同一次真机运行还暴露了第二个 bug，那个留给第 2 篇讲。

它做了什么：加了两行兜底，改了措辞，还顺手纠正了一个更危险的推断。

    line="$(cfggrep "^${sym}=" )"
    if [[ -z "$line" ]]; then
        line="$(cfggrep "^# ${sym} is not set")"
    fi

第一行按 = 形式找；找不到（$line 为空），第二行再按 is not set 形式找。两次都找不到，才是真的没有。

顺序是先找启用形式、再找关闭形式。反过来也能用，但先找启用能让"已启用"这个最常见的情况少一次 grep。

比这两行更重要的是下面这段注释，它改的是一个判断：

    # 注意：符号存在 ≠ 已回移。24.03 SP4 就是反例——配置里有这一行，
    # 但 OLK-6.6 树里 kernel/sched/ext.c 根本不存在。

原来的提示是"符号存在但被关掉，说明该树已回移，改 =y 重编即可"。这个推断在 26.09 上成立，在 24.03 SP4 上不成立——它的配置里确实有这一行，但源码树里根本没有 ext.c。这一行是发行版自己的补丁队列带进来的残留，不代表代码在。

一个符号出现在配置文件里，只能证明"有人写过这个符号"，不能证明"代码在这棵树里"。这条区别后来成了第 5 篇讲证据分级的起点。

    https://github.com/qhc0609/openeuler-sched-ext/commit/afde5ea

四、3b44ac5：把真机输出存下来

为什么要有这一条：上面所有结论都来自一台机器的一次运行。不把原始输出存进仓库，半年后谁都无法复核，包括我自己。

它做了什么：四条命令的原始输出写进 docs/verified-24.03-sp4.md（97 行），README 补了对应段落。

    uname -r                             -> 6.6.0-159.4.3.154.oe2403sp4.x86_64
    grep SCHED_CLASS_EXT /boot/config-*  -> # CONFIG_SCHED_CLASS_EXT is not set
    ls -d /sys/kernel/sched_ext          -> No such file or directory
    grep -ci scx_ /proc/kallsyms         -> 0

四条全部为负。这个"全部为负"本身就是结论：不是某一项没查到，是四条独立路径同时指向"没有"。

这条提交的说明里还留了一个未解疑点，没有假装已经搞清：配置里有符号，但 OLK-6.6 上游树里没有 ext.c，也没有 Kconfig 条目，所以 SP4 的构建树一定额外带了一批补丁。当时写的是"标记，不假设"。

    https://github.com/qhc0609/openeuler-sched-ext/commit/3b44ac5

提交方法本身没什么花哨的：

    git add -A
    git commit -m "docs: add verified 24.03 LTS SP4 baseline with real machine output"
    git push origin main

值得说的是 commit message 里写什么。上面这条的正文写了实测的四条输出、哪条前提成立哪条不成立、以及一个还没搞清楚的疑点。

不写"更新文档"这种话。半年后自己回来看，只有"当时测到什么、据此得出什么、哪里还没把握"有用。
