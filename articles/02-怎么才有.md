怎么让内核里真的有 sched_ext

—— 编一个 6.12，装进现有的 openEuler（第 2/6 篇）


一、先定三件事，再动手

上一篇的结论是：24.03 的内核里没有 sched_ext 的代码，打开开关也没用，必须自己造一个。

动手之前有三个决定要先定，定错了后面全是白干。

第一个决定：编哪个版本。

sched_ext 是 6.12 合入主线的，所以下限就是 6.12。再往上 6.13、6.14 都行，但没必要——我们要的是"能用"，不是"最新"。选 6.12 还有一个好处：它是 LTS，社区维护周期长，出问题查得到资料。

第二个决定：配置从哪来。

这是最容易做错的一步。有两条路：从 defconfig 开始自己配，或者拿现有系统的配置当基线。

我选后者。原因很实际：你现在这个系统跑得好好的，网卡、磁盘控制器、文件系统、VMware 的半虚拟化驱动全都配好了。从零配一遍，装完重启很可能网卡起不来、磁盘认不到，你连 SSH 都进不去，只能去 VMware 控制台救。

用 /boot/config-$(uname -r) 当基线，等于把"这个系统能跑起来"这件事直接继承过来。我们只在这上面叠加 sched_ext 需要的几项。

第三个决定：装完怎么回退。

答案不是"小心一点"，是快照。装内核会改 GRUB，改错了就进不了系统。VMware 打个快照，一条命令就能回到现在。

    vmrun -T ws snapshot "D:\vms\openEuler-24.03\openEuler-24.03.vmx" "pre-6.12-kernel"

回退：

    vmrun -T ws revertToSnapshot "D:\vms\openEuler-24.03\openEuler-24.03.vmx" "pre-6.12-kernel"

这个快照必须在**开始装内核之前**打，不是在编译之前。编译不碰系统，装了才碰。


二、配置片段：每个符号为什么要在

sched_ext 不是单独一个开关，它下面挂着一串依赖。缺一个，Kconfig 会静默地把它关掉，你编译完发现还是没有，还找不到原因。

所以我把需要的符号显式写成一个片段文件，缺了就立刻报错，而不是等编译完才发现。

片段长这样：

    # sched_ext 本体
    CONFIG_SCHED_CLASS_EXT=y

    # BPF 基础设施
    CONFIG_BPF_SYSCALL=y
    CONFIG_BPF_JIT=y
    CONFIG_BPF_JIT_ALWAYS_ON=y
    CONFIG_BPF_UNPRIV_DEFAULT_OFF=y

    # BTF
    CONFIG_DEBUG_INFO=y
    CONFIG_DEBUG_INFO_BTF=y
    CONFIG_DEBUG_INFO_BTF_MODULES=y

    # 调度器分组 / cgroup
    CONFIG_CGROUP_SCHED=y
    CONFIG_FAIR_GROUP_SCHED=y
    CONFIG_EXT_GROUP_SCHED=y

    # 观测用
    CONFIG_PERF_EVENTS=y
    CONFIG_FTRACE=y
    CONFIG_BPF_EVENTS=y

    # 调度核心
    CONFIG_SCHED_CORE=y
    CONFIG_SMP=y

逐个说清楚，不然你抄完不知道为什么。

CONFIG_SCHED_CLASS_EXT 是本体。它在 init/Kconfig 里定义，有一堆 depends，只要有一个不满足就自动变 n。

BPF_SYSCALL 是基础。没有它，用户态没法通过 bpf() 系统调用加载程序，sched_ext 就是死的。

BPF_JIT 把字节码编译成本机指令。解释执行太慢，调度器在热路径上，必须 JIT。BPF_JIT_ALWAYS_ON 是强制 JIT，不给关的机会。

BPF_UNPRIV_DEFAULT_OFF 是把非特权 BPF 默认关掉。这是个安全默认值，跟 sched_ext 无关，但发行版通常这么配，保持一致性。

DEBUG_INFO_BTF 是这篇里最容易被忽略、但绝对不能少的一项。

BTF 是 BPF Type Format，它把内核里所有结构体的布局（字段名、类型、偏移）编成一份元数据。为什么需要它？

因为 sched_ext 的接口是一张函数指针表，内核要知道"你的 BPF 程序里那个叫 enqueue 的函数，签名是不是跟我要的一样"。这个类型检查靠 BTF 做。没有 BTF，struct_ops 注册不上，加载直接失败。

DEBUG_INFO 是 BTF 的前置。DEBUG_INFO_BTF_MODULES 是给模块也生成 BTF，我们的场景其实用不到，但打开无害。

CGROUP_SCHED 和 FAIR_GROUP_SCHED 是 cgroup 的 CPU 控制。EXT_GROUP_SCHED 是 sched_ext 自己的分组支持——如果你的调度器要按 cgroup 分权重，需要它。

PERF_EVENTS、FTRACE、BPF_EVENTS 是观测用的。调度器调得对不对，得靠 tracepoint 看，这三个不开，后面你连它在干什么都不知道。

SCHED_CORE 是 core scheduling，SMT 场景下防止跨线程侧信道攻击用的。SMP 是多核，单核机器跑不了 sched_ext。

这些符号不是拍脑袋列的，是从 Kconfig 的 depends 链条上一层层扒下来的。列全了有个好处：合并配置的时候，如果哪个依赖不满足，merge_config 会当场报出来，而不是让 olddefconfig 悄悄改掉。


三、第一个坑：证书

第一次编译，四分四十三秒就挂了。报错是：

    make[3]: *** 没有规则可制作目标"certs/openeuler-cert.pem"，
    由"certs/x509_certificate_list" 需求。停止。

这个坑值得单独讲，因为**任何"拿发行版配置编原版内核"的人都会踩**。

原因在这儿：openEuler 的 /boot/config 里有一行

    CONFIG_SYSTEM_TRUSTED_KEYS="certs/openeuler-cert.pem"

这是内核用来验证模块签名的信任证书。openEuler 用它给自己签的模块做背书。

问题是这个文件只存在于 openEuler 自己的内核源码树里。你从 kernel.org 下的 linux-6.12.tar.xz 里，certs/ 目录下只有几个上游自带的测试证书，没有 openeuler-cert.pem。

于是构建流程走到"生成 x509 证书链"这一步，发现要的输入文件不存在，make 直接停。

修法一行：

    scripts/config --file .config --set-str SYSTEM_TRUSTED_KEYS ""

把它清空。清空之后内核会自己生成一对临时密钥给自己签名，构建继续。

这样做有副作用吗？有，但对我们无影响。清空信任链意味着你编出来的内核不信任 openEuler 官方签名的模块。我们的场景是自己编、自己装、不加载第三方签名模块，所以无所谓。

如果你要在生产上做模块签名，正确做法是把发行版的证书文件拷进源码树，而不是清空。这一点得说清楚，别照抄到不该用的地方。

顺便记一个教训。这次编译其实四分四十三秒就死了，但我的等待脚本白等了五十二分钟。

原因是脚本只判断"产物出现了没有"，没判断"make 进程还活着没有"。进程早退了，产物永远不会出现，循环就一直转。

后来改成两个条件一起看：进程消失 + 产物不存在 = 失败。这个改法在后面省了很多时间。


四、第二个坑：脚本找不到自己的配置文件

配置片段放在仓库根目录的 configs/ 下，脚本要去读它。第一版脚本这么写的：

    cd "$SRC"                              # 进内核源码树
    FRAG="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)/configs/sched-ext.fragment"

看起来没问题，实际全错。

因为脚本是被相对路径调用的：./scripts/10-build-kernel.sh。这时候 BASH_SOURCE[0] 就是字符串 "./scripts/10-build-kernel.sh"，不是绝对路径。

dirname 拿到 "./scripts"，再拼上 ".."，得到 "./scripts/.."，也就是当前目录。但这时候已经 cd 进 linux-6.12 了，所以它去找的是

    /root/src/linux-6.12/configs/sched-ext.fragment

这个文件当然不存在。报错是：

    找不到配置片段: /root/src/linux-6.12/configs/sched-ext.fragment

修法很简单，但要想明白为什么：**在任何 cd 之前**，把脚本所在目录和仓库根都解析成绝对路径。

    SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
    REPO_ROOT="$(cd "$SCRIPT_DIR/.." && pwd)"
    FRAG="$REPO_ROOT/configs/sched-ext.fragment"

    cd "$SRC"        # 之后才允许 cd

这类 bug 的特征是：在开发者机器上跑得好好的，换个调用方式就挂。凡是脚本里既有 cd 又有 BASH_SOURCE 的地方，都要检查一遍顺序。


五、编译

配置合完之后，先确认符号真的生效了。这一步不能跳，因为 olddefconfig 有可能把你设的 =y 改回 n。

    $ grep -E "CONFIG_SCHED_CLASS_EXT=|CONFIG_EXT_GROUP_SCHED=" .config
    CONFIG_SCHED_CLASS_EXT=y
    CONFIG_EXT_GROUP_SCHED=y

同时确认源码树里真的有那个文件：

    $ ls -l kernel/sched/ext.c
    -rw-r--r-- 1 root root 210944 ... kernel/sched/ext.c

210 KB，这就是 sched_ext 的本体。看到这个文件，才说明"代码真的在树里"，不是配置写了个空壳。

然后开始编：

    $ make -j4

为什么是 4 不是 8？

这台 VM 分了 4 个 vCPU。make 的 -j 值超过核数，进程会互相抢 CPU，还要抢内存带宽，实际更慢。经验值是核数的 1 到 1.5 倍，4 核就用 4 到 6。内存也要算：每个 gcc 进程峰值几百 MB，8 GB 内存跑 -j8 很容易触发 OOM，编译到一半被内核杀掉，你还以为是代码问题。

实际耗时：内核本体将近五十分钟，之后编模块又补了二十多分钟。慢的主要原因是 DEBUG_INFO_BTF=y——生成 BTF 要额外解析整个 vmlinux 的调试信息，这一步很重。但前面说了，不能关。

编完的产物：

    $ ls -lh arch/x86/boot/bzImage
    -rw-r--r-- 1 root root 14M ... arch/x86/boot/bzImage

14 MB。到这里只证明"编出来了"，还没证明"能启动"。


六、安装：四步，少一步都不行

安装不是 copy 一个文件那么简单，要做四件事。

第一步，装模块：

    $ make modules_install

模块装到 /lib/modules/6.12.0/。这一步之后 depmod 会自动跑，生成模块依赖表。

第二步，装内核本体：

    $ make install

把 bzImage 复制成 /boot/vmlinuz-6.12.0，把 System.map 和 config 也放过去。

第三步，更新 GRUB：

    $ grub2-mkconfig -o /boot/grub2/grub.cfg

这一步会扫描 /boot 下的所有 vmlinuz，重新生成启动菜单。跑完你会看到它找到了三个内核：

    Found linux image: /boot/vmlinuz-6.12.0
    Found linux image: /boot/vmlinuz-6.6.0-159.4.3.154.oe2403sp4.x86_64
    Found linux image: /boot/vmlinuz-0-rescue-...

第四步，重建 initramfs：

    $ dracut -f --kver 6.12.0

initramfs 是启动时先加载的小型根文件系统，里面装着挂载真实根分区需要的驱动。这一步不做，或者做的时候用错了内核版本，重启就会卡在 "dracut-initqueue timeout"，进不去系统。


七、第三个坑：GRUB 不会自动选新内核

装完四步，看起来齐了。查一下 GRUB 的条目顺序：

    $ grubby --info=ALL | grep -E "^index|^kernel="
    index=0
    kernel=/boot/vmlinuz-6.12.0
    index=1
    kernel=/boot/vmlinuz-6.6.0-159...
    index=2
    kernel=/boot/vmlinuz-0-rescue-...

6.12 排在 index=0。到这里很多人就重启了，然后发现起来还是 6.6。

因为 index=0 只是**菜单里的排序**，不是**默认启动项**。

openEuler 的 GRUB 配的是 GRUB_DEFAULT=saved，真正决定启动哪个的是 grubenv 里的 saved_entry：

    $ grub2-editenv list
    saved_entry=openEuler (6.6.0-159.4.3.154.oe2403sp4.x86_64) 6.6.0-...

它还是 6.6。

grub2-mkconfig 只重写菜单，不改这个变量。所以你装完、重启、进了旧内核，会以为"装失败了"，其实装得好好的，只是没选中。

正确的做法是显式设置：

    $ grubby --set-default /boot/vmlinuz-6.12.0

    $ grub2-editenv list
    saved_entry=openEuler (6.12.0) 6.12.0

    $ grubby --default-kernel
    /boot/vmlinuz-6.12.0

三条命令都确认指向 6.12，才算真的准备好。这个坑我在脚本里补上了，现在装完会自动设置。

顺便说一句兜底：菜单里那个 0-rescue 条目是救援内核，万一新内核起不来，在 GRUB 菜单里选它，还是能进系统把默认项改回去。加上快照，等于两道保险。


八、重启之后

    $ uname -r
    6.12.0

    $ ls -d /sys/kernel/sched_ext
    /sys/kernel/sched_ext

两行输出，说明两件事：跑的是新内核，而且 sched_ext 子系统初始化成功了。

用户态一个包都没动，还是 openEuler 24.03 的原样。变的只是内核。

到这里"使能"完成。但注意，这只是"有这个能力"，还没有任何调度器在跑。就像你装好了发动机，车还没发动。

下一篇讲怎么发动：BPF 调度器到底怎么写、怎么加载、内核是怎么把调度权交出去的。


九、本篇对应的提交

这一篇有两条提交。第一条修的是"脚本 cd 之后就把自己弄丢了"，第二条修的是"把发行版的配置喂给原版源码树"。两个 bug 都只有真编一次才会暴露，看文档永远看不出来。

**afde5ea：脚本 cd 之后就找不到自己了**

为什么要有这一条：10-build-kernel.sh 要在内核源码树里干活，所以中途必须 cd 进去。它同时又需要读仓库里的配置片段。这两件事放在一起，就出问题了。

具体是这样。脚本开头用相对路径解析自己的位置：

    SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
    REPO_ROOT="$(cd "${SCRIPT_DIR}/.." && pwd)"

BASH_SOURCE[0] 的值取决于你怎么调用它。用 ./scripts/10-build-kernel.sh 调用，它就是 ./scripts/10-build-kernel.sh，是一个相对路径。如果脚本在 cd 进 linux-6.12 之后才解析这个变量，dirname 算出来的相对路径就是相对当前目录的，于是 REPO_ROOT 指向了 linux-6.12 的父级，配置片段被找成 linux-6.12/configs/sched-ext.fragment。

报错是"找不到配置片段"。看起来像文件没生成，实际上是路径算错了。

修法的关键是第二行那个 cd：它把 SCRIPT_DIR 立刻转成绝对路径，所以 REPO_ROOT 也变成绝对的。之后脚本里再怎么 cd，这两个变量都不受影响。

    SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
    REPO_ROOT="$(cd "${SCRIPT_DIR}/.." && pwd)"

注释里那句 Resolve the repo root BEFORE any cd 就是这个意思。这种 bug 的特征是：从别的目录调用就正常，从仓库根目录调用就挂——因为它取决于调用者的当前目录。

同一次真机运行还暴露了 preflight 的匹配 bug，两条 bug 合成一条提交，那个 bug 在第 1 篇讲过。

    https://github.com/qhc0609/openeuler-sched-ext/commit/afde5ea

**4baba31：把发行版的配置喂给原版源码树**

为什么要有这一条：这是整个构建流程里唯一一个"必然踩"的坑。不是偶发，是设计上的不兼容。

第一次真编，跑到 4 分 43 秒挂掉：

    make[3]: *** 没有规则可制作目标"certs/openeuler-cert.pem"，
                由"certs/x509_certificate_list"需求

原因在 /boot/config 里：

    CONFIG_SYSTEM_TRUSTED_KEYS="certs/openeuler-cert.pem"

openEuler 用它自己的签名证书给内核模块签名，证书文件在 openEuler 自己的源码树里。我们把这份配置合并进原版 6.12 源码树，那个文件根本不存在，certs 阶段自然找不到。

修法不是"把证书拷过来"，是直接清空：

    if grep -qE '^CONFIG_SYSTEM_TRUSTED_KEYS=".+"' .config; then
        ./scripts/config --file .config --set-str SYSTEM_TRUSTED_KEYS ""
    fi
    if grep -qE '^CONFIG_SYSTEM_REVOCATION_KEYS=".+"' .config; then
        ./scripts/config --file .config --set-str SYSTEM_REVOCATION_KEYS ""
    fi

逐行看。grep -q 只问"有没有"，不打印；正则要求引号里至少有一个字符，所以已经是空串的情况不会重复处理，重复执行是安全的。./scripts/config 是内核自带的配置工具，--set-str 按字符串写值，空串就是关掉这条信任链。

清空之后内核改用自签名。对本项目够用——我们不发布签过名的内核模块，也不需要 openEuler 的密钥信任链生效。如果要发布签名模块，这里就得改成把证书拷进源码树，不能清空。

顺序很重要。这段必须落在 merge_config 之后、olddefconfig 之前：

    ./scripts/kconfig/merge_config.sh -m -O . .config "$FRAG"
    ...清空两个 KEYS...
    make olddefconfig

晚于 olddefconfig 的话，配置已经被规范化过一轮，再改还得重新算一遍依赖。

这条提交顺手把坑写进了 README 的常见问题。因为这个坑换任何发行版都会踩——Debian 指向 debian/certs，Ubuntu 指向自己的证书，文件名不同，问题一模一样。

    https://github.com/qhc0609/openeuler-sched-ext/commit/4baba31b0dd7f726ad20d653522e68e5f0cb7447

提交方法：

    $ git add -A
    $ git commit -m "fix(build): blank SYSTEM_TRUSTED_KEYS when reusing a distro kernel config"
    $ git push origin main

这条 message 的正文里写了完整报错、为什么会出现、清空之后有什么副作用、什么场景下不能这么干。写这些不是为了好看，是因为三个月后换台机器重来一遍，唯一能救你的就是当时记下的这些。


十、下一篇

内核有了，能力有了，但还没人用它。

下一篇进核心：BPF 调度器到底长什么样。sched_ext 给你的那张函数表有十几个回调，实际写一个能跑的调度器只需要其中三个。会讲到 DSQ 到底是什么、struct_ops 怎么把 BPF 函数注册成内核回调、以及为什么加载的时候内核会先做一次类型检查。
