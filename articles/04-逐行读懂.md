逐行读懂这个 200 行的调度器

—— minimal.bpf.c 每一行在干什么，以及三个卡住我的构建错误（第 4/6 篇）


一、先看文件

仓库里两个文件，一个 Makefile：

    scheds/minimal.bpf.c    216 行（含注释，去掉注释约 70 行）
    scheds/minimal.c        159 行（用户态加载器）
    scheds/Makefile          75 行

minimal.bpf.c 编成 BPF 字节码，加载进内核接管调度。minimal.c 是用户态程序，负责把它加载进去。

两个文件不链接，是两段独立的构建。这一点后面会有一个专门的坑。


二、第 1 行到第 35 行：那个奇怪的头文件

    #include <scx/common.bpf.h>

就这一行，是我花时间最多的地方。

直觉上应该 include <bpf/bpf_helpers.h>，因为写 BPF 程序都是这么开的头。但在这里不行，原因有四层。

第一层，这个头文件里包了 vmlinux.h。vmlinux.h 是从运行中内核的 BTF 导出的类型定义，里面有 struct task_struct、struct sched_ext_ops、SCX_DSQ_LOCAL 这些你要用的东西。没有它，你连参数类型都写不出来。

第二层，它包了 bpf_helpers.h 和 bpf_tracing.h，提供 SEC() 宏。

第三层，也是最关键的：所有 scx_bpf_ 开头的函数声明都在这里。

这些函数（scx_bpf_dispatch、scx_bpf_consume、scx_bpf_create_dsq……）不是普通内核函数，是 kfunc。它们的实现在 kernel/sched/ext.c 里，BPF 程序通过 __ksym 引用，加载时由 libbpf 解析成真实内核地址。

自己写 extern 声明行不行？行，但你得保证签名和内核版本完全一致。6.12 和 6.13 的参数可能就变了。用官方头文件，等于把这件事交给内核源码树。

第四层，SCX_OPS_DEFINE 宏也在这里。

然后是我真正卡住的地方。

libbpf 1.2.2 的 bpf_tracing.h 里没有 BPF_STRUCT_OPS 宏。它只在 sched_ext 自己的头文件里定义。而你也不能自己手写一个替代——因为这个名字和 vmlinux.h 里的一个枚举常量撞了。

真实报错：

    error: redefinition of 'BPF_STRUCT_OPS' as different kind of symbol
    note: previous definition is here ./vmlinux.h:6960: BPF_STRUCT_OPS = 44

vmlinux.h 第 6960 行有个枚举，BPF_STRUCT_OPS = 44，是 bpf_attach_type 的一个取值。你再用 #define 定义一个同名宏，C 编译器直接报"同一符号被定义成不同类型"。

所以正确的解法不是"绕过"，是"用对来源"——把内核源码树的 tools/sched_ext/include 加进 include 路径，让官方的 scx/common.bpf.h 进来。它内部对宏的处理已经和这个枚举共存了。

这就是 Makefile 里 SCX_INCLUDE 存在的唯一原因。


三、第 38 行：为什么许可证必须是 GPL

    char _license[] SEC("license") = "GPL";

内核只允许 GPL 兼容许可证的 BPF 程序调用非 GPL-only 的内核符号。

scx_bpf_* 这一批 kfunc 全部标记为 GPL-only。写别的，加载时报错，而且报错信息不会直接告诉你"因为许可证"——它会说某个 kfunc 找不到，让你去查一个不存在的问题。

这一行是字符串，不是注释，会被编进 ELF 的 license 段，加载时由内核读取。


四、第 49 行：为什么要自己建队列

    #define SHARED_DSQ 0

上一篇讲过 DSQ 有三种。这里用的是自建 DSQ，编号 0。

为什么不用现成的 SCX_DSQ_GLOBAL？因为内置全局队列不能当优先级队列用，只能 FIFO。现在这个最小实现确实只用了 FIFO，但接口留着——后面想改成按 vtime 排序，只需要把入队函数换掉，队列编号不用动。

0 是个占位值，用户自建 DSQ 的编号由调用方定，只要不和内置的特殊值冲突（那些都是 2 的 63 次方量级的大数）就行。


五、第 60 行到第 71 行：那个统计 map

    struct {
        __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
        __uint(key_size, sizeof(u32));
        __uint(value_size, sizeof(u64));
        __uint(max_entries, 2);
    } stats SEC(".maps");

这不是调试代码，是必需品。

原因：加载成功和真的在调度，是两件事。

bpf_object__load() 返回 0，只证明 verifier 放行了、struct_ops 挂上了。它不证明内核真的调用了你的 enqueue。完全有可能挂上去之后一个任务都没经过你的回调——比如你实现错了，内核走了默认路径。

所以需要一个"内核真的调用了我"的证据。这个 map 在回调里自增，用户态每秒读一次。数字在涨，就是铁证。

为什么用 PERCPU_ARRAY 而不是普通 ARRAY？因为每个 CPU 一份独立副本，写的时候不用加锁。调度器在热路径上加锁，代价不可接受。代价是读的时候要把所有 CPU 的值加起来，用户态多几行代码，值得。

max_entries 是 2，对应下面两个下标：

    enum {
        STAT_LOCAL  = 0,   /* 直接塞进某个 CPU 本地队列的次数 */
        STAT_SHARED = 1,   /* 塞进全局队列的次数 */
    };

两个计数器，正好对应两条入队路径。


六、第 74 行：为什么不检查失败

    static __always_inline void stat_inc(u32 idx)
    {
        u64 *cnt = bpf_map_lookup_elem(&stats, &idx);

        if (cnt)
            (*cnt)++;
    }

取不到就静默返回，不报错、不打印、不影响调度。

这是刻意的。统计是附加功能，调度是主功能。如果统计失败能导致调度失败，那这个统计就是负债。

__always_inline 是为了让编译器一定内联。BPF 程序的函数调用有额外开销，热路径上每个 enqueue 都调一次，内联掉省下的不只是函数调用本身。


七、第 95 行到第 121 行：select_cpu，挑核

    s32 BPF_STRUCT_OPS(minimal_select_cpu, struct task_struct *p,
                       s32 prev_cpu, u64 wake_flags)
    {
        bool is_idle = false;
        s32 cpu = scx_bpf_select_cpu_dfl(p, prev_cpu, wake_flags, &is_idle);

        if (is_idle) {
            stat_inc(STAT_LOCAL);
            scx_bpf_dispatch(p, SCX_DSQ_LOCAL, SCX_SLICE_DFL, 0);
        }

        return cpu;
    }

BPF_STRUCT_OPS 这个宏展开成两件事：给函数加 SEC("struct_ops/minimal_select_cpu") 段标记，以及声明成 BPF_PROG 类型。段名里的 minimal_select_cpu 就是它在回调表里的名字。

三个参数：p 是要调度的任务，prev_cpu 是它上次跑的核，wake_flags 是唤醒标志（比如 WF_SYNC 表示唤醒者要让出 CPU）。

第一行不自己实现选核逻辑，借内核的默认实现。scx_bpf_select_cpu_dfl 会考虑缓存亲和性、空闲核、NUMA 距离。真实调度器在这里写自己的逻辑，最小实现没必要重复造轮子。

is_idle 是出参，回填挑中的那个核当时是否空闲。

然后是这段的核心：

    if (is_idle) {
        scx_bpf_dispatch(p, SCX_DSQ_LOCAL, SCX_SLICE_DFL, 0);
    }

如果那个核空闲，直接把任务塞进它的本地 DSQ，不绕全局队列。

这是性能关键。不这么做，任务要先入全局队列，等那个核下次触发 dispatch 才能被取走，中间多一次唤醒延迟。对交互式任务，这就是"敲键盘有顿感"。

SCX_DSQ_LOCAL 会被解析成"当前 CPU 的本地队列"，只有这个核能取，不参与抢夺。

最后 return cpu，告诉内核：挑中了这个核。


八、第 133 行到第 147 行：enqueue，策略的落点

    void BPF_STRUCT_OPS(minimal_enqueue, struct task_struct *p, u64 enq_flags)
    {
        stat_inc(STAT_SHARED);
        scx_bpf_dispatch(p, SHARED_DSQ, SCX_SLICE_DFL, enq_flags);
    }

三行。其中一行是统计。

enq_flags 说明入队原因：新任务、被唤醒、时间片用完、被抢占。最小实现不看它，真实调度器会用它区分处理——比如时间片用完的任务放到队尾，被抢占的放回队头。

SCX_SLICE_DFL 是 20000000 纳秒，20 毫秒。任务这次最多连续跑 20 ms，然后回队列重新排。

这一行就是"策略"的全部：先来先跑，谁先入队谁先出队。

想按权重排序，把这行换成 scx_bpf_dispatch_vtime()，传一个根据 p->scx.weight 算出来的虚拟时间。想按 deadline，换成 scx_bpf_dispatch() 配合自己维护的时间戳。

策略只有一个落点，改起来不会漏。


九、第 159 行到第 170 行：dispatch，取谁

    void BPF_STRUCT_OPS(minimal_dispatch, s32 cpu, struct task_struct *prev)
    {
        scx_bpf_consume(SHARED_DSQ);
    }

一个函数调用，没有循环。

scx_bpf_consume 从指定 DSQ 取一个任务。取到了内核就把它切上去；队列空则返回 false，内核让这个 CPU 进 idle。

为什么没有 while 循环批量取？因为 BPF verifier 要求所有循环有可证明的上界。写 while 不是不行，但你得让它能静态证明"这个循环一定会结束"。最小实现不碰这条线。


十、第 178 行到第 186 行：init，建队列

    s32 BPF_STRUCT_OPS_SLEEPABLE(minimal_init)
    {
        return scx_bpf_create_dsq(SHARED_DSQ, -1);
    }

注意后缀是 BPF_STRUCT_OPS_SLEEPABLE，不是 BPF_STRUCT_OPS。

区别在于它展开出的段名是 SEC("struct_ops.s/...")，那个 .s 表示这个回调允许睡眠。

为什么需要？因为 scx_bpf_create_dsq 要分配内存，分配内存可能睡眠。普通 struct_ops 回调运行在不可睡眠的上下文里，调它会报错。

第二个参数 -1 是 NUMA 节点，-1 表示不绑定节点。

返回值直接 return 出去：0 表示成功，非 0 会导致整个调度器加载失败。


十一、第 195 行到第 197 行：exit，空的

    void BPF_STRUCT_OPS(minimal_exit, struct scx_exit_info *ei)
    {
    }

空实现。

但真实调度器一定要在这里打印 ei 里的退出原因。原因包括：用户态主动退出、运行出错、被看门狗踢掉。

不打印的后果是：调度器某天突然没了，CPU 回到 CFS，性能变了，而你不知道为什么。dmesg 里只有一行"disabled"，没有原因。


十二、第 209 行到第 215 行：把函数登记成一张表

    SCX_OPS_DEFINE(minimal_ops,
               .select_cpu = (void *)minimal_select_cpu,
               .enqueue    = (void *)minimal_enqueue,
               .dispatch   = (void *)minimal_dispatch,
               .init       = (void *)minimal_init,
               .exit       = (void *)minimal_exit,
               .name       = "minimal");

这个宏展开成：

    SEC(".struct_ops.link") struct sched_ext_ops minimal_ops = {
        .select_cpu = ...,
        ...
    };

一个带段标记的全局结构体变量。

为什么强制转成 (void *)？因为内核里的成员类型是函数指针，而 BPF 程序编译出来是 BPF_PROG 类型，两者在 C 里不兼容，不转换编译不过。真正的类型校验不在这里做，在加载时用 BTF 做。

.name 是字符串 "minimal"，它会出现在 /sys/kernel/sched_ext/root/ops 里。这是你确认"谁在跑"的唯一直接手段。

33 个格子里只填了 5 个，剩下 28 个是 0（空指针），内核遇到时走默认行为。


十三、用户态加载器：四步，顺序不能错

minimal.c 一共四步。

第一步，打开：

    obj = bpf_object__open_file(obj_path, NULL);

这一步只是把 ELF 读进内存，解析段和 BTF，完全不碰内核。它失败通常是文件路径错了。

第二步，加载：

    err = bpf_object__load(obj);

这是最容易失败的一步。它会过 verifier、过 BTF 类型校验、解析所有 kfunc 地址、创建 map。常见失败原因有三类：verifier 拒绝（循环没上界、指针越界、调了白名单外的 kfunc）、BTF 类型不匹配（回调签名和内核表对不上）、内核没开 CONFIG_SCHED_CLASS_EXT。

失败时 libbpf 会把 verifier 的完整日志打到 stderr。那份日志很长，但它会明确指出第几条指令、什么问题。别忽略。

第三步，挂上：

    ops_map = bpf_object__find_map_by_name(obj, "minimal_ops");
    link = bpf_map__attach_struct_ops(ops_map);

找 map 用的名字是 BPF 程序里那个变量名——minimal_ops。

attach 成功的那一刻，调度器就开始接管了。不需要重启，不需要额外命令，不需要改任何配置。

第四步，每秒读一次统计：

    while (!exiting) {
        print_stats(stats_fd, libbpf_num_possible_cpus());
        sleep(1);
    }

print_stats 里有个细节：因为 map 是 PERCPU_ARRAY，bpf_map_lookup_elem 会把所有 CPU 的值一次性拷出来（长度等于 CPU 数），所以要累加：

    for (int i = 0; i < nr_cpus; i++)
        sum += vals[i];

只读 vals[0] 会得到一个 CPU 的局部数字，看起来像"计数器不涨"。

销毁顺序也有讲究：

    if (link)
        bpf_link__destroy(link);
    if (obj)
        bpf_object__close(obj);

link 必须先销毁。link 一销毁，内核就把 sched_ext 注销，任务全部回到 CFS。反过来先 close obj，link 就悬空了。

这个顺序保证了"Ctrl+C 就回 CFS，不用重启"。


十四、三个构建坑，报错原文

第一个坑，头文件来源。上一篇讲过了，报错是：

    error: redefinition of 'BPF_STRUCT_OPS' as different kind of symbol
    note: previous definition is here ./vmlinux.h:6960: BPF_STRUCT_OPS = 44

解法：加 -I$(SCX_INCLUDE)，用内核树的 scx 头文件。

第二个坑，BPF 目标不能参与链接。

我最初的 Makefile 把 minimal.bpf.o 放进了链接行：

    $(CC) -o minimal minimal.c minimal.bpf.o -lbpf

报错：

    /usr/bin/ld: minimal.bpf.o: Relocations in generic ELF (EM: 247)
    /usr/bin/ld: minimal.bpf.o: error adding symbols: file in wrong format

EM: 247 是 EM_BPF，BPF 字节码在 ELF 里的机器类型编号。系统链接器不认识它。

正确的理解是：minimal.bpf.o 不是编译期依赖，是运行时数据。它由 bpf_object__open_file() 在程序跑起来之后读进去。所以它必须出现在 all 目标里（要生成），但绝不能出现在链接行上。

第三个坑，-g 不能省。

BPF 编译参数是：

    clang -g -O2 -target bpf -D__TARGET_ARCH_x86 -I. -I$(SCX_INCLUDE) -c

-g 生成 BTF 调试信息。libbpf 就是靠它来校验 struct_ops 的函数签名。去掉 -g，加载时类型检查必然失败，而且报错不会说"你少了 -g"。

还有一个隐藏的：vmlinux.h 必须从当前运行内核生成，换内核后要删掉重新生成。6.6 生成的 vmlinux.h 拿去编 6.12 的调度器，编译能过，加载会失败——因为结构体布局变了，字段偏移全错。Makefile 里 vmlinux.h 是个普通目标，不会自动感知内核变化，所以 make clean 之后重来是标准动作。


十五、跑起来是什么样

    $ sudo ./minimal ./minimal.bpf.o
    调度器已挂载。查看接管状态：
      cat /sys/kernel/sched_ext/root/ops
    Ctrl+C 退出（退出后 CPU 自动回到 CFS）

    local=4        shared=1
    local=32       shared=14
    local=43       shared=23
    local=50       shared=34

local 是"直接塞本地队列"的次数，shared 是"进全局队列"的次数。两个都在涨。

local 涨得比 shared 快，符合预期：任务唤醒时目标核往往空闲，走了 select_cpu 的快路径，没进全局队列。

下一篇讲怎么用这些数字、sysfs 和 dmesg 组成一条完整的证据链，证明"它真的在调度"，而不是"加载成功了"。
