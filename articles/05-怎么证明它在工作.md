跑起来之后怎么证明它在工作

—— 四级证据链、看门狗，和那个骗过我的 [ OK ]（第 5/6 篇）


一、"加载成功"这句话不能信

上一篇最后，程序打印了 local 和 shared 两组数字。看到数字在涨，人就容易下结论：成了。

但这句话必须拆开。加载成功和真的在调度，是两件不同的事。

加载成功只证明 verifier 放行了、struct_ops 挂上了。它不证明内核真的调用了你的 enqueue。完全可能挂上去之后一个任务都没经过你——比如你写错了，内核走了默认路径。

所以要证明"它在工作"，得拿出不止一条证据，而且要能说清每条证据的强度。

我按强度排了四级，从弱到强。


二、第一级：CONFIG_SCHED_CLASS_EXT=y

    $ grep CONFIG_SCHED_CLASS_EXT /boot/config-$(uname -r)
    CONFIG_SCHED_CLASS_EXT=y

这是最弱的一级。

它只证明"编进去了"，不证明"能用"。配置对了但依赖没满足、代码编进去了但运行时初始化失败，都会让你停在这一级。

而且这一级有个陷阱：它和"这个内核支持 sched_ext"不是一回事。发行版可能把符号留着但值改成 n，也可能回移了代码但没回移全。

所以这一级只能当起点，不能当结论。


三、第二级：/sys/kernel/sched_ext 存在

    $ ls /sys/kernel/sched_ext/
    bypass  enable_seq  nr_rejected  root  state

比第一级强。sysfs 目录是内核在初始化时真的注册出来的，不是编译期产物。

但它还是不够。目录存在只说明 sched_ext 这个子系统起来了，不说明有任何调度器在使用它。

刚启动的系统，这个目录存在，state 是 disabled，root/ops 是空的。这是完全正常的健康状态。


四、第三级：root/ops 非空

    $ cat /sys/kernel/sched_ext/root/ops
    minimal

到这一级，才有实质意义。

root/ops 里的名字来自 BPF 程序里 SCX_OPS_DEFINE 的 .name 字段。它非空，说明有一个 BPF 调度器注册成功并且被内核接受了。

这是"接管"的边界。从这一刻起，任务切换走的是你的代码，不是 CFS。

但还有一层没证明：内核在调用你的回调，还是挂上去就晾着？


五、第四级：dmesg 亲口说

    $ dmesg | grep sched_ext
    sched_ext: BPF scheduler "minimal" enabled
    sched_ext: BPF scheduler "minimal" disabled (unregistered from user space)

内核自己在日志里写下了这两行。这比读 sysfs 更强，因为它是事件记录，带了时间和原因。

注意第二行的括号：unregistered from user space。它明确说明是用户态主动注销的，不是崩溃、不是被看门狗踢掉。

如果这行写的是 watchdog，那就是另一回事了——说明调度器卡住了，内核把它强行摘掉。


六、还有第五级，也是最强的一级：计数器

    local=4        shared=1
    local=32       shared=14
    local=43       shared=23
    local=50       shared=34

这四行是程序自己每秒打印的。local 和 shared 是 BPF 程序内部 map 里的计数。

为什么它比前四级都强？因为前面四级证明的是"内核接受了这个调度器"，这一级证明的是"内核正在执行我的代码"。

数字在涨，意味着 enqueue 和 select_cpu 这两个函数真的被调用了，一次一次地。这没法伪造——除非内核在调你的函数，否则 map 里的值不会变。

这也是为什么 minimal.bpf.c 里那个 stats map 不是调试代码。没有它，你只能停在第三级。


七、看门狗：为什么需要它，nr_rejected 是什么

BPF 程序理论上可以死循环。verifier 会尽量证明它不会，但"尽量"不是"一定"——尤其是有状态的循环，证明能力有限。

调度器死循环的后果不是程序卡住，是整机卡住。因为它在 CPU 调度的路径上。

所以 sched_ext 带了一个看门狗。它的工作很简单：观察调度器是否在合理时间内推进。超时就强制摘掉，把 CPU 还给 CFS，机器活下来。

摘掉的次数记在 nr_rejected 里：

    $ cat /sys/kernel/sched_ext/nr_rejected
    0

0 表示从来没被踢过。

这个数字要盯着看。调试期间它一旦不是 0，说明你的调度器有问题，而且问题严重到内核必须介入。这时候不要看性能数据，先看 dmesg 里的 watchdog 记录。

配套的还有 timeout_ms。它是 SCX_OPS_DEFINE 里可以设的字段，默认值给了一个保守的超时窗口。真实调度器调这个值要谨慎——调太小会误杀，调太大等于没有保护。


八、热切换：从 CFS 到 minimal 再回 CFS，全程不重启

这是 sched_ext 最实用的特性，也是最好演示的。

加载前：

    $ cat /sys/kernel/sched_ext/root/ops
    （空）

    $ cat /sys/kernel/sched_ext/state
    disabled

运行 sudo ./minimal ./minimal.bpf.o 之后：

    $ cat /sys/kernel/sched_ext/root/ops
    minimal

    $ cat /sys/kernel/sched_ext/state
    enabled

    $ cat /sys/kernel/sched_ext/enable_seq
    3

enable_seq 是启用序号，每启用一次加一。这里是 3，因为前面调代码时加载过两次。

Ctrl+C 之后：

    $ cat /sys/kernel/sched_ext/root/ops
    （空）

    $ cat /sys/kernel/sched_ext/state
    disabled

CPU 回到 CFS，全程没有重启，没有改 GRUB，没有改任何配置。

这件事的意义不只是"方便调试"。它意味着你可以在生产机器上试一个新调度器，不满意就 Ctrl+C 退出，风险窗口等于你观察的那几分钟。

传统换调度器不是这样的——要改内核、要重启、要停机窗口。


九、那个骗过我的 [ OK ]

现在讲这一篇最该讲的部分。

第一次跑验收脚本，输出是这样的：

    == 4. 加载一个真实调度器 ==
      [WARN] 没找到 scx_simple，跳过实机验证
    == 结论 ==
      [ OK ] sched_ext 验证通过

同一份输出里，第 4 步说"跳过"，结论说"通过"。

这两句话是矛盾的。第 4 步是唯一能证明"真的能接管"的一步，它被跳过了，那结论凭什么是通过？

原因在脚本的写法：RC 变量只在明确的失败分支里置 1，跳过的时候只是打了个 WARN，没动 RC。于是 RC 还是 0，结论就打印了 OK。

这是最坏的一类 bug。它不报错、不崩溃，它给你一个绿色的结果，让你带着一个没验证过的结论往下走。

发现它是因为我不信。看到 WARN 和 OK 挨在一起，第一反应应该是"这两个不可能同时成立"。

修复很直接：

    if ((RC != 0)); then
        err "还有项目没通过，见上面的 [FAIL]"
    elif [[ "${SKIPPED:-0}" == "1" ]]; then
        warn "内核层面通过，但第 4 步被跳过 —— 还没证明调度器真能接管"
        RC=1
    else
        ok "sched_ext 验证通过（已实际加载调度器并接管 CPU）"
    fi

跳过就是失败，退出码必须是 1。

这条规则值得单独记下来：一个验证脚本，只要它跳过了关键步骤，就必须返回失败。否则它会在 CI 里、在别人机器上、在半年后的你自己手里，持续输出一个假的通过。

这个修复在提交 afde5ea 里，和第 2 篇讲的两个真机 bug 放在一起——它们都是同一类问题：脚本在小白的机器上跑，出错时必须说话。


十、想看更细的调度行为，看哪里

四级证据链回答的是"它在不在工作"。要回答"它工作得好不好"，需要另一套工具。

tracepoint 是最直接的：

    $ ls /sys/kernel/tracing/events/sched/
    sched_switch  sched_wakeup  sched_wakeup_new  sched_migrate_task  ...

sched_switch 记录每次任务切换：谁下来、谁上去、在哪个核。你的调度器每做一次决策，这里就有一条记录。

bpftrace 可以按核统计切换次数，看负载是否均衡：

    bpftrace -e 'tracepoint:sched:sched_switch { @[cpu] = count(); }'

runqlat 看的是排队延迟——任务从可运行到真正拿到 CPU 等了多久。这是衡量调度器好坏最直接的指标，比吞吐量敏感得多。

这些工具在第 4 篇那个最小调度器上意义不大，因为它的策略就是 FIFO，延迟分布必然难看。它们是为真实调度器准备的。


十一、到这里，链路走完了

从"内核里没有 sched_ext"，到"自己写一个调度器接管 CPU"，再到"用五级证据证明它真的在工作"。

技术主线到这里结束。

最后一篇换一个角度：怎么把这些东西做成别人能复现的。三段式脚本为什么这么编号、commit message 该写什么、以及推送这件事为什么值得单独写一条提交。


本篇对应提交

这一篇只有一条提交是真正做验证的：b395f23。它同时修了三个只有真跑才会暴露的问题，其中一个是"脚本骗了我"。

一、b395f23：第一次真的把调度器换掉

为什么要有这一条：前面所有检查都只能证明"内核里有 sched_ext"。有和用是两件事。这条提交记录的是第一次真的加载一个 BPF 调度器、并确认它接管了 CPU。

它证明到什么程度，看三条 sysfs：

    uname -r                            -> 6.12.0
    /sys/kernel/sched_ext/root/ops      -> simple
    /sys/kernel/sched_ext/state         -> enabled
    /sys/kernel/sched_ext/nr_rejected   -> 0

root/ops 显示 simple，意思是 scx_simple 这个调度器正在管 CPU 调度，不是"编译进去了"而已。用户态一个包都没换，还是 openEuler 24.03 原样。

顺手修了三个坑，每个都值得单独说。

第一个：验收脚本会跳过唯一有意义的那一步，然后报告通过。

原来的逻辑是：找不到 scx_simple 就 warn 一句"跳过实机验证"，但 RC 保持 0，最后照样打印"验证通过"。也就是说，前三段（配置、sysfs、struct_ops）全过了，第四段——唯一能证明调度器真的接管了 CPU 的那一段——被跳过了，脚本还是绿的。

这是最难发现的一类 bug：它不报错，它给你一个假的安心。

修法是把"跳过"变成一个显式状态，并且在结论里改判：

    if [[ -z "$SCX_BIN" ]]; then
        warn "没找到 scx_simple，跳过实机验证（内核层面已通过，但没证明真能接管）"
        ...
        SKIPPED=1
    fi

    if ((RC != 0)); then
        err "还有项目没通过，见上面的 [FAIL]"
    elif [[ "${SKIPPED:-0}" == "1" ]]; then
        warn "内核层面通过，但第 4 步被跳过 —— 还没证明调度器真能接管"
        RC=1
    else
        ok "sched_ext 验证通过（已实际加载调度器并接管 CPU）"
    fi
    exit "$RC"

注意判断顺序：先判 RC 非 0，再判 SKIPPED。反过来的话，一个既失败又被跳过的场景会显示成"跳过"，把真错误盖掉。

结论那三句话也重写了。通过的时候必须说清通过到什么程度——"已实际加载调度器并接管 CPU"，而不是笼统的"验证通过"。一个报告如果不敢说清自己证明了什么，它就等于什么都没证明。

第二个：官方仓库里已经没有 scx_simple 了。

原来脚本提示去 clone sched-ext/scx 然后 meson 编译。实际上游已经把 scheds/c 删掉、全部改成 Rust，scx_simple 在那个仓库里不存在了。照着提示做，会卡在"编不出来"。

正确来源是内核源码树自带的示例：

    cd ~/src/linux-$(uname -r | cut -d. -f1-2)/tools/sched_ext && make
    sudo ./build/bin/scx_simple &

纯 C，不需要 rust。脚本里也把搜索路径改成先找这个位置，并且支持外部指定：

    SCX_BIN="${SCX_BIN:-$(command -v scx_simple || true)}"

${SCX_BIN:-...} 的意思是"外部给了就用外部的，没给才自己找"。别人在自己机器上已经编好了，可以直接指定，不用改脚本。

第三个：装了新内核，重启还是进老的。

grub2-mkconfig 只重写菜单，不改变默认项。openEuler 的 GRUB_DEFAULT=saved，真正的默认项存在 grubenv 的 saved_entry 里，mkconfig 不会动它。所以菜单里明明有新内核，重启还是进 6.6。

修法是显式设一次：

    grubby --set-default /boot/vmlinuz-<新版本>

顺便记住一件事：grubby --info=ALL 里 index=0 指的是菜单顺序，不是默认项。用那个判断默认内核，会得出错误结论。

    https://github.com/qhc0609/openeuler-sched-ext/commit/b395f23
