怎么把它做成别人能复现的东西

—— 三段式脚本、提交怎么写，以及为什么推送失败占了六条提交（第 6/6 篇）


一、技术走通了，不等于别人能走通

前五篇讲的是一条我自己走通的路径。走通和可复现之间隔着一段距离。

差距在三个地方：命令的顺序（我脑子里有，别人没有）、出错时怎么办（我知道该看哪里，别人不知道）、以及为什么这么写（我当时的判断依据，代码里看不到）。

这三件事分别对应脚本、提交说明、和文档。


二、三段式脚本：编号就是顺序

scripts/ 下三个文件：

    00-preflight.sh      装内核之前跑，判断要不要编
    10-build-kernel.sh   编内核并安装
    20-verify.sh         装完重启后跑，判断到底成没成

编号不是装饰，是执行顺序，也是"跑错了会怎样"的提示。

00 在装内核之前跑，所以它绝对不能改系统。它只读：读 /etc/os-release、读 uname -r、读 /boot/config、读 /sys/kernel/sched_ext、查工具链版本。全部只读，跑一百遍也没有副作用。

这一点很重要。基线校验脚本如果会改系统，那它就不能在"我还不确定要不要动这台机器"的时候跑，它的价值就没了。

10 是唯一会改系统的。它编内核、装到 /boot、改 GRUB、重建 initramfs。所以它必须能回退——这也是为什么第 2 篇强调快照要在装之前打。

20 在重启之后跑，只读加一次短暂加载。它加载调度器 10 秒、观察、然后杀掉，不改任何持久配置。

三段的分界线是"是否改系统"，不是"逻辑是否相关"。按这个分，每段的失败后果是清楚的。


三、退出码要能当判据用

00 的退出码有三种含义：

    0  基线正确，sched_ext 可用，不用编
    1  基线正确，但 sched_ext 不可用，需要编内核
    其他  环境有问题（不是 openEuler、工具链缺失等）

第 2 篇贴过那段输出，结尾是 [exit=1]。这是设计预期，不是故障。

为什么要把"需要编内核"和"环境有问题"分开？因为它们的下一步完全不同。前者是正常流程，后者要先修环境。

如果两者都返回 1，调用方就没法区分"继续下一步"和"停下来看看"。


四、commit message：写现象，不写动作

同样一条提交，说明有两种写法，效果差得很远。

一种是写动作：「添加预检查脚本」「修复配置问题」。半年后看这条提交，只知道加了什么，不知道为什么加、解决什么问题、当时看到了什么。

另一种写四段：现象、判据、结论、未解疑点。

拿 afde5ea 举例，它修了两个真机才暴露的 bug。说明里写的是：第一个是 10-build-kernel.sh 在 cd 进内核源码树之后才解析 BASH_SOURCE，相对路径被算错，配置片段被找成 linux-6.12/configs/sched-ext.fragment，报「找不到配置片段」。第二个是 00-preflight.sh 只匹配 ^CONFIG_X=，关闭的选项写成 # CONFIG_X is not set 抓不到，于是「代码不在」和「代码在但关着」两种状态都被报成「没找到」。

现象写清楚，判据写清楚，别人才能判断"我遇到的和他遇到的是不是同一个"。

还有一条：承认判断错误要写进去。89dedef 那条提交就是在纠正我自己之前的结论——我先写了"26.09 的 6.6 树里没有 sched_ext"，实际去查源码树发现有 kernel/sched/ext.c，只是 defconfig 里关了。这条更正是单独一条提交，没有偷偷改掉。

错误留在历史里比抹掉有价值。别人踩到同一个坑时，能看到"这里有人也想错了，错在哪"。


五、GitHub 上看提交原委的六种视角

单条提交是最核心的，上半是"为什么"（说明），下半是"改了什么"（diff）：

    https://github.com/qhc0609/openeuler-sched-ext/commit/3dc833c

其余五种，按"我想知道什么"来选：

想知道整体脉络 → /commits/main，按时间倒序列出全部提交

想知道两条提交之间累积改了什么 → /compare/89dedef..b395f23

想知道某个文件的演变 → /commits/main/scripts/10-build-kernel.sh

想知道某一行是谁、为什么写的 → /blame/main/push.ps1

想知道机器验证过没有 → /actions，每次 push 触发的 CI 结果

想拿补丁原文（可以 git am 应用）→ commit URL 后面加 .patch 或 .diff

对应到本地，等价命令是 git log --oneline、git show、git log -p -- <file>、git blame。


六、然后是推送。这件事占了六条提交

从技术主线上看，推送和 sched_ext 没有任何关系。但它占了 15 条提交里的 6 条，而且最后一条还是个新工具。

原因很简单：我给这个仓库的定位是"一键复现"，那"一键发布"就必须真的能一键。如果每次改完都要手动折腾半小时才能推上去，这个定位就是假的。

这六条提交的过程值得完整讲，因为它是一次典型的"错误归因 → 逐层排除 → 找到真因 → 换路绕开"。

第一条 fedae1a：让脚本自己找 git 和 gh。现象是"命令找不到"，原因是装完没重开终端，PATH 没刷新。修法是探测常见安装位置，找到就临时加进 PATH。

第二条 ff0af55：告诉用户到底哪个主机不通。现象是报 502 和超时，但浏览器能打开 GitHub。测了一圈发现：

    api.github.com          200 / 0.35s
    codeload.github.com     301 / 0.64s
    github.com              超时
    raw.githubusercontent.com  超时
    ssh.github.com:443      被阻断

关键结论：git push 只走 github.com，gh 走 api.github.com。这两个是不同命运。所以"网络是通的"这句话没有意义，得问"哪个主机通"。

顺带加了 -Watch 模式，30 秒一轮挂机重试。后来证明这个间隔是对的——成功那次是在第 4 轮，中断窗口大约 2 分钟。

第三条 8b98ce1：脚本说了谎，修掉它。这条最值得讲，下面单独说。

第四条 d85ce44：把上面这些写进 README 的 FAQ。排障经验不写下来，下次还得重新查一遍。

第五条 3f13880：判断"到底推上去没有"的方法错了。现象是 push 明明成功，紧接着 git ls-remote 却说远端和本地不一致，连试三次都一样。换 gh api 查同一个 ref，返回的 sha 和本地完全相同。

结论：github.com 抖动期间，ls-remote 不可信，api.github.com 可信。于是把判断依据换掉，ls-remote 降级成备用。

第六条 93c2ccd：换路。这一条单独说。


七、脚本说了谎：8b98ce1

push.ps1 里有个 -ClearEnv 参数，作用是清掉 http_proxy / https_proxy，试一次直连。

写的时候很自然：

    foreach ($k in $ClearEnv) {
        [Environment]::SetEnvironmentVariable($k, $null)
    }

删完就开始直连，失败就报"直连失败"。

问题是：这个环境里的代理是外部强制注入的，删不掉。

我是在某次调试时顺手加了一行读回来验证，才发现：

    [Environment]::SetEnvironmentVariable('http_proxy', $null)
    [Environment]::GetEnvironmentVariable('http_proxy')
    → http://127.0.0.1:50083

值还在。Remove-Item Env:\http_proxy 也一样，删完立刻读回来，值还在。

这意味着之前所有标着"直连"的尝试，实际上都走了代理。脚本在说谎——它报的错误是"直连失败"，但根本没有发生直连。

修法不是想办法把变量删掉（做不到），是承认它删不掉：

    if ([Environment]::GetEnvironmentVariable($ClearEnv[0])) {
        $script:DirectBlocked = $true
    }

检测到删不掉，就置位，后续跳过直连路径，输出里明确说"代理无法清除，直连不可用"。

这条提交的标题是 "stop pretending a direct attempt happened when the proxy cannot be cleared"。用 pretending 这个词是刻意的。

工具骗人比工具报错危险得多。报错你会去查，骗你你会相信。


八、换路：93c2ccd，用 Git Data API 推送

github.com 不通的时候，除了等，还有一条路。

一个 push 的本质只有三件事：传对象、建提交、挪 ref。这三件事 Git Data API 全都能做，而它挂在 api.github.com 上。

所以 push-via-api.py 做的事是：

    1. 对每个改动文件 POST /git/blobs，比对本地 blob 哈希
    2. POST /git/trees（带 base_tree），比对 tree 哈希
    3. POST /git/commits，原样填回 tree / parent / author / committer / message
    4. PATCH /git/refs/heads/main 挪分支

第 3 步是关键。提交对象的哈希，就是 tree + parent + author + committer + message 的哈希。只要这些字段逐字节一致，重建出来的 commit 哈希和本地完全相同。

实测结果：

    commit
      local  3dc833cea28674052adad5a15453b22f6ca8b3b0
      remote 3dc833cea28674052adad5a15453b22f6ca8b3b0
      match - byte-identical commit object

这不是"另建一个提交糊弄过去"，是同一个对象换了一条路上来。

任何一步哈希对不上，脚本就停在原地不动 ref。宁可失败，也不留一个"看起来推上去了"的分叉历史。

唯一的坑是日期格式：git 内部存 <epoch> <+-HHMM>，API 只收 ISO 8601。第一次跑就报：

    gh: Invalid request.
    1792921135 +0800 is not a valid date-time. (HTTP 422)

两者表示同一时刻，转一下就行，GitHub 会再规范化回 git 格式，哈希不受影响。

最有意思的是：93c2ccd 这条提交，是用 93c2ccd 自己推上去的。


九、CI 让"验证过"变成可查的

每次 push 触发一次 CI：shellcheck 检查所有脚本，然后在 openEuler 24.03 容器里跑一遍冒烟。

它不是万能的——容器里没有 sched_ext，跑不了真正的调度验证。但它能拦住两类问题：脚本语法错误、以及基础路径失效。

对读者来说，CI 的意义是"这条提交的脚本至少能跑"。绿色的勾比我的文字更可信。

2b832f8 那条提交是修 CI 的：把 runner 钉到 ubuntu-24.04，checkout 升到 v7。原因是 GitHub 逐步下架旧 runner 镜像，不钉版本的话某天会突然全红。


十、最后一件事：文档要写"为什么不行"

README 里我花了很大篇幅写"为什么不能靠 WSL""为什么 24.03 原版不行""为什么 26.09 的 6.6 树有代码却用不了"。

这些是负结果。负结果通常不写，因为"我试了，不行"看起来没有产出。

但对读者来说，负结果比正结果有用。正结果告诉他一条能走的路，负结果帮他省掉三条走不通的路。

这套东西的价值不在于我走通了，而在于别人能少走我走过的弯路。


本篇对应提交

这一篇有八条提交，其中六条是推送相关。一个"推送"为什么能占六条，下面按顺序说清楚。

一、45604d6：让脚本别把 stderr 当成崩溃

先说这条，因为它的提交说明正好是个反面例子：只有一行 chore: bootstrap...，正文是空的。这是脚本自动生成的默认消息，只说了「初始化」，没说初始化了什么、为什么现在做。

它要解决的问题是：PowerShell 5.1 把原生命令的 stderr 当成终止错误，脚本会当场中断。

所以所有 git/gh 调用都被包进一个函数：

    function Invoke-Native {
        param([string]$Exe, [string[]]$ArgList)
        $prev = $ErrorActionPreference
        $ErrorActionPreference = 'Continue'
        try {
            $out = & $Exe @ArgList 2>&1
            $code = $LASTEXITCODE
        } catch {
            $out = @($_.Exception.Message)
            $code = 1
        } finally {
            $ErrorActionPreference = $prev
        }
        return [pscustomobject]@{ Output = $out; Code = $code }
    }

逐行看。先把 ErrorActionPreference 改成 Continue，让"错误"变成"输出"而不是"终止"。2>&1 把 stderr 并进 stdout，否则报错信息抓不到。$LASTEXITCODE 是原生命令的真实退出码，PowerShell 自己的 $? 在这里不可靠。finally 里恢复原设置，避免污染调用方。

返回一个对象而不是直接输出文本，是因为调用方要同时拿到输出和退出码，分两次返回在 PowerShell 里很容易串味。

自动化提交省事，但默认消息会盖掉你本来想写的内容。提交完花三秒看一眼 git log -1，比事后猜便宜得多。

    https://github.com/qhc0609/openeuler-sched-ext/commit/45604d6

二、2b832f8：把 CI 钉死在一个版本上

ubuntu-latest 会随时间漂移，今天能过不代表明天能过。改成 ubuntu-24.04，checkout 从 v4 升到 v7，两个 job 各改一处，4 行。

为什么值得单独提交：CI 的基线变了，出问题时要能一眼看出是哪次改动导致行为变化。混在功能提交里就查不出来了。

    https://github.com/qhc0609/openeuler-sched-ext/commit/2b832f8

三、fedae1a：双击脚本失败的两个原因

这条解决"一键推送跑不起来"。两个独立原因。

一是 git.exe 和 gh.exe 装了但不在 PATH 上。Get-Command git 返回空，脚本第一行就退出。修法是主动去常见位置找：

    function Add-ToolToPath {
        param([string]$Name, [string[]]$Candidates)
        if (Get-Command $Name -ErrorAction SilentlyContinue) { return $true }
        foreach ($c in $Candidates) {
            if (Test-Path $c) {
                $dir = Split-Path -Parent $c
                $env:PATH = "$dir;$env:PATH"
                return $true
            }
        }
        return $false
    }

逐行看。第一行先看 PATH 里有没有，有就直接返回——重复加会让 PATH 越来越长。foreach 里 Test-Path 检查的是文件本身，不是目录。最后把目录前插到 $env:PATH，只改当前会话，不动系统环境变量——脚本不该悄悄改用户的机器。

二是推送只有一条路，没有重试。实测同一时刻：git 直连 20.205.243.166:443 超时 21 秒，curl 同一个 IP 0.36 秒返回 200。说明出口是按进程过滤的，git 只能走本地代理，而代理会间歇性回 502。

这条提交加了重试和线性退避。

    https://github.com/qhc0609/openeuler-sched-ext/commit/fedae1a

四、ff0af55：分清是哪个域名挂了

上一条只能告诉你"失败了"。这一条把失败拆开：

    api.github.com:443        200 in 0.35s
    codeload.github.com:443   301 in 0.64s
    github.com:443            timeout
    raw.githubusercontent.com timeout

git push 只跟 github.com 说话，所以它必挂；gh 走 api.github.com，所以它一直是好的。以前所有失败都长得像"网络问题"，这个区别看不见。

Show-NetworkVerdict 用裸 TCP 各探 6 秒，把结论分成三种：github-blocked（只是这个域名不通）、offline（全都不通）、reachable（都通）。下次失败时不用重新诊断。

同时加了 -Watch 参数，每 30 秒试一轮，成功即退出。

    https://github.com/qhc0609/openeuler-sched-ext/commit/ff0af55

五、8b98ce1：脚本在说谎

这条最短，15 行，但最值得看。

之前的脚本会"清空代理变量然后直连"。实测发现，两种写法都删不掉：

    [Environment]::SetEnvironmentVariable('http_proxy', $null)
    Remove-Item Env:\http_proxy

删完立刻读回来，值还在。环境是受管的，会强制重新注入，子进程全部继承。所以之前那些标着"直连"的尝试，从来没有真的直连过——它们走的是同一个代理，报的是同一个 502，而日志写着另一回事。

修法是删完读回来验证：

    if ($ClearEnv) {
        foreach ($k in $ClearEnv) { [Environment]::SetEnvironmentVariable($k, $null) }
        # 有些受管环境会强制注入代理，SetEnvironmentVariable(null) 删不掉。
        # 实测过：删完读回来值还在。这时"直连"是假的，必须承认。
        if ([Environment]::GetEnvironmentVariable($ClearEnv[0])) {
            $script:DirectBlocked = $true
        }
    }

读回来还在，就把 DirectBlocked 置真。后面的 Push-Robust 直接跳过直连那条路——不再假装试过，也省掉每次 21 秒的白等。

这条提交的价值不在代码，在态度：脚本不能报告一件没发生的事。

    https://github.com/qhc0609/openeuler-sched-ext/commit/8b98ce1

22 行，纯文档。记下端点对比表、-Watch 用法、PATH 自动发现，目的是下次再遇到不用从头诊断一遍。

这类提交最容易被跳过，但它决定同一个问题你会踩第二次还是第三次。

七、3f13880：验证也得换条路

推送成功了，脚本却报"远端和本地不一致"。原因是它用 git ls-remote 验证，而 ls-remote 走 github.com——同一台正在抽风的机器。

实测现场：连续三次 ls-remote 失败，而 gh api 返回的 sha 和本地 HEAD 一模一样。

修法是换数据源：

    function Get-RemoteHead {
        param([string]$Full, [string]$Branch = 'main')
        for ($i = 1; $i -le 3; $i++) {
            $r = Invoke-Native 'gh' @('api', "repos/$Full/git/refs/heads/$Branch", '--jq', '.object.sha')
            if ($r.Code -eq 0) { return $sha }
            if ($i -lt 3) { Start-Sleep -Seconds (2 * $i) }
        }
        return $null
    }

读的是 refs/heads/main 这个引用本身，不是 ls-remote 的列表输出。三次退避，间隔 2 秒、4 秒。

顺带改了一个更根本的地方：推送前先问远端在哪，如果远端已经是本地 HEAD 就直接停下，不再对着一个连不上的域名白重试。

    https://github.com/qhc0609/openeuler-sched-ext/commit/3f13880

八、93c2ccd：换一条完全不同的路

最后一条。既然 github.com 不通而 api.github.com 通，那就别走 git push 了。

一个 push 的本质只有三件事：传对象、建提交、挪 ref。这三件事 Git Data API 全都有，而它挂在 api.github.com 上。

push-via-api.py 按这个顺序做，每一步都拿本地哈希比对：

    1. POST  /git/blobs            逐文件上传，比对本地 blob sha，不一致立即退出
    2. POST  /git/trees            带 base_tree，比对 tree sha
    3. POST  /git/commits          原样填 tree/parent/author/committer/message
    4. PATCH /git/refs/heads/main  挪分支

关键是第三步。commit 哈希就是 tree + parent + author + committer + message 的哈希，字段原样填回去，重建出来的对象和本地那个逐字节相同，所以 sha 也一样。

这不是另建一个提交糊弄过去，是同一个对象换了条路运上去。任何一步哈希对不上，脚本就停在原地不动 ref。

踩到的坑：git 存的时间是 epoch 加时区，API 只收 ISO 8601，直接传会 422。转成 ISO 之后 GitHub 会规范化回 git 格式，哈希不受影响。

    https://github.com/qhc0609/openeuler-sched-ext/commit/93c2ccd
