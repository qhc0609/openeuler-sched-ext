三条现成的路，都只解决一半

—— nice、chrt、cgroup，各自卡在哪儿（AI 推理优先级 · 第 2/6 篇）

上一篇量出来四个数：调度延迟 p50 1499 微秒、p90 24287、25.6% 的请求超过 5 毫秒、四十毫秒的活干了一百零二毫秒。

最后那个数说明引擎只拿到 39% 的一个核。

先别急着写代码。内核里有现成的手段，能一条命令解决的，不值得花两天。

但这一篇的重点不是"哪条路能让引擎变快"——大概率都能。重点是**变快之后，单次占核涨到了多少**。上一辑只看前一个数，所以结论是 `nice` 就够了；这一辑多看了后一个数，结论就变了。


一、路一：调权重，`nice -n -20`

命令只有一条：

    nice -n -20 ./tiny_infer --requests 120 --interval-ms 150 --passes 1300 ...

`nice` 的值从 -20 到 19，数字越小优先级越高。它改的不是"能不能抢占"，而是一个权重：

    nice 值   权重
      -20    88761
      -10     9548
        0     1024
       10      110
       19       15

nice 0 的权重是 1024，nice -20 是 88761，差 86.7 倍。内核拿这个权重算每个任务"应该分到多少 CPU"：八个批处理线程权重各 1024，加起来 8192；引擎 88761。总权重 96953，引擎占 91.5%。

四核的话，91.5% 就是 3.66 个核。引擎是单线程，最多用一个核，所以它想跑的时候基本随时有份。

实测：

    调度延迟 p50     626 微秒      （CFS 是 1499）
    调度延迟 p90    5684 微秒      （CFS 是 24287）
    计算耗时 p50   44569 微秒      （CFS 是 102133）
    单次占核 p50   21382 微秒      （CFS 是 2990）
    单次占核 p90   46598 微秒      （CFS 是 3988）
    占核超 5 毫秒    608/998 = 60.9%（CFS 是 8.2%）
    旁观 p50         593 微秒      （CFS 是 598）
    批处理吞吐       100%

前三行是好消息：延迟降到三分之一，算力从 39% 一个核回到接近一整个核。

后三行是坏消息：**单次占核从 3 毫秒涨到 21 毫秒，p90 是 47 毫秒。**

为什么？因为权重同时管两件事。

**第一件，份额。** 权重决定长期分配比例，这个上面算过了。

**第二件，时间片。** CFS 的时间片是按权重缩放的。权重越大，分到的时间片越长——内核的逻辑是"你份额大，那一次多跑一会儿，减少切换次数"。

所以 `nice -n -20` 拿到的不只是"分得多"，还有"一次占得久"。这两件事在内核里是同一个旋钮，拧一个，两个一起动。

这就撞上了第二条判据：单次占核 90% 要在 5 毫秒以内。实测 p90 是 47 毫秒，超了九倍。

换句话说：**引擎变快了，代价是运维敲 `ls` 要等四十七毫秒。**


二、路二：换调度类，`chrt -f 50`

    chrt -f 50 ./tiny_infer --requests 120 --interval-ms 150 --passes 1300 ...

`-f` 是 SCHED_FIFO，实时调度类，优先级 50。它和 CFS 不是一个体系：实时类的任务永远排在 CFS 任务前面，只要它可运行，CFS 任务就得让。

而且 SCHED_FIFO **没有时间片**。同优先级的 FIFO 任务之间，先跑的那个一直跑，直到它自己阻塞或者被更高优先级的任务抢占。

实测：

    调度延迟 p50     558 微秒
    调度延迟 p90    5714 微秒
    计算耗时 p50   43813 微秒
    单次占核 p50   43599 微秒      ← 四十毫秒，就是整个请求
    单次占核 p90   52274 微秒
    占核超 5 毫秒    512/518 = 98.8%
    旁观 p50         597 微秒
    批处理吞吐        99%

延迟和 `nice` 差不多（558 对 626），算力也一样。

但占核是 43 毫秒——比 `nice` 还差一倍。因为实时类压根没有时间片这个概念：引擎一旦跑起来，就要把这四十毫秒算完才肯放手。

`98.8%` 这个数要解释一下：不是"98.8% 的请求占核超过 5 毫秒"，是"98.8% 的连续占核片段超过 5 毫秒"。一个请求四十毫秒，中途可能被更高优先级抢占一两次，所以切成几段，每一段都很长。

这个结果说明一件事：**实时类不是"优先级更高"，是"另一种规则"。** 它的规则里没有"让出来"这回事。

比占核更值得注意的是它**没有的东西**：

- 没有上限。如果引擎里有个 bug 死循环，整台机器会卡死。CFS 下死循环只是慢，实时类下死循环是停机。
- 没有范围。`chrt` 改的是整个进程。你没法说"只有处理请求的那个线程用实时类，加载模型的那个线程不用"。

所以 `chrt` 这条路过不了第二条判据，而且过不了的方式比 `nice` 更彻底。


三、路三：cgroup 的权重

很多人第一反应是 cgroup，觉得那是"容器时代的正确答案"。

先说清楚两个文件：

    cpu.max     上限。限制一个 cgroup 最多用多少 CPU
    cpu.weight  下限。按权重分配，1 到 10000

`cpu.max` 是**上限**不是下限：它只会让这个 cgroup 少用，不会让它多用。你要"优先"，它帮不上忙。

`cpu.weight` 有用，但它是 nice 的另一种写法——内核里映射到同一套权重。`cpu.weight 10000` 对应的就是很高的权重，效果和 `nice -n -20` 一样，包括那个副作用：时间片也一起变长。

所以这条路在"占核"这个指标上没有任何改善，只是换了个地方配。

顺带说一句，这一辑的测试机上 `cgroup_disable=files` 是开着的（cgroup v2 没启用），所以连 `cpu.weight` 都没有，只有 v1 的 `cpu.shares`。名字不同，数学一样。


四、比"做不到"更麻烦的：应用根本没权限

上面三条路，都默认你有权限。

真实部署不是这样。推理服务跑在容器里，容器默认没有 `CAP_SYS_NICE`，`RLIMIT_NICE` 是 0。这时候 `nice` 和 `chrt` 会怎样？

在测试机上用 `nobody` 用户、`ulimit -e 0` 复现同样的约束：

    root    nice -n -20   -> nice=-20
    root    chrt -f 50    -> policy=1
    nobody  nice -n -20   -> nice=0   nice: 无法设置优先级: Permission denied
    nobody  chrt -f 50    -> chrt: 设置 pid 0 的策略失败: Operation not permitted

第三行有个陷阱：`nice` **没有失败退出**。它设不上优先级时，照样把命令跑起来，只是优先级没变，退出码还是 0。

所以判断 `nice` 有没有生效，不能看退出码。要看进程自己的 `/proc/<pid>/stat` 第 19 字段——上面那个 `nice=0` 才是实情。

`chrt` 会失败退出，退出码 1。

这两行合起来的意思是：**"用 nice 调一下"这个方案，在容器里连试都试不了。**


五、三条路对照

| | `nice -n -20` | `chrt -f 50` | cgroup 权重 |
|---|---|---|---|
| 调度延迟 p90 ≤ 5 ms | 不过（5684） | 不过（5714） | 同 nice |
| 单次占核 p90 ≤ 5 ms | 不过（46598） | 不过（52274） | 同 nice |
| 旁观 p50 ≤ 1.2 倍 CFS | 过（593） | 过（597） | 同 nice |
| 吞吐 ≥ 95% | 过（100%） | 过（99%） | 同 nice |
| 容器里能不能用 | 不能（EPERM） | 不能（EPERM） | 要 cgroupfs 写权限 |

三条路，没有一条过得了第二条判据。

而且注意一个规律：**前两条判据在现成手段里是互斥的。**

- 想要延迟低，就得把优先级推上去；
- 优先级推上去，时间片跟着变长，占核就压不住；
- 反过来，想让占核短，就得把时间片调小，但时间片在 CFS 里不是你能直接设的参数——它由权重和 `sched_latency` 算出来。

这不是调参没调好，是**这套机制里没有"占多久"这个维度**。CFS 的旋钮只有权重，实时类的旋钮只有优先级，两者都不表达"一次最多跑多久"。


六、那能不能两个都要

把需求写清楚：

    引擎的调度延迟 p90 ≤ 5 毫秒
    引擎的单次占核 p90 ≤ 5 毫秒
    别的任务不受影响
    吞吐不掉

第一条要"快"，第二条要"别霸占"。这两条在现成的三个旋钮上是互斥的。

要做成，需要的是一个**能同时表达"优先"和"限时"的策略**：

- 引擎醒来时，插到队头，并且立刻把正在跑的任务踢下去（这一半 `chrt` 有）；
- 引擎连续跑满一个时间片，就必须让一次，哪怕队列里还有它的活（这一半 `chrt` 没有，`nice` 也没有）；
- 让出去的时候，把机会给刚醒来的普通任务，而不是随便给一个（这一半谁都没有）；
- 这些规则只对引擎生效，别的任务照旧按 CFS 的公平性跑。

四条规则，三条是现成机制里没有的。

内核里能表达"自定义规则"的地方只有一个：**sched_ext**。它允许你把调度策略写成 BPF 程序，挂到内核里跑，替换掉 CFS 的调度逻辑——只替换"挑谁跑"，别的照旧。

代价是：CFS 的公平性你也一起拆掉了，得自己补回来。这是这一辑后半段的全部内容。
