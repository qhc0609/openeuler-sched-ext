自己造一把尺子：一个引擎，一个 trace

—— 把"等多久"和"占多久"都变成能读出来的数（AI 推理优先级 · 第 3/6 篇）

上一篇的结论是：现成的三条路都过不了第二条判据。

在动手写调度器之前，得先有一把能重复量的尺子。不然改完只能说"感觉快了"，说不出快了哪里、代价是什么。

这把尺子有两个部分：

    一个引擎   量"我的请求等了多久、算了多久"
    一个探针   量"它一次占住 CPU 多久"

第二部分是这一辑新加的。第一部分在上一辑写过，这里只挑关键处讲。


一、引擎要满足三个条件

自己写一个"推理引擎"而不是用 PyTorch，不是为了炫技，是为了让测量成立。三个条件：

**第一，结果可重复。** 同一份代码、同一台机器，跑两次得到的分布要一样。框架自己的线程池、动态 batch、内存分配器都会引入抖动，这些抖动和调度无关，但会混进统计。

**第二，只测调度。** 一个请求的时间要拆成"等"和"算"两段，不能只有一个总时间。总时间变快了，你不知道是排队短了还是代码快了。

**第三，够重。** 一次前向只有几微秒的话，一个请求占不满一个时间片，"单次占核"这个量根本测不出来。所以计算量要大到能连续占核几十毫秒。

第三条是这一辑和上一辑最大的区别。上一辑的请求只有 446 微秒，短到根本不存在"占核"问题；这一辑的请求是 40 毫秒，占核变成了主要矛盾。

引擎是两层全连接（128 → 256 → 64），中间 ReLU，权重由固定种子的线性同余生成器算出来，不需要任何模型文件。

量一下：空载 400 次前向 12.2 毫秒、800 次 24.5 毫秒、1430 次 43.9 毫秒，约 30.6 微秒一次。取 1300 次，就是 40 毫秒。


二、三个时刻，两个差值

    long long t0 = now_ns();
    long long interval_ns = (long long)interval_ms * 1000000LL;

    for (int i = 0; i < requests; i++) {
        struct timespec next;
        long long target = t0 + (long long)(i + 1) * interval_ns;

        next.tv_sec = target / 1000000000LL;
        next.tv_nsec = target % 1000000000LL;

        while (clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL) == EINTR)
            ;

        long long t_wake = now_ns();

        for (int k = 0; k < passes; k++)
            forward();

        long long t_done = now_ns();
        long long s = t_wake - target;
        long long w = t_done - t_wake;

        if (s < 0) {
            /* 提前醒来（极少见），钳到 0，但记一笔 */
            early++;
            s = 0;
        }

        sched[n] = s / 1000;
        work[n] = w / 1000;
        n++;
    }

`target` 是计划时刻，`t_wake` 是真正醒来的时刻，`t_done` 是算完的时刻。

    sched = t_wake - target    调度延迟：该跑了，到真的跑了
    work  = t_done - t_wake    计算耗时：真的在算的时间

这两个量必须分开存。只存 `t_done - target` 的话，"排队短了"和"代码快了"会混在一起，最后没法归因。


三、为什么用 `TIMER_ABSTIME`

用"睡 150 毫秒"而不是"睡到 t0 + i×150ms"，是一个容易踩的坑。

如果写成"算完再睡 150 毫秒"，实际周期是：

    150 毫秒 + 计算时间 + 调度误差

四十毫秒的请求，一个周期就变成 190 毫秒以上；跑一百个请求，最后一个的计划时刻和实际差了四秒。统计出来的"调度延迟"里全是自己累积的漂移。

`TIMER_ABSTIME` 每次重新对齐到绝对时刻 `t0 + i×150ms`，误差不累积。代价是：如果某一次算超了，下一个请求的睡眠时间会变短甚至变成 0——这是对的，那才是真实负载。

`while (... == EINTR)` 那个循环也不能省。信号会打断 `clock_nanosleep`，返回值是 `EINTR` 而不是 0，不重试的话这个请求会提前醒来，`sched` 变成负数。


四、两个容易被忽略的细节

**为什么不用 `rand()`。**

    static unsigned int lcg_state = 20261025u;

    static float lcg_next(void)
    {
        lcg_state = lcg_state * 1664525u + 1013904223u;
        /* 取高 16 位映射到 [-1, 1)，低位随机性差，不能用 */
        return ((float)(lcg_state >> 16) / 32768.0f) - 1.0f;
    }

`rand()` 在不同 libc 上序列不同，换台机器权重就不一样，"同一份代码同一个结果"就没了。自己写一个 LCG，参数固定，序列就固定。

取高 16 位而不是低位：LCG 的低位周期短、随机性差，取低位会让权重出现肉眼可见的规律。

**为什么内层循环写成行优先。**

    for (int h = 0; h < HID_DIM; h++) {
        float s = b1[h];
        const float *row = W1[h];

        for (int i = 0; i < IN_DIM; i++)
            s += row[i] * input[i];

        hidden[h] = s > 0.0f ? s : 0.0f;
    }

`W1` 有 32768 个 float，128 KB，超过 L1。内层按行访问，同一行的权重在内存里连续；如果反过来把 `i` 放外层，每次跨 128 个 float 取一个，缓存命中率会掉一半以上。

这一段决定了"四十毫秒"这个数字稳不稳。访存顺序不对，同样的代码可能跑出八十毫秒，而且不同轮次之间还不一样。


五、预热和握手

两个细节，不加就会出错。

**预热。** 前几十次调用会把权重和代码推进缓存，这段开销不属于调度延迟。所以先空跑 50 个请求，不计入统计。预热期间也照常睡，保证进入正式计时时进程状态一致。

**握手。** 引擎启动后不马上开跑，先写 pid 文件，然后等一个"开始"文件出现：

    if (pidfile) {
        FILE *f = fopen(pidfile, "w");

        if (!f) {
            fprintf(stderr, "写不了 %s: %s\n", pidfile, strerror(errno));
            return 1;
        }
        fprintf(f, "%d\n", (int)getpid());
        fclose(f);
    }

    if (waitfile) {
        while (access(waitfile, F_OK) != 0)
            usleep(2000);
    }

因为调度器必须在计时开始之前挂好。如果先跑再挂，前几十个请求是在没有调度器的状态下测的，会被算进统计，把结论稀释掉。

用 `usleep` 轮询而不是 inotify：这里对精度的要求是毫秒级，轮询简单，不会因为事件队列出问题。


六、百分位取整

    static long long pct(long long *v, int n, int p)
    {
        int idx;

        if (n <= 0)
            return 0;
        idx = (int)(((long long)n * p + 99) / 100) - 1;
        if (idx < 0)
            idx = 0;
        if (idx >= n)
            idx = n - 1;
        return v[idx];
    }

`(n * p + 99) / 100` 是向上取整。写成 `n * p / 100` 的话，120 个样本的 p90 会算成第 108 个，而正确答案是第 108 个（向上取整后）。差别在小样本上很明显：5 个样本的 p90，向上取整是第 5 个，向下取整是第 4 个。

`+99` 而不是 `+100`：`(x + 99) / 100` 正好是 `ceil(x / 100)`，写 `+100` 会在整除时多进一位。


七、超时计数：`--sla-us`

引擎还有一个开关：

    --sla-us 5000

它的作用是数"调度延迟超过 5 毫秒的请求有几个"。

为什么要这个数，而不是直接看 p99：120 个样本的 p99 按定义就是"最差的那一个"，一台虚拟机偶尔被宿主机拖住一百多毫秒，p99 立刻变成一百多毫秒，七组数据的排序能被这一个点翻过来。

超时计数对单个噪声点不敏感——一个 200 毫秒的抖动只算一次超时。而且它直接对应判据：90% 要在 5 毫秒以内，等价于超时比例不超过 10%。


八、第二个部分：占核探针

引擎测不了"我占住 CPU 多久"。

它知道自己什么时候在算，但不知道内核什么时候把它换下去。等它重新拿到 CPU 的时候，中间被换下去过几次、每次多久，这些信息它一点都没有。

`/proc/<pid>/schedstat` 也不行。那里只有累计运行时间和累计等待时间，都是加总，没有"这一次跑了多久"。

能拿到这个量的地方只有内核的调度事件。每次任务切换，内核发一个 `sched_switch`，写着谁被换下去、谁被换上来、时间戳多少。

**第一步，设过滤条件。**

    echo "prev_pid == $target || next_pid == $target" \
        > "$TRACE/events/sched/sched_switch/filter"

这里有两个坑。

第一个：只写 `prev_pid == $target` 会漏掉一半。`prev_pid` 是"被换下去"的那一方，引擎被换上来的时候它在 `next_pid` 里。只过滤 `prev_pid`，你只能看到它离开，看不到它进来，配不成对。

第二个：过滤文件不能用 `echo >` 清空。写空字符串会返回 `Invalid argument`，要用 `echo 0 >`。

**第二步，配对。**

    awk -v pid="$pid" '
        /sched_switch:/ {
            ts = ""
            for (i = 1; i <= NF; i++)
                if ($i ~ /^[0-9]+\.[0-9]+:$/) { ts = $i; sub(":", "", ts); break }
            if (ts == "") next
            pv = ""; nx = ""
            for (i = 1; i <= NF; i++) {
                if ($i ~ /^prev_pid=/) { pv = $i; sub("prev_pid=", "", pv) }
                if ($i ~ /^next_pid=/) { nx = $i; sub("next_pid=", "", nx) }
            }
            if (nx == pid) t_in = ts
            if (pv == pid && t_in > 0) {
                d = (ts - t_in) * 1000000
                if (d >= 0) print int(d)
                t_in = 0
            }
        }
    ' "$TRACE/trace" >"$out"

逐段说：

`for (i = 1; i <= NF; i++) if ($i ~ /^[0-9]+\.[0-9]+:$/)` 是找时间戳。trace 每行长这样：

    loadgen-32269   [000] d.... 32817.094758: sched_switch: prev_comm=loadgen ...

时间戳是 `32817.094758:`，以冒号结尾。前面还有 `[000]`（CPU 号）和 `d....`（中断标志），都不能误判成时间戳。用"数字.数字.冒号"这个模式匹配，只会有唯一一个。

`if (nx == pid) t_in = ts` 是记录"被换上来"的时刻。`if (pv == pid && t_in > 0)` 是遇到"被换下去"时结算。`t_in = 0` 那一行是防止重复结算——如果不归零，同一个 `t_in` 会被后面所有的 `prev_pid` 行重复使用。

`d >= 0` 是防脏数据：trace 缓冲区溢出时会丢事件，可能先看到"换下去"再看到"换上来"，算出来是负数。这种样本直接丢掉，不参与统计。

**第三步，取分位数。**

    N=$(wc -l < "$DUR")
    if [ "$N" -eq 0 ]; then echo "$LABEL 没有采到样本"; exit 1; fi
    pick() { sort -n "$DUR" | sed -n "$1p"; }
    printf '%-8s 样本 %-5s p50 %-6s p90 %-6s p99 %-6s max %s\n' "$LABEL" "$N" \
        "$(pick $((N * 50 / 100 + 1)))" \
        "$(pick $((N * 90 / 100 + 1)))" \
        "$(pick $((N * 99 / 100 + 1)))" \
        "$(pick "$N")"

这里没有用 awk 的 `asort`：那是 gawk 的扩展，换一台只有 mawk 的机器就跑不了。`sort -n` 加 `sed -n` 是 POSIX，到处都有。

十、三个容易测错的点

**第一，trace 只开在引擎身上。** 不加过滤的话，八个压测线程的切换会把缓冲区冲爆，而且解析出来的数据里混着别人的片段。过滤到单个 pid，一轮跑下来只有几千行。

**第二，缓冲区要提前设大。** 默认 1.4 MB，1 毫秒时间片跑 18 秒会产生上万行，不够就丢事件，丢事件就产生负数样本。设到 16 MB。

**第三，`max` 不要拿来排序。** 这台机器是虚拟机，`max` 一列全是十万微秒以上的值，那是宿主机拖的，不是调度器。用 p50 和 p90。
