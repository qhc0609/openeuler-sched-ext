两百多行，把"占多久"变成可调的

—— 四个旋钮，和它们各自管什么（AI 推理优先级 · 第 4/6 篇）

上一篇把尺子造好了：两个 p90，一个量"等多久"，一个量"占多久"。

这一篇写调度器。目标很具体：把占核 p90 从 21 毫秒压到 5 毫秒以内，同时不把调度延迟搞回去。

先说结论：两百多行 BPF，四个旋钮，最后占核 p50 从 21382 微秒降到 1975 微秒，延迟还略微变好。


一、先想清楚要什么

CFS 的调度逻辑是"挑 vruntime 最小的跑"。这个逻辑里没有"这个任务该不该多跑一会儿"这个概念——它只有"谁最欠"。

我们要的是三条规则：

    推理任务入队      → 排到队头，并且让正在跑的那个让位
    推理任务连续跑满   → 必须让一次，哪怕队列里还有它的活
    普通任务刚睡醒    → 插到队头，并且踢一脚

第一条保证"快"，第二条保证"不霸占"，第三条保证"换掉 CFS 之后别人不遭殃"。

第三条最容易被忽略。换掉 CFS 的时候，你拆掉的不只是"谁先跑"，还有它的整套公平性机制——而公平性机制同时承担着保护交互式任务的责任。不补，普通任务就退化。


二、四个旋钮

    struct cfg {
        u32 target_pid;      /* 要优待的进程（0 = 不优待任何人） */
        u32 kick_on_wake;    /* 1 = 推理任务唤醒时打断目标 CPU */
        u32 ai_burst;        /* 推理任务最多连续占几个时间片（0 = 不限） */
        u32 wake_boost;      /* 1 = 普通任务唤醒时插队头并踢核 */
        u64 ai_slice_ns;     /* 推理任务的时间片，纳秒 */
        u64 other_slice_ns;  /* 普通任务的时间片，纳秒 */
    };

六个字段，其中前四个是开关，后两个是时间片。对应命令行：

    --ai-slice-us N    推理任务的时间片（微秒）
    --other-slice-us N 普通任务的时间片
    --burst N          连续占满 N 片必须让一次（0 = 不限）
    --wake-boost 0|1   普通任务唤醒时插队头并踢核

这一辑的最后一组 `scxbw` 用的是：

    --ai-slice-us 1000 --burst 1 --wake-boost 1 --kick 1

1 毫秒时间片，占满 1 片让一次，唤醒插队头并踢核。

另一组 `scx20` 只改了三个数：

    --ai-slice-us 20000 --burst 0 --wake-boost 0 --kick 1

20 毫秒时间片，不限连续片数，唤醒不插队。

这两组的差别就是这一篇要解释的东西。


三、分道：把推理任务放进自己的队列

    if (!is_ai(p, c)) {
        ...
        return;
    }

    stat_inc(ST_AI_ENQ);

    scx_bpf_dispatch(p, AI_DSQ, c->ai_slice_ns, enq_flags);

`is_ai()` 只做一件事：比对 `p->pid` 和 `c->target_pid`。

入队时进的是 `AI_DSQ`，不是 `SCX_DSQ_LOCAL`。区别在于：`SCX_DSQ_LOCAL` 是"某个 CPU 的本地队列"，你得先知道它跑哪个核；`AI_DSQ` 是全局队列，哪个核空了哪个核来取，跨核也能抢。

然后踢一脚：

    if (c->kick_on_wake) {
        scx_bpf_kick_cpu(scx_bpf_task_cpu(p), KICK_PREEMPT);
        stat_inc(ST_KICK);
    }

不踢会怎样？那个核上正在跑一个普通任务，它的时间片是 3 毫秒。推理任务得等这 3 毫秒过完、那个任务自己让出来，才轮得到。

也就是说，"优先级高"只体现在队列排序上，不影响正在跑的人。踢一下 = 让那个核立刻重新调度。

到这里，`scx20` 的全部逻辑就讲完了。它的效果：

    调度延迟 p50    552 微秒      （CFS 是 1499）
    单次占核 p50  20219 微秒      （CFS 是 2990）
    旁观 p50       5796 微秒      （CFS 是 598）

延迟好了，占核坏了，旁观也坏了。

**旁观为什么坏了。** 分道之后，普通任务全进 `SHARED_DSQ`，队列是先进先出，时间片统一 3 毫秒。旁观探针醒来时，前面排着几个正在跑时间片的压测线程，它只能等。

CFS 不会这样：它按 vruntime 排序，刚睡醒的任务欠账最少，天然排在最前面。这个"天然"在我们换成自己的队列之后就没了。


四、让一次：切断"到期就取回"的循环

最直觉的想法是"把时间片调小"。

第一版改成 1 毫秒时间片，结果什么都没变——占核还是 20 毫秒左右。

原因在 `dispatch` 的调用时机。时间片到期时，推理任务被重新入队到 `AI_DSQ`，紧接着内核又调 `dispatch` 挑下一个任务。`dispatch` 一看 `AI_DSQ` 里有人，又把它自己取回来。

**时间片等于白设。** 一个 40 毫秒的请求就这么把核按住 40 毫秒，中间那些"到期—重新入队—又被取回"的循环，一次都没让别人插进来。

要切断这个循环，得让调度器记住"这个任务刚跑过一整片"：

    if (c && c->ai_burst && *used >= c->ai_burst) {
        if (scx_bpf_consume(SHARED_DSQ)) {
            *used = 0;
            stat_inc(ST_OTHER_PICK);
            return;
        }
        /* 普通队列是空的：让也没人接，预算不清零 */
    }
    if (scx_bpf_consume(AI_DSQ)) {
        (*used)++;
        stat_inc(ST_AI_PICK);
        return;
    }
    if (scx_bpf_consume(SHARED_DSQ)) {
        *used = 0;
        stat_inc(ST_OTHER_PICK);
    }

三条规则，顺序不能换：

1. 预算用完了：先取普通队列。取到了就清零预算，回去接着跑。
2. 预算没用完（或者普通队列空）：取 AI 队列，预算加一。
3. 兜底：取普通队列。

`*used` 从哪来？一张 per-CPU 的 map：

    struct {
        __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
        __uint(key_size, sizeof(u32));
        __uint(value_size, sizeof(u32));
        __uint(max_entries, 1);
    } ai_burst SEC(".maps");

`PERCPU_ARRAY` 只放一个元素就够。每个 CPU 查到的都是自己那一份，不用按 cpu 编号做键，也不用原子操作——CPU 之间本来就不会同时改同一个元素。

"普通队列是空的就不清零"这一行有讲究：预算只在"真的把机会让出去了"的时候才重置。否则一个空转的让出会把预算清掉，规则等于没有。


五、唤醒插队头：把 CFS 丢掉的那块补回来

加了"让一次"之后，占核降下来了，但旁观还是慢。

上一辑用同一份代码、同样的参数（1 毫秒时间片 + 让一次，但不带唤醒插队）单独测过这一版：旁观 p50 是 5480 微秒，和 `scx20` 的 5796 基本一样。

因为"让一次"让给的是队头那个任务，而旁观探针根本不在队头。它排在八个压测线程后面。

规则生效了（`other_pick` 在涨），受益的人不是我们想救的那个。

所以要补第三块：

    if (!is_ai(p, c)) {
        u64 fl = enq_flags;
        bool wake = c->wake_boost && (enq_flags & SCX_ENQ_WAKEUP);

        stat_inc(ST_OTHER_ENQ);

        if (wake)
            fl |= SCX_ENQ_HEAD;

        scx_bpf_dispatch(p, SHARED_DSQ, c->other_slice_ns, fl);

        if (wake) {
            scx_bpf_kick_cpu(scx_bpf_task_cpu(p), KICK_PREEMPT);
            stat_inc(ST_WAKE_BOOST);
        }

        return;
    }

两件事：

**`SCX_ENQ_HEAD`。** 刚睡醒的任务插到队头。这是 CFS 的"按欠账排序"的廉价近似——CFS 按 vruntime 精确排序，我们只做"插队头"。不精确，但方向对。

**踢一脚。** 只对 `SCX_ENQ_WAKEUP` 做。被抢占后重新入队的任务不踢，否则一次唤醒会引发一连串抢占，白烧 CPU。

这两件事必须一起做。只插队头不踢核，插进去的任务还得等当前时间片跑完；只踢核不插队头，被踢醒的核去队头一看，排着的还是压测线程。

这一组（`scxbw`）的结果：

    调度延迟 p50    591 微秒
    单次占核 p50   1975 微秒
    旁观 p50        631 微秒

三个数都回来了。


六、加载器的顺序不能乱

    open  →  load  →  写 cfg  →  attach

四步，顺序有讲究。

不能"写 cfg 再 load"：map 的文件描述符要到 load 之后才存在，load 之前你拿不到 map 去写。

不能"attach 之后再写 cfg"：attach 那一刻调度器就开始接管，而 `target_pid` 还是 0，等于有几十毫秒谁都得不到优待。这段时间的请求会混进统计。

load 和 attach 之间那个空档正好用来写配置——内核里还没人在调度，写什么都不影响任何人。


七、挂上之后看什么

三条 sysfs：

    cat /sys/kernel/sched_ext/root/ops      # 应该是 ai_prio
    cat /sys/kernel/sched_ext/state         # 应该是 enabled
    cat /sys/kernel/sched_ext/nr_rejected   # 应该是 0

`root/ops` 显示 `ai_prio`，才说明是我们的调度器在管 CPU，而不是"加载成功了但没生效"。

`nr_rejected` 是被看门狗踢掉的次数。BPF 调度器如果卡住超过超时时间（默认 30 秒），内核会把它踢掉，所有任务回到 CFS。这个数字大于 0，说明你的调度器出过事。

然后看计数器。六个：

    ai_enq     推理任务入队次数
    other_enq  普通任务入队次数
    kick       推理任务唤醒时踢核次数
    ai_pick    dispatch 从 AI 队列取到任务的次数
    other_pick dispatch 从普通队列取到任务的次数
    boost      普通任务唤醒时插队头 + 踢核的次数

分开计数是为了能定位问题：

- `ai_enq` 涨但 `ai_pick` 不涨 → 任务进了优先队列却没被优先取走，`dispatch` 的逻辑有问题。
- `kick` 比 `ai_enq` 少 → 有些入队没走到踢核那条路，可能是 `select_cpu` 里已经直接塞进本地队列了（那条路径不经过 `enqueue`），这是正常的。

调度器挂上之后，`cat /sys/kernel/sched_ext/root/ops` 只能告诉你"它在管"，不能告诉你"它管得对不对"。策略写错的时候，系统不会报错，只会安静地变慢。


八、这一篇的三次翻车

写这一篇的时候，前面两版都是错的，值得记下来。

**第一版：只分道 + 踢核（就是 `scx20`）。** 延迟好了，占核 20 毫秒。原因是时间片设成了 20 毫秒——这个数是我拍的，没算过。四十毫秒的请求，20 毫秒时间片意味着一次就占掉一半。

**第二版：把时间片缩到 1 毫秒。** 占核没变。原因上面说了：到期就重新入队，`dispatch` 立刻又取回来，时间片从来没生效过。`ctxt` 涨了 24%，全是空转。

**第三版：加"让一次"。** 占核降下来了，旁观还是慢。因为让出去的机会给了队头那个压测线程。

**第四版：加"唤醒插队头 + 踢核"。** 三个数都回来了。

四次里只有最后一次是对的，而前三次每一次都"看起来在变好"。这就是为什么上一篇要花一整篇去造尺子——没有尺子，第三版就会被当成成功。


九、代价

三个代价，都得说清楚。

**上下文切换多了。** 1 毫秒时间片，一个 40 毫秒的请求要切成几十段。这一组的 `ctxt` 是 34322，CFS 是 36117——反而更低，因为 CFS 在竞争激烈时本来就在频繁切换。但和 `nice` 的 20053 比，多了七成。

**只认一个 pid。** 多线程的引擎要把每个线程的 tid 都配进去。现在的 `is_ai()` 只比一个数，主线程之外的线程完全不受优待。真实的推理服务几乎都是多线程的。

**普通任务之间没有公平性。** `SHARED_DSQ` 是先进先出，加上"唤醒插队头"之后，长期跑的任务会被不断插队。CFS 用 vruntime 保证的那件事，这里没有。

三处都不是"以后优化"，是"这个实现证明了机制可行，没有证明工程可用"。
