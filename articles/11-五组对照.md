五组对照：谁快，谁霸占，谁两头都要

—— 同一台机器、同一份负载、同一个脚本（AI 推理优先级 · 第 5/6 篇）

前四篇分别讲了场景、三条现成路、尺子、调度器。这一篇把五组放进同一张表。

五组里，后两组是同一份代码，只差三个参数。这样每一列数字都能归因到具体的某一行，而不是"反正我改了之后就变好了"。


一、五组怎么设

| 组 | 手段 | 说明 |
|---|---|---|
| `cfs` | 什么都不做 | 基线 |
| `nice` | `nice -n -20` | CFS 内部权重 87 倍 |
| `fifo` | `chrt -f 50` | 实时类，同一优先级内没有时间片 |
| `scx20` | `ai_prio --ai-slice-us 20000 --burst 0` | 分道 + 踢核，一次占 20 ms |
| `scxbw` | `--ai-slice-us 1000 --burst 1 --wake-boost 1` | 1 ms 片，占满让一次，唤醒插队头并踢核 |

负载：

    4 个 vCPU
    8 个压测线程（2 倍核数），死循环做浮点运算
    引擎每 150 毫秒来一个请求，每个请求 40 毫秒计算量
    旁观探针每 40 毫秒醒一次，每次算 32 微秒
    每轮 120 个引擎请求、400 个探针请求
    重复 3 轮

三个量同时采：

    引擎的调度延迟      引擎自己的体感
    引擎的单次占核      同核上别人的体感
    旁观延迟 + 吞吐      整台机器付出了什么


二、四条判据

    调度延迟 p90 ≤ 5 毫秒     典型请求等多久
    单次占核 p90 ≤ 5 毫秒     别人最多等多久
    旁观 p50 ≤ 1.2 倍 CFS     没把别人拖垮
    吞吐 ≥ 95%                总量没掉

第一条和第二条是这一辑的核心。它们是两个方向：一个要求"快点轮到我"，一个要求"别占着不放"。

现成的机制只能满足一个——上一篇解释过为什么。


三、脚本：一组怎么跑

五步，顺序不能换：

1. 先起压测，睡 0.5 秒。让八个线程真的跑起来、把核占满。
2. 再起旁观探针，带 `--wait`。它已经开始计时，但还没开始跑。
3. 再起引擎，带 `--pidfile` 和 `--wait`。它写出 pid，然后等。
4. 挂调度器（或者 `nice` / `chrt`），等 sysfs 确认挂上；然后打开 trace。
5. 最后 `touch /tmp/ai.go`，探针和引擎同时开跑。

引擎和探针必须同时开始，否则两边的统计窗口错开，比的不是同一段时间。

第 4 步里的 trace 是这个脚本和前几篇最大的不同：

    echo 0 > "$TRACE/tracing_on"
    echo > "$TRACE/trace"
    echo 16384 > "$TRACE/buffer_size_kb"
    echo "prev_pid == $target || next_pid == $target" \
        > "$TRACE/events/sched/sched_switch/filter"
    echo 1 > "$TRACE/events/sched/sched_switch/enable"
    echo 1 > "$TRACE/tracing_on"

顺序有讲究：先关 tracing，再清缓冲，再设 buffer 大小，再设过滤条件，最后开。反过来的话，清缓冲那一下会有一段没过滤的事件进来。

引擎跑完之后：

    echo 0 > "$TRACE/tracing_on"
    echo 0 > "$TRACE/events/sched/sched_switch/enable"
    hold_dump "$target" "/tmp/hold-$name-$r.txt"
    echo 0 > "$TRACE/events/sched/sched_switch/filter"

`hold_dump` 就是上一篇那段 awk。

过滤条件必须用 `echo 0 >` 清，不能用 `echo >`——写空字符串会返回 `Invalid argument`，这是这一篇踩的坑之一。


四、引擎侧：调度延迟（微秒，各轮中位数）

| 组 | p50 | p90 | max | 超过 5 ms |
|---|---|---|---|---|
| `cfs` | 1499 | 24287 | 233122 | 92/360 25.6% |
| `nice` | 626 | 5684 | 133917 | 43/360 11.9% |
| `fifo` | 558 | 5714 | 94767 | 39/360 10.8% |
| `scx20` | 552 | 6788 | 111219 | 56/360 15.6% |
| `scxbw` | 591 | 3295 | 184184 | 43/360 11.9% |

先说 `p50` 那一列：`cfs` 是 1499，其余四组都在 552–626 之间。CFS 慢了将近三倍。

`p90` 那一列才有意思：`scxbw` 是 3295，是唯一低于 5000 的。`nice` 和 `fifo` 都在 5700 上下，`scx20` 是 6788。

为什么 `scxbw` 的 p90 比 `nice` 低？因为 1 毫秒时间片让引擎在 CPU 上被换下去的频率更高，一旦有请求进来，正在跑的人剩下的时间片最多 1 毫秒。而 `nice` 下正在跑的人可能还剩十几毫秒的时间片。

**这就是"占得短"反过来帮了"等得短"。** 两个指标不是纯粹对立的——把时间片压小，两边都会受益；但压小时间片的前提是你能自己设时间片，现成机制里没有这个旋钮。


五、引擎侧：单次连续占核（微秒）

| 组 | p50 | p90 | p99 | max | 超过 5 ms |
|---|---|---|---|---|---|
| `cfs` | 2990 | 3988 | 11060 | 158999 | 571/6988 8.2% |
| `nice` | 21382 | 46598 | 87085 | 228029 | 608/998 60.9% |
| `fifo` | 43599 | 52274 | 95755 | 274464 | 512/518 98.8% |
| `scx20` | 20219 | 22435 | 46934 | 151244 | 1167/1348 86.6% |
| `scxbw` | 1975 | 2131 | 8843 | 188161 | 502/11612 4.3% |

这张表是这一辑的核心。

`cfs` 的 2990 微秒就是 CFS 时间片的量级——一个任务跑 3 毫秒换人。

`nice` 涨到 21382。**权重把时间片一起放大了**，这是 CFS 的设计：份额大就一次多跑一会儿，减少切换。所以 `nice` 的"快"和"霸占"是同一个旋钮的两面。

`fifo` 涨到 43599——四十毫秒的请求整个占住，实时类没有时间片。

`scx20` 是 20219，因为它的时间片就是 20 毫秒。

`scxbw` 是 1975。

注意样本数那一列：`scxbw` 是 11612，`fifo` 只有 518。因为 `scxbw` 把 40 毫秒切成几十段，每段都记一次；`fifo` 一个请求只记一两次。

`超过 5 毫秒` 那一列更直观：`fifo` 是 98.8%，`scx20` 是 86.6%，`nice` 是 60.9%，`cfs` 是 8.2%，`scxbw` 是 4.3%。


六、系统侧：旁观探针（微秒）

| 组 | p50 | p90 | max | 超过 10 ms |
|---|---|---|---|---|
| `cfs` | 598 | 5451 | 246774 | 127/1200 10.6% |
| `nice` | 593 | 4383 | 211040 | 71/1200 5.9% |
| `fifo` | 597 | 4606 | 210330 | 81/1200 6.8% |
| `scx20` | 5796 | 9983 | 147288 | 153/1200 12.8% |
| `scxbw` | 631 | 7205 | 155914 | 92/1200 7.7% |

`scx20` 的 p50 是 5796——差了将近十倍。分道把引擎捞到前面去了，但没限制它占多久，普通任务只能排在它 20 毫秒的时间片后面。

这一列也解释了为什么"分道 + 踢核"这个看起来很合理的方案在真实环境里会出事：它让被优待的任务变快了，代价全写在别人的延迟里。


七、吞吐与算力

| 组 | iters/秒 | 相对 CFS | ctxt | policy | work_p50 |
|---|---|---|---|---|---|
| `cfs` | 220978 | 100% | 36117 | 0 | 102133 |
| `nice` | 222127 | 100% | 20053 | 0 | 44569 |
| `fifo` | 219968 | 99% | 27853 | 1 | 43813 |
| `scx20` | 213269 | 96% | 27283 | 0 | 44141 |
| `scxbw` | 211239 | 95% | 34322 | 0 | 46130 |

**吞吐没掉。** 五组在 211239 到 222127 之间，最大差 5%。引擎每 150 毫秒只占 40 毫秒，也就是一个核的 27%，四核机器上不到 7%。抢这点算力，动不了总量。

**`work_p50` 一列说明算力是否一致。** `cfs` 是 102133，其余四组 43813–46130。CFS 下引擎只拿到约 39% 的一个核，另外四组都拿到了接近一整个核。

这一列比所有延迟数字都重要：它说明 `cfs` 的问题不是"某一次调度慢了"，是"这个进程整体分不到算力"。

**`ctxt` 一列说明代价。** `nice` 是 20053，`scxbw` 是 34322。多出来的切换来自 1 毫秒时间片——一个 40 毫秒的请求要切成几十段。这个成本没有体现在吞吐上，体现在调度器自己的开销上。

`policy` 一列用来确认 `nice` 和 `chrt` 真的生效了：`fifo` 是 1（SCHED_FIFO），其余是 0。`nice` 那一行的 `0` 是 policy，它的 nice 值在另一个文件里，上一篇讲过怎么看。


八、五组放一起

| 组 | 延迟 p90 | 占核 p90 | 旁观 p50 | 吞吐 | 全过 |
|---|---|---|---|---|---|
| `cfs` | 24287 ✗ | 3988 ✓ | 598 ✓ | 100% ✓ | ✗ |
| `nice` | 5684 ✗ | 46598 ✗ | 593 ✓ | 100% ✓ | ✗ |
| `fifo` | 5714 ✗ | 52274 ✗ | 597 ✓ | 99% ✓ | ✗ |
| `scx20` | 6788 ✗ | 22435 ✗ | 5796 ✗ | 96% ✓ | ✗ |
| `scxbw` | 3295 ✓ | 2131 ✓ | 631 ✓ | 95% ✓ | **✓** |

五组里只有 `scxbw` 全过。

把每一组的失败方式读一遍，能看出四种不同的"半对"：

- `cfs`：占核合格，延迟不合格。它是"公平但慢"。
- `nice`：旁观合格，延迟和占核都不合格。它是"快了但霸占"。
- `fifo`：和 `nice` 一样，但占核更糟，因为连时间片都没有。
- `scx20`：延迟勉强，占核和旁观都糟。它是"分了道但没限时"。
- `scxbw`：四个都过。

这四种"半对"正好对应四种设计取向：公平、优先、实时、可编程。前三种都在内核里现成，第四种要自己写。


九、这一组数字是怎么来的

`scx20` 到 `scxbw` 只改了三个参数，可以把变化一格一格读出来。

**时间片 20000 → 1000：** 占核 20219 → 1975，降了十倍。

**`--burst 0` → `--burst 1`：** 这是让时间片真正生效的那一步。没有它，时间片到期只是重新入队，`dispatch` 立刻又取回来，切片等于白设。

**`--wake-boost 0` → `1`：** 旁观 p50 从 5796 降到 631。这一格是整篇文章的重点——前两条规则让引擎变快了，但普通任务还是排在它后面。补上"唤醒插队头 + 踢核"之后，普通任务才回到 CFS 的水平。

也就是说：**前两条规则解决的是"引擎占多久"，第三条解决的是"别人等多久"。两件事。**


十、还有一条数据：应用自己动手

    root    nice -n -20   -> nice=-20
    root    chrt -f 50    -> policy=1
    nobody  nice -n -20   -> nice=0   nice: 无法设置优先级: Permission denied
    nobody  chrt -f 50    -> chrt: 设置 pid 0 的策略失败: Operation not permitted

前两行说明命令本身是对的，后两行说明在非 root 的容器里它们用不了。

`nice` 那一行尤其要注意：它没有失败退出，退出码还是 0，只是优先级没变。判断它有没有生效，要看 `/proc/self/stat` 第 19 字段。
