CPU 如何执行一条机器指令

—— 取指、译码、执行、访存、写回，从两行代码开始拆（第 1/5 篇）


先看这个函数：

    int add(int a, int b)
    {
        return a + b;
    }

调用 `add(3, 4)`，返回 7。

对写代码的人来说，事情到这儿就结束了。但对机器来说，"a 加 b"这句话根本不存在。CPU 不认识加法函数，它只有一张指令表，每条指令做一件很小的事。所以这两行代码必须先被翻译成那张表上的指令，然后一条一条执行。

这一篇就从它开始，一路往下拆。拆完你会知道两件事：一条指令要过几道工序，以及为什么一行 `s += a[i] * b[i]` 在 CPU 上要花四拍而不是一拍。


一、先看编译器把它变成了什么

把上面那个函数存成文件，编译，然后看生成的机器码：

    gcc -O2 -fno-tree-vectorize -o bin/oneline src/oneline.c
    objdump -d --no-show-raw-insn bin/oneline

`objdump` 是反汇编器，把二进制翻回人能读的指令。`--no-show-raw-insn` 是不要左边那串机器码，只留地址和指令，读起来干净。

加一个 `-fno-tree-vectorize`，是因为这篇要看"一条指令"长什么样，先把编译器的自动向量化关掉。不关的话它会把循环改成一条指令算八个数，就看不见最基本的形态了。打开以后变成什么样，第三篇再说。

`add` 那一段出来是这样：

    0000000000401840 <add>:
      401840:	lea    (%rdi,%rsi,1),%eax
      401843:	ret

两条指令。一条 `lea`，一条 `ret`。

先说个意外：**没有 `add`。**

`lea` 是"算有效地址"的指令，本来是给访存算地址用的。`(%rdi,%rsi,1)` 的意思是 rdi + rsi × 1，而 rdi 和 rsi 正是传进来的两个参数。所以编译器用一条算地址的指令，把加法顺手做了。

为什么不直接用 `add`？因为 `add` 会写标志位寄存器（进位、溢出那些），`lea` 不写。少一次写，就少一点开销。这是编译器的小算盘。

这件事本身就说明一个问题：**你写的运算和 CPU 执行的指令不是一一对应的。** 你以为是一次加法，编译器觉得用 `lea` 更划算。后面所有的性能账，都得按机器指令算，不能按源码算。


二、一条指令要过五道工序

不管它是 `lea` 还是 `add`，进了 CPU 之后都要走同样的五道工序。

**一、取指。** CPU 得先知道要执行什么。指令自己也在内存里——`lea (%rdi,%rsi,1),%eax` 这一条占三个字节，就存在 0x401840 这个位置。取指就是按程序计数器指的地址把字节读进来，然后把计数器加上这条指令的长度，指向下一条。

这里有个容易忽略的事：**指令也走缓存。** 一个函数第一次被调用，取指要等内存；之后就在 L1 的指令缓存里。所以"第一次调用慢、后面快"这个现象，不只是数据缓存造成的，取指也一样。

**二、译码。** 取进来的是字节，CPU 不认识。译码器把它拆成"要做什么"：读 rdi、读 rsi、相加、结果放 eax。x86 的指令长度从 1 个字节到 15 个字节不等，所以译码得先判断这条有多长，再决定怎么拆——这也是 x86 前端比 ARM 那种定长指令更费电的原因之一。

**三、执行。** 真正去算。这里有个细节：`lea` 用的是地址生成单元，不是算术逻辑单元。它算的是"基址 + 变址 × 比例"这种形式，这个加法器在访存那一侧。所以 `add` 这个函数严格说连 ALU 都没用上。

**四、访存。** 如果这条指令要读内存或者写内存，在这一步做。`lea` 只算地址、不真去读，`ret` 也不读，所以这两条指令的访存这一关是空的。

这是第一件要记住的事：**五道工序里，访存不是每条指令都走。**

**五、写回。** 结果写进寄存器。`lea` 的结果写进 eax，也就是返回值。然后 `ret` 从栈里取出返回地址，跳回调用者的下一条指令，取指从那里继续。


三、五道工序是并行的

如果一条指令必须走完五道才轮到下一条，那 CPU 一拍只能做五分之一个指令，慢到没法用。

真实的做法跟工厂流水线一样：第一道工序在处理第 1 条的时候，第二道在处理第 0 条，第三道在处理更早的。五条指令同时待在不同的工序上。

于是有了两个完全不同的数：

| | 含义 | 这台机器上的值 |
|---|---|---|
| 延迟 | 后一条指令要等前一条多久才能开始 | 整数加 0.94 拍 |
| 吞吐 | 流水线满了以后，每拍能出来几条 | 每拍 3.82 条 |

同一个加法，两个数差了四倍。**这两个数必须分开，混在一起算，后面所有的账都会错。**

还有一件事要说清楚：一条指令从进到出确实要走四五拍，但**它的结果不用等走完**。结果在执行那一步就出来了，后面两道是访存和写回。所以下一条指令等的是"执行完"，不是"走完全程"。

整数加法从开始执行到结果可用，是 0.94 拍——就是上面表里那个数，接近一拍。


四、加一个循环，指令变成五条

刚才那个函数太简单了：没有循环，不碰内存，连访存那道关都是空的。加一个循环看看：

    long sum_int(const int *a, long n)
    {
        long s = 0;

        for (long i = 0; i < n; i++)
            s += a[i];
        return s;
    }

编译出来：

    0000000000401850 <sum_int>:
      401850:	test   %rsi,%rsi
      401853:	jle    401870 <sum_int+0x20>
      401855:	lea    (%rdi,%rsi,4),%rcx
      401859:	xor    %eax,%eax
      40185b:	nopl   0x0(%rax,%rax,1)
      401860:	movslq (%rdi),%rdx
      401863:	add    $0x4,%rdi
      401867:	add    %rdx,%rax
      40186a:	cmp    %rcx,%rdi
      40186d:	jne    401860 <sum_int+0x10>
      40186f:	ret

五条（不算前面那两条准备工作和后面那句 `ret`）。逐条看。

`test %rsi,%rsi` 加 `jle 401870`：n 小于等于 0 就直接返回。你没写这个判断，是编译器加的。它得防止你传个 0 进来。

`lea (%rdi,%rsi,4),%rcx`：算 a + n × 4，也就是数组末尾的地址。为什么要先算这个？这样循环里就不用每次做 `i < n` 的比较，改成比较指针——指针走到末尾就停。编译器又帮你省了一条指令。

`xor %eax,%eax`：s = 0。用异或清零比 `mov $0` 短，省一个字节。这种细节你写不出来，编译器顺手就做了。

然后是循环体五条：

- `movslq (%rdi),%rdx`：从内存读一个 int，符号扩展到 64 位。**这是第一条真正访存的指令。**
- `add $0x4,%rdi`：指针往后挪 4 个字节，就是 `i++`
- `add %rdx,%rax`：累加，就是 `s +=`
- `cmp %rcx,%rdi`：和末尾地址比一下，就是 `i < n`
- `jne 401860`：不相等就跳回循环开头

`jne` 这一条要特别注意：**它往回跳。** 往回跳意味着取指要从 401860 重新开始取——而 CPU 在取到 `jne` 之前，早就顺着往下取了好几条了。那些白取的指令得扔掉。

怎么少扔一点，是第四篇的事。这里只要记住：**循环的代价不只在循环体里，还在那个跳转上。**


五、再加一次乘法，链就咬住了

把求和换成点积：

    float dot_f32(const float *a, const float *b, long n)
    {
        float s = 0.0f;

        for (long i = 0; i < n; i++)
            s += a[i] * b[i];
        return s;
    }

    0000000000401880 <dot_f32>:
      401880:	test   %rdx,%rdx
      401883:	jle    4018b0 <dot_f32+0x30>
      401885:	xor    %eax,%eax
      401887:	pxor   %xmm1,%xmm1
      40188b:	nopl   0x0(%rax,%rax,1)
      401890:	movss  (%rdi,%rax,4),%xmm0
      401895:	mulss  (%rsi,%rax,4),%xmm0
      40189a:	add    $0x1,%rax
      40189e:	addss  %xmm0,%xmm1
      4018a2:	cmp    %rax,%rdx
      4018a5:	jne    401890 <dot_f32+0x10>
      4018a7:	movaps %xmm1,%xmm0
      4018aa:	ret

跟上面比，循环体从五条变成六条，但内容换了。

`movss (%rdi,%rax,4),%xmm0`：从 a 里读一个 float 进 xmm0。`ss` 是 scalar single，一次一个单精度浮点，不是一批。

`mulss (%rsi,%rax,4),%xmm0`：这一条同时干了三件事——从 b 里读一个 float、和 xmm0 相乘、结果还放回 xmm0。它的第二个操作数直接写成内存地址，所以**它自己就是一次访存**，不需要单独再写一条 load。一行 `a[i] * b[i]`，两个数组各读一次，正好两条指令。

`addss %xmm0,%xmm1`：把乘积加进总和。

现在盯住 `addss` 这一条。它读 xmm1，也写 xmm1。下一轮循环的 `addss` 要读的 xmm1，正是这一轮写进去的那个。

**后一条必须等前一条算完。** 不是"差不多同时"，是硬等。这就是依赖链。

`add $0x1,%rax` 和 `cmp`、`jne` 不在这条链上，它们各算各的，可以提前跑。所以真正被卡住的只有那一条 `addss`。

一条链咬到底，整段循环的速度就由它决定。这是后面所有问题的根源。


六、量一量，这条链到底要等多久

要量"拍"，先得知道一拍有多长。

x86 上有个计数器叫 TSC，`rdtsc` 一条指令就能读出来。很多人直接拿它的差值当周期数。**它不是。**

TSC 走一个固定频率，跟核心实际跑多快没关系。核心睿频的时候比它快，省电的时候比它慢。这台机器上，TSC 是 2.30 GHz，核心实际跑 2.53 GHz，差一成。

差一成不是随机误差，是**朝一个方向的偏差**：拿 TSC 差值当周期数，所有结论都会系统性地偏小一成，而且不会报错。

所以得先标定。办法很朴素：找一条每拍只能走一条的指令，跑很多遍，用墙钟时间反推频率。整数加法就是这样一条。

    static inline double bench_calibrate_ghz(void)
    {
        const uint64_t n = 200000000ull;
        uint64_t ns0, ns1;

        bench_chain_add(n / 10);
        ns0 = bench_ns();
        bench_chain_add(n);
        ns1 = bench_ns();

        return (double)n / (double)(ns1 - ns0);
    }

第一行那个 `n / 10` 是热身：刚上电频率还没稳，先跑一小段让它进入状态，这段不计入。

然后记开始时间，跑 n 次加法，记结束时间。最后一行是全部秘密：**n 拍除以纳秒数。** 一拍等于一纳秒的一千兆分之一，所以"拍每纳秒"就是 GHz。

`bench_chain_add` 里是内联汇编，八条 `addq` 串在同一个寄存器上（`"+r"(x)` 的意思是读进来、算完写回同一个寄存器）。所以第二条读的必须是第一条的结果，第三条读第二条的，一条咬一条。

现在换成浮点加法，同样的依赖链，只是指令从 `addq` 换成 `addss`：

    static void chain_add_float(uint64_t n)
    {
        float x = 1.0f, one = 1.0f;

        for (uint64_t i = 0; i < n; i += 8)
            __asm__ __volatile__(
                "addss %1, %0\n\t" "addss %1, %0\n\t"
                "addss %1, %0\n\t" "addss %1, %0\n\t"
                "addss %1, %0\n\t" "addss %1, %0\n\t"
                "addss %1, %0\n\t" "addss %1, %0"
                : "+x"(x) : "x"(one));

        g_sink_f = x;
    }

一次写八条，是为了让循环本身的开销（`i += 8`、比较、跳转）摊薄。这一点第四节已经踩过一次：八条的时候循环开销占四分之一，量出来的不是指令本身。

跑出来：

| 依赖链 | 拍/条 |
|---|---|
| 整数 add | 0.94 |
| 浮点 addss | 3.90 |
| 浮点 / 整数 | 4.14 倍 |

**同样是加法，整数版一拍出结果，浮点版要四拍。**

原因在硬件。浮点加法要先把两个数的指数对齐——小数点位置不一样，得先挪成一样的；然后尾数相加；最后还要规格化，把结果收拾成标准形式。整数加法没有这些步骤，一条线就走完了。

所以第四篇里那句"每拍一次乘加"错在哪，现在清楚了：**点积里那条 `s +=` 是浮点加法，它四拍才出一次结果。**


七、把 3.74 拍算回去

理论说完了，跑一个真的。

两个两万 float 的数组，共 160 KB，L2 装得下（这颗核的 L2 是 256 KB）。点积算一千遍，总共两千万次乘加：

    === 三、两千万次乘加要多久 ===
    元素个数        20000
    重复次数        1000
    乘加总次数      20000000
    实测耗时        29.6 ms
    每次乘加        3.74 拍
    按每拍一次算    7.9 ms
    相差            3.7 倍

按每拍一次算，两千万拍，2.53 GHz 下是 7.9 毫秒。实测 29.6 毫秒，差 3.7 倍。

3.74 拍——和刚才量出来的浮点加法 3.90 拍基本是同一个数。**这不是巧合：整个循环的速度就是那条 `addss` 链的速度。**

两千万次乘加，每次 3.74 拍，七千五百万拍，2.53 GHz 下是 29.5 毫秒。实测 29.6 毫秒。对上了。

顺便说清楚这台机器的脾气：同一份代码跑八遍，每次乘加在 3.7 到 4.8 拍之间晃，主频标定在 2.1 到 2.7 GHz 之间晃。最差的一次是 5.66 拍，那一次主频标定偏低——不是代码变慢了，是虚拟机被宿主机挤了。所以这里所有的"拍"都只能当量级看，**比值才是可靠的**：浮点加法是整数加法的四倍，这个结论跑多少遍都一样。


八、如果数据不在缓存里

上面那个实验，160 KB 的数据稳稳待在 L2 里。真实的模型没这么客气。

数据在内存里，一次访问要等多少拍？这个数得用另一种办法量：把数组做成一条环，每个位置存下一个位置的序号，然后 `cur = next[cur]` 一步一步走。每一步都要等上一步读出地址，这是纯延迟，没有任何东西可以提前做。

量出来是这样：

| 工作集 | 拍/次访问 |
|---|---|
| 16 KB　L1 | 4.3 |
| 128 KB　L2 | 13.2 |
| 4 MB　L3 | 122.1 |
| 32 MB　内存 | 304.7 |

还是两千万次乘加，但每次都要等一次完整的内存延迟，三百零五拍：

两千万乘以三百零五，六十一亿拍，2.53 GHz 下是 **2.4 秒**。

7.9 毫秒、29.6 毫秒、2.4 秒。同一个 CPU，同一个算法，同一份代码，三个数字差三百倍。

真实的程序不会落到最惨那一头——一个缓存行能装 16 个 float，硬件预取器也会帮你提前搬。但"数据在哪"这一件事，能造成三百倍的差距，这个量级说明了一件事：为什么推理框架里那些看起来很底层的东西——分块、预取、改数据布局、算子融合——值得花力气。

它们干的事只有一件：**把操作数从内存里挪到寄存器里。**


九、小结

回到最开始那个函数。一行 `s += a[i] * b[i]`，编译出来是六条指令，要过五道工序：

| 工序 | 做什么 | 这台机器上的代价 |
|---|---|---|
| 取指 | 把指令字节读进来 | 走缓存，第一次要等内存 |
| 译码 | 拆成 CPU 能懂的动作 | x86 变长指令，比定长贵 |
| 执行 | 真正算 | 整数加 0.94 拍，浮点加 3.90 拍 |
| 访存 | 读或写内存 | L1 4.3 拍，内存 304.7 拍 |
| 写回 | 结果写进寄存器 | 不单独占时间，但下一条要等 |

五道工序里，真正把这段代码卡住的只有两处：**执行那一步的浮点加法（四拍），和访存那一步的取数（如果不在缓存里，三百拍）。**

其余的都在并行地跑，不占时间。
