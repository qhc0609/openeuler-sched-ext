CPU 如何执行一条机器指令

—— 取指、译码、执行、访存、写回，每一步各要几拍（第 1/5 篇）


一台机器上跑着一个推理服务，一次请求要做三千万次乘加。

"三千万次乘加"这句话听着挺快，但它没说清楚一件事：这些乘加在 CPU 里到底花了多长时间，时间又花在哪一步。不知道这个，就没法解释为什么有时候同样的模型、同样的机器，速度能差三倍。

这一篇不讲模型，只讲一条指令。任何一条指令进 CPU，都要走五个步骤：取指、译码、执行、访存、写回。五个步骤里，有的只要一拍，有的要三百拍。

下面的数字全部来自一台真实的机器：4 核、标称 2.5 GHz、openEuler。代码在 `cpu-ai/` 里，原始输出在 `cpu-ai/results/01-stage5.txt`。


一、先看清楚一条指令长什么样

从最热的一段代码看起。这是一个点积的内层循环，反汇编出来是这样：

    401348:  vmovss 0x40e060(%rax),%xmm0      从内存读一个数进寄存器
    401350:  vmulss 0x406060(%rax),%xmm0,%xmm0 和另一个数相乘
    401358:  add    $0x4,%rax                  指针往后挪 4 字节
    40135c:  vaddss %xmm0,%xmm1,%xmm1          累加到总和里
    401360:  cmp    $0x8000,%rax               看看走完了没有
    401366:  jne    401348                     没走完就跳回去

左边是地址，右边是指令。地址每次加 4 或 8，因为一条指令占这么多字节。

这六条指令，正好把五个阶段都用上了：

    取指      jne 要从 401348 重新取，前面的预测也得跟着走
    译码      每条指令拆成 CPU 能执行的动作
    执行      vmulss 和 vaddss 是运算，cmp 也是
    访存      vmovss 从内存读，这是唯一碰内存的一条
    写回      vaddss 把结果写回 xmm1，下一条才能用

注意 `vmovss` 和 `vaddss` 的关系：后者要等前者读完才能算，前者要等上上一条循环的 `vaddss` 写完才能读。**这一串依赖，就是延迟的来源。**


二、五步各要多久

取指和译码没法单独量——你看不见"取指用了多久"，只能看见整条指令花了多久。但它们的结果能间接看出来：**如果能同时喂进去的指令变多了，说明前端变宽了。**

执行和访存能直接量。办法是把后一条指令卡在前一条的结果上，让它没法提前开工，然后计时。

    // 三十二条 add 串在同一个寄存器上，后一条必须等前一条
    __asm__ __volatile__(
        "addq $1, %0\n\t"
        "addq $1, %0\n\t"
        ... 一共 32 条
        : "+r"(x));

`"+r"(x)` 的意思是：x 从寄存器读进来，算完写回同一个寄存器。所以第 2 条 add 读的必须是第 1 条的结果，跑不掉。

n 条这样的 add，就是 n 拍。量出总时间，除一下，就得到每拍多少纳秒。

2.1 先标定这台机器到底跑多快

这里有个坑，先说清楚。

x86 上有个计数器叫 TSC，`rdtsc` 指令就能读。很多人直接拿它当"跑了多少拍"。**它不是。** TSC 走的是一个固定频率，核心在睿频时跑得比它快。

    核心实际频率   2.54 GHz
    TSC 计数器     2.30 GHz

差 10%。直接拿 TSC 差值当周期数，所有结论会系统性偏小一成。

所以要先标定：跑一条已知延迟的指令链（依赖 add，每拍一条），用墙钟时间反推频率。

    g_ghz = bench_calibrate_ghz();

这一步看着多余，但后面每个"拍"都是它换算出来的。标定错了，全篇都错。

2.2 执行阶段：add 一拍，乘法三拍

    依赖 add  链     0.98 拍/条
    依赖 imul 链     2.94 拍/条

加法器是 1 拍，乘法器是 3 拍。差在哪？乘法在硬件里是分几级算出来的，级数多，延迟就长。

这两个数很干净，是因为它们就是硬件的真实延迟，没有别的因素掺进来。

2.3 取指译码阶段：一拍能喂几条

把依赖拆掉——八条 add 分别写进八个不同寄存器，互不相干，再重复四遍：

    uint64_t a = 1, b = 2, c = 3, d = 4, e = 5, f = 6, g = 7, h = 8;

    __asm__ __volatile__(
        "addq $1, %0\n\t"
        "addq $1, %1\n\t"
        ... 一共 32 条，八个寄存器轮着加
        : "+r"(a), "+r"(b), "+r"(c), "+r"(d),
          "+r"(e), "+r"(f), "+r"(g), "+r"(h));

结果：

    8 条独立 add     0.26 拍/条 → 3.82 条/拍

每拍能走 3.82 条。这是前端宽度的天花板：指令要一条条取进来、译码、派发到各个执行单元，这条路不够宽，后面再快也没用。

一台四发射的机器，理论上限是 4。实测 3.82，已经很接近。

2.4 访存阶段：数据放在哪，差两个数量级

访存没法用依赖链直接量，因为访问地址要提前知道。换个办法：把数组做成一条环，每个元素存下一个元素的序号，然后跟着走。

    next[i] = (i + K) & (n - 1)

K 是一个很大的奇数，n 是 2 的幂。两者互素，所以从任意一点出发都能走遍全部元素。K 取得大，相邻两次访问的地址跨得很远——**这是为了让硬件预取器跟不住**。预取器一旦猜到你要读哪，会提前搬进缓存，量出来的延迟就是假的。

跟着这条环走一圈，每一步都得等上一步读出来才知道下一步去哪。这就是纯延迟。

结果：

    工作集        拍/次访问    折合纳秒
    16 KB   L1        4.3         1.7
    128 KB  L2       13.2         5.2
    4 MB    L3      122.1        48.0
    32 MB   内存    304.7       119.8

从 L1 到内存，七十倍。

L3 这一档的 122 拍比一般资料里的 40~50 拍高不少。原因有两个：这是虚拟机，每次访问还要过一层地址转换；而且宿主的缓存被别的负载占着。真实机器上这一档会低一些，但"L1 和内存差两个数量级"这个结论不变。

2.5 写回阶段

写回不单独占时间——结果写进寄存器是一拍之内的事。但下一条要用这个结果的指令必须等它写完，所以它的影响体现在"延迟"里，而不是"吞吐"里。

这就是为什么 2.2 节那个依赖链是 0.98 拍一条：加法本身一拍做完，但下一条要等这一拍结束才能开始。两件事是同一拍。


三、代码是怎么写的

三个关键函数都在 `cpu-ai/common/bench.h` 和 `cpu-ai/src/stage5.c` 里。

标定主频：

    static inline double bench_calibrate_ghz(void)
    {
        const uint64_t n = 200000000ull;
        uint64_t ns0, ns1;

        bench_chain_add(n / 10);
        ns0 = bench_ns();
        bench_chain_add(n);
        ns1 = bench_ns();

        return (double)n / (double)(ns1 - ns0);
    }

第一行那个 `n / 10` 是热身，让频率先稳定下来，不计入时间。

最后一行是全部秘密：n 拍除以纳秒数。因为一拍等于一纳秒的一千兆分之一，所以 拍/纳秒 就是 GHz。

指针追逐：

    static double chase_cycles(uint32_t n)
    {
        const uint32_t k = 2654435761u;    // 0x9E3779B1，奇数
        uint32_t *next = malloc((size_t)n * sizeof(uint32_t));
        ...
        for (i = 0; i < n; i++)
            next[i] = (uint32_t)((i + k) & (uint32_t)(n - 1));

        // 预热：把整条环走一遍
        for (i = 0; i < n; i++)
            idx = next[idx];

        for (int r = 0; r < 3; r++) {
            uint32_t cur = idx;

            ns0 = bench_ns();
            for (i = 0; i < steps; i++)
                cur = next[cur];
            ns1 = bench_ns();
            ...
        }

        g_sink = idx;      // 这一句不能少
        ...
    }

最后那句 `g_sink = idx;` 看起来莫名其妙，其实很关键。`g_sink` 是一个 `volatile` 全局变量。没有它，编译器会发现"这个循环算出来的 idx 没人用"，直接把整个循环删掉——量出来的时间是 0，四个缓存层级全是 0.0 拍。

这类测量里，**"结果没人用"是最常见的假数据来源**，而且它不报错，只是给你一个漂亮的零。


四、三个容易量错的坑

一、把 TSC 当周期数。差 10%，所有绝对值偏小。

二、循环开销混进来。一开始每条 asm 块里只放 8 条 add，量出来是 1.77 条/拍，比理论值 4 低了一半。原因是循环自己的 `add`、`cmp`、`jne` 三条指令占了位置。改成每块 32 条之后，循环开销被摊薄到 1/4，才回到 3.82。

三、让预取器猜到你的访问。指针追逐如果用固定小步长，硬件会提前把数据搬进缓存，量出来 L1 和内存差不多快——因为全都在 L1 里了。

三个坑有一个共同点：**都不报错，都给出一个看起来合理的数。** 微基准的可信度不在于跑得通，而在于知道自己在量什么。


五、这些数字对 AI 有什么用

回到开头那句话：一次请求三千万次乘加。

如果操作数在寄存器里，一次乘加 1 拍。三千万次就是三千万拍，2.54 GHz 下大约 12 毫秒。

如果每次乘加都要从内存读操作数，一次 305 拍，那就是九十一亿拍，三点六秒。

**差了三百倍。同一个 CPU，同一段代码，同一个模型。**

这就是为什么推理框架里那些看着很"底层"的东西——分块、预取、数据布局、算子融合——值得花力气。它们干的事只有一件：把操作数从"内存里"挪到"寄存器里"。

也是为什么"这个模型在这个 CPU 上跑多快"这个问题，光看参数量算不出来。得知道它跑的时候，数据在哪里。
