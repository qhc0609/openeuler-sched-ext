CPU 如何执行一条机器指令

—— 取指、译码、执行、访存、写回，每一步各要几拍（第 1/5 篇）


厂里那台视觉检测设备，一帧图像进来，先算一个相似度：把实时特征向量和模板向量逐项相乘再累加，两千万次乘加。

写这段代码的人算过账。机器标称 2.5 GHz，一拍做一次乘加，两千万次就是两千万拍，八毫秒。够用了。

实测三十毫秒。

八毫秒变三十毫秒，中间那二十二毫秒不是凭空消失的，它花在了一些代码里看不见的地方。一行 `sum += a[i] * b[i]`，在 C 里是一次乘加，在 CPU 里根本不是——它是六条指令、五道关口、好几次等待。

这一篇就把这一行拆到底。拆完你会发现，三十毫秒这个数字是可以算出来的，一分一毫都对得上。


一、一行 C 代码，六条机器指令

那段循环长这样：

    for (int i = 0; i < n; i++)
        s += a[i] * b[i];

人看这句话，看到的是"两个数组逐项相乘再累加"。CPU 看不到这个。CPU 只认识很笨的动作：从某个地址搬一个数进寄存器、把两个寄存器相乘、把某个数加一、比较两个数、跳转到别处。它不知道什么叫"数组"，也不知道什么叫"累加"。

所以编译出来是这样：

    401348:  vmovss 0x40e060(%rax),%xmm0       从内存读一个数进 xmm0
    401350:  vmulss 0x406060(%rax),%xmm0,%xmm0 和另一个数相乘
    401358:  add    $0x4,%rax                  指针往后挪 4 字节
    40135c:  vaddss %xmm0,%xmm1,%xmm1          累加到总和里
    401360:  cmp    $0x8000,%rax               看看走完了没有
    401366:  jne    401348                     没走完就跳回去

一行 C，六条指令。逐条看它们在干什么。

第一条 `vmovss 0x40e060(%rax),%xmm0`：把 `%rax` 指向的那个地址里的一个 float 搬进 `%xmm0` 寄存器。`vmovss` 里的 `ss` 是 scalar single，意思是一次只搬一个单精度浮点数——不是一批。这就是数组取元素 `a[i]` 的真身。

第二条 `vmulss 0x406060(%rax),%xmm0,%xmm0`：把 `%xmm0` 里的数和另一个地址里的数相乘，结果还放回 `%xmm0`。注意它的第二个操作数 `0x406060(%rax)` 是直接写在指令里的内存地址——也就是说，**这一条指令自己也读了一次内存**。它一个人干了"读 b[i]"和"相乘"两件事。这一点后面会用到。

第三条 `add $0x4,%rax`：指针往后挪 4 个字节。一个 float 占 4 个字节，所以挪 4 就是下一个元素。这是 `i++` 的真身。

第四条 `vaddss %xmm0,%xmm1,%xmm1`：把刚算出来的乘积加进 `%xmm1`，也就是那个总和。这是 `s +=` 的真身。

第五条 `cmp $0x8000,%rax`：拿指针和 `0x8000` 比一下。`0x8000` 是 32768，也就是数组有多少个字节。这是 `i < n` 的真身。

第六条 `jne 401348`：如果上一条比较的结果是"不相等"，就跳回 401348 继续循环。

六条指令里，四条是"真正的计算"（取数、乘、加、比较），两条是"让循环转起来"（挪指针、跳回去）。

为什么要费劲看这个？因为后面所有关于"快慢"的讨论，都发生在这六条上面。CPU 不关心你的算法叫什么名字，它只看见六条指令，然后一条一条地喂进去。


二、这六条指令要过五道关

一条指令进 CPU，不是"进去就出来"。它要走五道工序：取指、译码、执行、访存、写回。

取指是从内存里把指令本身读进来——对，指令也要占内存，也在缓存里。译码是把这条指令的字节拆成 CPU 内部能懂的动作，比如"要读哪个寄存器、要算什么、结果写回哪里"。执行是算术逻辑单元真正去算。访存是如果这条指令要读或写内存，在这一步做。写回是把结果写进寄存器。

听起来像流水线，事实上就是流水线。工厂里装一台机器分五道工序，每道工序一分钟，但五台半成品可以同时在五道工序上——所以第一台出来要五分钟，之后每分钟出来一台。

CPU 也是这样。**单条指令从进到出要五拍，但流水线满了以后，每拍能出来一条。**

这两个数字很容易搞混，而搞混的后果很严重。很多人算性能账时默认"一拍一次乘加"，依据就是"每拍能出来一条指令"。但乘法那条指令自己的延迟是三拍、四拍，它出结果要等，等的时候下一条用它的指令只能干看着。

所以"每拍能发几条"和"每条要几拍才出结果"是两个完全不同的数。前者决定吞吐的上限，后者决定一条依赖链能不能跑满。这一篇要把两个都量出来。

取指和译码这两道，没法单独量——你没法在代码里插一根探针，问"刚才取指用了多久"。它们的效果只体现在一件事上：**一拍能同时喂进去几条指令**。这个数能反推出来。

执行和访存这两道能量，而且量得比较干净，办法后面说。


三、量一条指令要几拍

先说一个前提：得知道"一拍"有多长。

x86 上有个计数器叫 TSC，`rdtsc` 指令读一下就能得到一个数。很多人直接拿这个数当"跑了多少拍"。它不是。

TSC 走的是一个固定频率，跟核心实际跑多快没关系。核心在睿频的时候跑得比它快，在省电的时候比它慢。这台机器上：

| | 频率 |
|---|---|
| 核心实际频率 | 2.54 GHz |
| TSC 计数器 | 2.30 GHz |

差 10%。如果拿 TSC 的差值当周期数，所有结论会系统性地偏小一成——不是随机误差，是朝一个方向的偏差，而且不会报错。

所以得先标定。标定的办法很朴素：找一条**每拍只能走一条**的指令，跑很多遍，用墙钟时间反推频率。

加法就是这样一条指令。`x = x + 1` 连做 n 次，每一次都要等上一次的结果写回同一个寄存器，跑不掉。所以 n 次就是 n 拍。

代码在 `cpu-ai/common/bench.h` 里：

    static inline double bench_calibrate_ghz(void)
    {
        const uint64_t n = 200000000ull;
        uint64_t ns0, ns1;

        bench_chain_add(n / 10);
        ns0 = bench_ns();
        bench_chain_add(n);
        ns1 = bench_ns();

        return (double)n / (double)(ns1 - ns0);
    }

第一行那个 `n / 10` 是热身。刚上电的时候频率还没稳，先跑一小段让它进入状态，这一段时间不计入。

然后记下开始时间，跑 n 次加法，记下结束时间。最后一行是全部秘密：n 拍除以纳秒数。一拍等于一纳秒的一千兆分之一，所以"拍每纳秒"就是 GHz。

那 `bench_chain_add` 里面是什么？是一段内联汇编：

    static inline void bench_chain_add(uint64_t n)
    {
        uint64_t x = 1;

        for (uint64_t i = 0; i < n; i += 8)
            __asm__ __volatile__(
                "addq $1, %0\n\t"
                ...
                "addq $1, %0"
                : "+r"(x));

        if (x == 0)
            putchar('\n');
    }

`"+r"(x)` 这个写法是关键。它的意思是：x 从寄存器读进来，算完写回**同一个**寄存器。所以第二条 add 读的必须是第一条的结果，第三条读第二条的，一条咬一条。

一次写八条而不是一条，是为了让循环本身的开销被摊薄——这一点下面还会踩一次坑。

最后那句 `if (x == 0) putchar('\n')` 看着莫名其妙。它的作用是让编译器相信 x 真的被用到了。没有它，编译器一看"这个 x 算完没人要"，会把整条链删掉。

这类"结果没人用"的删除，是微基准里最常见的假数据来源。它不报错，只是给你一个漂亮的零。后面量访存的时候还会栽一次。

主频标定出来是 2.54 GHz。有了这个数，后面每个"拍"都能从纳秒换算出来。

**加法和乘法各要几拍**

还是用依赖链，把 add 换成 imul：

| 依赖链 | 拍/条 |
|---|---|
| add | 0.98 |
| imul | 2.94 |

加法一拍，乘法三拍。

0.98 不是 1.00，是因为标定本身有百分之一的误差，不影响结论。

为什么乘法要三拍？因为乘法器在硬件里是分几级算出来的：先把乘数拆成几个部分积，再把这些部分积加起来。级数多，从输入到输出的路径就长。

但这里有个容易搞混的地方：**延迟三拍，不等于三拍才能开工一次。** 乘法器是流水的，这一条还在第三级的时候，下一条已经进第一级了。所以连着做一串互不相干的乘法，吞吐可以是一拍一条；只有后一条要用前一条的结果时，才被迫三拍一条。

这就是为什么"延迟"和"吞吐"必须分开量。

**一拍能喂几条**

把依赖拆掉，量吞吐。八条 add 分别写进八个不同的寄存器，互不相干：

    uint64_t a = 1, b = 2, c = 3, d = 4, e = 5, f = 6, g = 7, h = 8;

    __asm__ __volatile__(
        "addq $1, %0\n\t"
        "addq $1, %1\n\t"
        ... 一共 32 条，八个寄存器轮着加
        : "+r"(a), "+r"(b), "+r"(c), "+r"(d),
          "+r"(e), "+r"(f), "+r"(g), "+r"(h));

第一次量，得到 1.77 条/拍。

一台四发射的机器，理论上限是 4，量出 1.77，连一半都不到。问题出在写法上：一开始每个 asm 块里只放八条 add，而循环自己还有三条指令——`i += 8`、比较、跳转。十一条指令里三条是杂活，占了两成七。量出来的不是"add 能发几条"，是"add 加循环控制能发几条"。

把每块改成 32 条，杂活占比降到十一分之一，再量：

| 测试 | 拍/条 | 条/拍 |
|---|---|---|
| 8 条独立 add | 0.26 | 3.82 |

3.82 条/拍。这才像四发射机器该有的样子。

这个坑值得记住，因为它有个很讨厌的性质：**你量到的永远是你写的那段代码，不是你心里想的那个动作。** 循环控制、函数调用、栈帧准备，这些"不算计算"的东西都会混进来。唯一的办法是把它们摊薄，摊到可以忽略为止。

**五道关合起来**

到这里，五道关里三道有了数：取指译码 3.82 条/拍，执行 add 一拍、imul 三拍。写回不单独占时间——结果写进寄存器是一拍之内的事，但下一条要用这个结果的指令必须等它，所以它的影响体现在"延迟"里，不体现在"吞吐"里。

剩下访存这一道，单独说。


四、量一次访存要几拍

访存没法用依赖链直接量，因为地址得先知道。`a[i]` 的地址取决于 i，i 又取决于循环，这条链是断的。

换个办法：让地址本身也变成一条依赖链。

做法是把数组做成一条环。第 i 个位置存下一个位置的序号：

    next[i] = (i + K) & (n - 1)

K 是一个很大的奇数，n 是 2 的幂。奇数和 2 的幂互素，所以从任意一点出发，沿着这条环走，一定能走遍全部元素，不会提前回到起点。

K 取大是关键。相邻两次访问的地址跨得很远，硬件预取器就跟不上了。预取器是 CPU 里一个小预测器，它盯着你的访问模式，猜你下一步要读哪，提前把数据搬进缓存。它一旦猜中，你量到的就不是内存延迟，而是缓存延迟——数字好看，但没意义。

代码长这样：

    static double chase_cycles(uint32_t n)
    {
        const uint32_t k = 2654435761u;    /* 0x9E3779B1，奇数 */
        uint32_t *next = malloc((size_t)n * sizeof(uint32_t));
        ...
        for (i = 0; i < n; i++)
            next[i] = (uint32_t)((i + k) & (uint32_t)(n - 1));

        /* 预热：把整条环走一遍 */
        for (i = 0; i < n; i++)
            idx = next[idx];

        for (int r = 0; r < 3; r++) {
            uint32_t cur = idx;

            ns0 = bench_ns();
            for (i = 0; i < steps; i++)
                cur = next[cur];
            ns1 = bench_ns();
            ...
        }

        g_sink = idx;
        ...
    }

先把环建好，然后空走一圈预热，让缓存进入稳定状态。接着量三次，取最小值——干扰只会让时间变长，不会变短，所以最快的那次最接近真实。

`cur = next[cur]` 这一句就是全部。要读 `next[cur]`，得先知道 cur；cur 是上一次读出来的。一步等一步，这就是纯延迟。

最后那句 `g_sink = idx;` 看起来也莫名其妙，但它是这段代码里最不能少的一行。`g_sink` 是一个 `volatile` 全局变量。没有它，编译器会发现"这个循环算出来的 idx 没人用"，把整个循环删掉。

第一版就是这样：四个缓存层级全量出 0.0 拍。程序正常退出，输出格式漂亮，四个零。

量出来的结果：

| 工作集 | 拍/次访问 | 折合纳秒 |
|---|---|---|
| 16 KB　L1 | 4.3 | 1.7 |
| 128 KB　L2 | 13.2 | 5.2 |
| 4 MB　L3 | 122.1 | 48.0 |
| 32 MB　内存 | 304.7 | 119.8 |

从 L1 到内存，七十倍。

L3 那一档的 122 拍比一般资料里的 40 到 50 拍高不少。原因有两个：这是虚拟机，每次访问还要过一层地址转换；而且宿主的缓存被别的负载占着。真实机器上这一档会低一些，但"L1 和内存差两个数量级"这个结论不变。

这四个数就是"数据放在哪"的价格表。后面所有关于缓存、分块、数据布局的讨论，都是在这张表上做文章。


五、把三十毫秒算回去

回到开头那两千万次乘加。

如果每次乘加都能马上开工，一拍一次，两千万拍，2.54 GHz 下是 7.9 毫秒。这是那个"八毫秒"的来路。

实测三十毫秒，慢了将近四倍。四倍这个数字太整了，整到不像巧合。

看那条 `vaddss`。它要等上一轮的 `vaddss` 写完 `%xmm1` 才能读。而加法本身要走一拍才出结果，加上流水线的往返，一条依赖链上的加法是四拍一条。

两千万次乘加，每次四拍，八千万拍，三十一毫秒。

对上了。

所以这三十毫秒不是"CPU 慢"，是"每四拍才做完一次乘加"。计算单元在中间那三拍里是空的——不是没活干，是活还没轮到它。

能不能改？能。把一条累加链拆成四条，四条各自等各自的，四拍的延迟就被填满了。这一招在第四篇会量到，改完之后每拍能到 0.98 次乘加。

那如果数据不在 L1，而在内存里呢？

还是两千万次乘加，但每次都要等一次完整的内存延迟，三百零五拍：

两千万乘以三百零五，六十亿拍，二点四秒。

八毫秒到三十毫秒，再到二点四秒。同一个 CPU，同一个算法，同一份代码，三个数字差三百倍。

真实的程序不会落到最惨那一头——一个缓存行能装 16 个 float，预取器也会帮忙，实际是介于两者之间。但这三百倍的区间解释了一件事：为什么推理框架里那些看起来很"底层"的东西——分块、预取、数据布局、算子融合——值得花力气。

它们干的事只有一件：把操作数从"内存里"挪到"寄存器里"。

也是为什么"这个模型在这个 CPU 上跑多快"这个问题，光看参数量算不出来。得知道它跑的时候，数据在哪里。
