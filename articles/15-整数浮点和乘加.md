CPU 如何完成 AI 所需的整数、浮点数和乘加运算

—— 数据类型、精度，以及计算单元到底有多宽（第 2/5 篇）


一个模型量化到 int8，体积缩到四分之一，理论上计算量也该快四倍。

这句话在 CPU 上只对了一半。同一台机器、同一段点积，实测 int8 是 fp32 的两倍出头，不是四倍。原因不在算法，在硬件的两条约束上。

这一篇把这两条约束量出来：一条叫"一条指令能做几次乘加"，一条叫"每拍能搬多少字节"。


一、一条指令做几次乘加，是数据类型决定的

x86 上做点积，最核心的指令是乘加。同样一条指令，装什么类型，结果差很远：

    fp32   一条指令装 8 个 float，做 8 次乘加
    fp64   一条指令装 4 个 double，做 4 次乘加
    int32  一条指令装 8 个 int，做 8 次乘加
    int8   一条指令装 32 个字节，做 32 次乘加

看着 int8 是 fp32 的四倍，对吧。

这是"一条指令"的账，不是"一拍"的账。一条指令要几个拍才能发出去，还要看它需要读多少数据。

二、先把四种类型都量一遍

四个内核，都用 AVX2 手写，数据全部放在 L1 里（每对数组 8 KB + 8 KB = 16 KB，L1 是 32 KB），每个内核把整个数组跑两万遍，量总时间。

fp32 用 FMA 指令：

    for (; i + 32 <= n; i += 32) {
        s0 = _mm256_fmadd_ps(_mm256_loadu_ps(a + i), _mm256_loadu_ps(b + i), s0);
        s1 = _mm256_fmadd_ps(_mm256_loadu_ps(a + i + 8), _mm256_loadu_ps(b + i + 8), s1);
        s2 = _mm256_fmadd_ps(_mm256_loadu_ps(a + i + 16), _mm256_loadu_ps(b + i + 16), s2);
        s3 = _mm256_fmadd_ps(_mm256_loadu_ps(a + i + 24), _mm256_loadu_ps(b + i + 24), s3);
    }

四个累加器不是摆着好看的。一个 FMA 的延迟是 4 拍，只用一个累加器的话每 4 拍才能发下一条。

int8 用的是一条很多人不认识的指令：

    __m256i p16 = _mm256_maddubs_epi16(va, vb);
    acc = _mm256_add_epi32(acc, _mm256_madd_epi16(p16, ones));

`maddubs` 一次吃 32 个无符号字节和 32 个有符号字节，两两相乘再相加，得到 16 个 int16。一条指令 32 次乘加。

注意它的限制：**第一个操作数必须无符号**。这正好对上量化推理里的"uint8 激活 × int8 权重"，不是巧合，这条指令就是为这个设计的。

结果：

| 类型 | GMAC/s | MAC/拍 | 相对 fp32 |
|---|---|---|---|
| fp32　AVX2 FMA | 17.33 | 6.7 | 1.00x |
| fp64　AVX2 FMA | 9.60 | 3.7 | 0.55x |
| int32　AVX2 mullo | 9.84 | 3.8 | 0.57x |
| int8　AVX2 maddubs | 34.75 | 13.5 | 2.01x |

GMAC/s 是每秒十亿次乘加。MAC/拍 是每拍做几次，用第一篇那个标定出来的主频换算。

这台虚拟机上同一段程序连跑几遍，fp32 在 15~17 GMAC/s 之间晃，int8 的倍数在 2.0~2.7 之间晃——宿主在抢核，绝对值稳不住。**下面所有"差几倍"的结论都只看倍数关系，不看绝对值**，倍数比绝对值稳得多。

两个地方值得盯住。

三、fp64 正好是 fp32 的一半，这说明卡的不是运算

0.55 倍。不是 0.5，但很接近。

如果瓶颈在运算单元，fp64 应该是 fp32 的一半——因为一条指令只装 4 个 double 而不是 8 个 float，FMA 单元数量没变。

但 fp32 实测每拍只有 6.7 次，理论上是 16。差的那一半去哪了？

**去取数了。**

一条 AVX2 的 FMA 要读两个 256 位的操作数，加起来 64 字节。而这类 CPU 每拍只能做两次 32 字节的装载，也就是 64 字节。所以：

    每拍最多装 64 字节 ÷ 每次 FMA 要 64 字节 = 每拍 1 条 FMA

一条 FMA 装 8 个 float，所以每拍 8 次乘加是天花板。实测 6.7，是天花板的 84%。

fp64 呢？一条 FMA 装 4 个 double，仍然要 64 字节。所以每拍 1 条 FMA = 4 次乘加。实测 3.7，是天花板的 92%。

**两个都在九成上下，撞的是同一堵墙，所以比例正好是 2:1。** 这不是巧合，是同一个瓶颈的两种表现。

这也是为什么矩阵乘比点积快：矩阵乘里 A 的一个数被广播给 8 个通道重复用，一次装载喂了 8 次乘加，取数压力降到 1/8。第三篇会量到这一点。

四、int8 只有两倍，不是四倍

一条指令 32 次乘加，理论上该是 fp32 的四倍。实测 2.01 倍。

两个原因叠在一起。

**第一，取数还是 64 字节。** 32 个字节加 32 个字节，正好一拍装完，所以每拍最多 1 条 maddubs = 32 次乘加。这一层它赢了——fp32 每拍只有 8 次。

**第二，乘完还要归约。** `maddubs` 出来的是 16 个 int16，不能直接累加（会溢出），得再用 `madd_epi16` 两两合并成 8 个 int32，再 `add_epi32` 累加。**多出来两条指令，把四倍的优势吃掉了大半。**

这就是为什么后来的 CPU 加了 VNNI 指令集（`vpdpbusd`）：把"乘、两两合并、累加"合成一条。有一条指令就能真拿到接近四倍的收益。

ARM 上对应的是 `sdot` / `udot`（ARMv8.2 的 dotprod 扩展），思路一样。

**结论：int8 的收益取决于 CPU 有没有那条"融合乘加"指令。** 没有的话，别指望四倍，两倍是正常的。做选型的时候，这一条比"支持不支持 int8"重要得多——几乎所有 CPU 都"支持" int8，差别在快多少。

五、精度：累加器用多宽，结果差几千倍

吞吐是一半的故事。另一半是：位宽降下去，算出来的数还对吗？

做一个一百万项的求和，值都在 [-1,1]，正负各半。真值是一个随机游走的结果，量级几百——**这是最坏的情况：结果比每一项大得多，但比总和的正负抵消小得多。** 神经网络里 ReLU 之后的激活、带正负的权重，都是这个样子。

换 15 组不同的随机数各做一遍，取误差的中位数：

| 累加器 | 误差中位数 | 相对朴素 |
|---|---|---|
| fp16 累加 | 23.4378 | 6.6e+03x |
| fp32 朴素累加 | 0.0035 | 1x |
| fp32 八个累加器 | 0.0014 | 0.402x |
| fp32 两两合并 | 0.0001 | 0.0336x |
| fp32 Kahan 补偿 | 0.0000 | 0.00171x |
| fp64 直接累加 | 0.0000 | 0x |

fp16 累加器的误差是 23.4，而真值本身才 164。**误差是真值的 14%。**

原因很简单：fp16 只有 11 位尾数。累加到 100 多的时候，它能表示的最小间隔是 0.0625，而每次加进去的数才 0.5 左右——加一次就丢一半精度，加一百万次就全丢了。

这就是为什么量化推理里那条铁律：**权重可以 8 位，激活可以 8 位，累加器必须是 32 位。**

但更值得注意的是中间三行。

- 八个累加器：0.40 倍误差。改的是代码，不是类型。
- 两两合并：0.034 倍。改的是求和顺序。
- Kahan 补偿：0.0017 倍，比朴素好 585 倍。代价是每加一次多算三条指令。

**三个都不花硬件代价。** 相比之下 fp64 把吞吐砍掉一半，只换来 1e-16 的精度——对推理来说完全没必要。

一个实用的判断：如果你的模型在 CPU 上跑出来的结果和 GPU 对不上，先别怀疑算子写错了，先看看累加器是不是被降到了 fp16。

六、代码里两个容易踩的坑

**一、int8 的数据不能取太大。** `maddubs` 内部会把两两相乘的结果饱和到 int16，最大值 32767。两个 127 相乘再相加就 32258 了，再大就截断。测吞吐时数据取小一点（我用的 0~8 和 -8~8），否则量出来的数没意义。

**二、求和顺序会改变结果。** 浮点加法不满足结合律，`(a+b)+c` 和 `a+(b+c)` 结果可能不同。所以并行求和（SIMD、多线程、GPU）出来的结果和串行求和不一样，这是正常的，不是 bug。要求逐位一致的话，只能固定求和顺序，或者用整数。

七、回到场景

开头那个"量化到 int8 该快四倍"，现在可以拆开回答：

- 指令层面：确实一条做 32 次，是 fp32 的四倍；
- 取数层面：一拍只能装 64 字节，所以每拍最多 32 次，还是四倍；
- 归约层面：多两条指令，掉到两倍左右；
- 有 VNNI 或 dotprod：能拿回接近四倍。

**这四句话里，只有第三句是"你这台机器上"的答案，前三句是通用的。**

下一篇讲怎么用 SIMD 把这些乘加组织起来——以及一个反直觉的结果：手写向量指令，未必比让编译器自动做更快。
