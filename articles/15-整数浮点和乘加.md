CPU 如何完成 AI 所需的整数、浮点数和乘加运算

—— 数据类型、精度，以及计算单元到底有多宽（第 2/5 篇）


上一篇把一行 `s += a[i] * b[i]` 拆成六条指令，量出一件事：浮点加法四拍才出结果，整段循环就被这四拍卡住。

那换个数据类型呢？

你手上有一段跑得慢的点积，想让它快一点。最容易想到的办法是把数据从 float 换成 int8：体积小四倍，一条指令能多装几个数，怎么算都该快。

改起来也不难，把内层换成这两行：

    __m256i p16 = _mm256_maddubs_epi16(va, vb);
    acc = _mm256_add_epi32(acc, _mm256_madd_epi16(p16, ones));

编译，跑，量。

2.01 倍。

不是四倍，是两倍。而且这个 2 在不同机器上还会变——有的机器能给到三倍多，有的只有一倍出头。

差的那一半去哪了？这个问题值得追，因为答案不在算法里，在硬件的两条约束上：一条叫"一条指令能做几次乘加"，另一条叫"一拍能搬多少字节"。这两条一摆出来，fp32、fp64、int32、int8 四种类型的快慢关系就全定了，而且是算出来的，不是查出来的。

顺便还要回答量化绕不开的另一半：位宽降下去，算出来的数还对吗。


一、把四种类型写成同一道题

要比较四种类型，得让它们做同一件事。最合适的是点积——两个数组逐项相乘再累加。它是矩阵乘、卷积、全连接层的内核，也是"乘加"这件事最纯粹的形式。

每种类型写一个向量版内核，都用 AVX2 手写。为什么不用编译器自动向量化？因为要量的是"一条指令能做几次乘加"，得让指令是我指定的那一条，不能让它替我选。

fp32 的内核长这样：

    for (; i + 32 <= n; i += 32) {
        s0 = _mm256_fmadd_ps(_mm256_loadu_ps(a + i), _mm256_loadu_ps(b + i), s0);
        s1 = _mm256_fmadd_ps(_mm256_loadu_ps(a + i + 8), _mm256_loadu_ps(b + i + 8), s1);
        s2 = _mm256_fmadd_ps(_mm256_loadu_ps(a + i + 16), _mm256_loadu_ps(b + i + 16), s2);
        s3 = _mm256_fmadd_ps(_mm256_loadu_ps(a + i + 24), _mm256_loadu_ps(b + i + 24), s3);
    }

一行一条指令，一条指令干三件事：从 `a + i` 装八个 float 进来，从 `b + i` 装八个进来，乘完加进累加器。`fmadd` 是"乘加合一"，乘和加在一条指令里做完，中间那个乘积不落地。

八个通道，一次八次乘加。这就是 AVX2 的 256 位寄存器装得下的 float 个数：256 除以 32 等于 8。

**为什么是四个累加器，不是一个？**

一个 FMA 指令的延迟是四拍。如果只用 `s0` 一个累加器，第二组数据算出来要往 `s0` 里加，但它得等第一组的结果写完——四拍里只干了一拍的活。拆成四个，四条链各自等各自的，四拍的延迟就被填满了。

这个"四个"不是随便写的，它就是延迟的数字。

fp64 的内核结构一模一样，只是类型从 `__m256` 变成 `__m256d`，一条指令装四个 double 而不是八个 float。

int32 用的是另一条指令，`_mm256_mullo_epi32`，一次乘八个 32 位整数，加用 `_mm256_add_epi32`。整数没有"乘加合一"的指令，所以是两条。

int8 用的这条，很多人没见过：

    __m256i p16 = _mm256_maddubs_epi16(va, vb);
    acc = _mm256_add_epi32(acc, _mm256_madd_epi16(p16, ones));

`maddubs` 一次吃 32 个无符号字节和 32 个有符号字节，两两相乘再相加，得到 16 个 int16。一条指令 32 次乘加。

注意它的限制：**第一个操作数必须无符号**。这不是设计缺陷，是刻意为之——量化推理里最常见的就是"uint8 激活乘以 int8 权重"，这条指令就是为这个组合造的。

数据全部放在 L1 里。每对数组 8 KB 加 8 KB，一共 16 KB，L1 是 32 KB，装得下。这样量到的就只是计算单元，不掺访存。


二、先证明算得对，再谈算得快

程序跑起来，屏幕上先跳出来的不是速度，是一张核对表：

    === 一、先验证向量版和标量版算的是同一个数 ===
    fp32  标量 2.875000   向量 2.875000
    fp64  标量 -1.437500   向量 -1.437500
    int32 标量 92   向量 92
    int8  标量 -68   向量 -68

四行，左右两边必须一模一样。

这一步不能省，也不能放到最后做。向量版的手写代码最容易错的地方是边界——尾巴循环从哪儿开始、`i + 32 <= n` 是不是写成了 `i + 32 < n`、饱和有没有触发。这些错误不会让程序崩，只会让结果差一点点，然后你在一个错误的数上量出漂亮的速度。

所以先证明"算得对"，再谈"算得快"。顺序反过来，后面所有数字都白测。


三、四个内核排在一起量：fp64 正好是 fp32 的一半

四行都对上了，才开始计时。每个内核跑两万遍，量总时间，换算成每秒多少亿次乘加。

| 类型 | GMAC/s | MAC/拍 | 相对 fp32 |
|---|---|---|---|
| fp32　AVX2 FMA | 17.33 | 6.7 | 1.00x |
| fp64　AVX2 FMA | 9.60 | 3.7 | 0.55x |
| int32　AVX2 mullo | 9.84 | 3.8 | 0.57x |
| int8　AVX2 maddubs | 34.75 | 13.5 | 2.01x |

"MAC/拍"是每拍做几次乘加，用上一篇标定出来的 2.53 GHz 换算。

先看 fp64 那一行：0.55 倍。

如果瓶颈在运算单元，fp64 应该正好是 fp32 的一半——一条指令装四个 double 而不是八个 float，FMA 单元的数量没变，所以吞吐减半。0.55 离 0.5 很近，这个解释说得通。

但顺着这条线索往下算，会算出一个对不上的数。

fp32 每拍 6.7 次乘加，而理论上限是 16——八个通道乘两个 FMA 单元。实测只有四成。那六成去哪了？

**去取数了。**

一条 AVX2 的 FMA 要读两个 256 位的操作数，加起来 64 字节。而这类 CPU 每拍只能做两次 32 字节的装载，也就是 64 字节。

    每拍最多装 64 字节 ÷ 每次 FMA 要 64 字节 = 每拍 1 条 FMA

一条 FMA 装八个 float，所以每拍八次乘加就是天花板。实测 6.7，是天花板的 84%。

fp64 呢？一条 FMA 装四个 double，仍然要读 64 字节——两个 256 位操作数，一个字节都少不了。所以每拍还是一条 FMA，只是这条 FMA 只做四次乘加。实测 3.7，是天花板的 92%。

**两个都在九成上下，撞的是同一堵墙，所以比例正好是 2:1。**

这就是这件事的关键：fp64 慢一半，不是因为"double 运算更慢"，是因为"double 更宽，同样一拍搬不完"。运算单元一直闲着，卡住的是把数据送进去的那条路。

这也顺带解释了为什么矩阵乘能跑到几十 GFLOPS，而点积只能跑到十几。矩阵乘里 A 的一个数被广播给八个通道重复用，一次装载喂了八次乘加，取数压力降到八分之一。第三篇会量到这一点。


四、int8 撞的是同一堵墙，还多撞了一堵

回到开头那个问题。int8 一条指令 32 次乘加，是 fp32 的四倍，理论上该快四倍。实测 2.01 倍。

两个原因叠在一起。

**第一个：取数还是 64 字节。**

32 个字节的 uint8 加 32 个字节的 int8，正好一拍装完。所以每拍最多一条 `maddubs`，也就是 32 次乘加。

这一层 int8 赢了，而且赢得很干脆——fp32 每拍只有 8 次。如果只算这一层，int8 就是四倍。

**第二个：乘完还得把结果收拢。**

`maddubs` 出来的是 16 个 int16。这 16 个数不能直接往累加器里加，因为 int16 最大才 32767，累加几次就溢出了。

所以得再做两步：先用 `madd_epi16` 把相邻两个 int16 加起来变成 8 个 int32，再用 `add_epi32` 把它们累加进去。

    acc = _mm256_add_epi32(acc, _mm256_madd_epi16(p16, ones));

这一行里塞了两条指令：`madd_epi16` 和 `add_epi32`。加上前面那条 `maddubs`，做 32 次乘加要发三条指令。

三条指令一拍只能发一条（因为取数已经占满了一拍），所以每拍 32 次乘加变成了每三拍 32 次。四倍的优势被吃掉三分之二，落到两倍附近。

**这就是为什么后来的 CPU 加了 VNNI 指令集。**

VNNI 里有一条 `vpdpbusd`，把"乘、两两合并、累加"三步合成一条。有这条指令，32 次乘加就真的是一拍一次，四倍才拿得到。

ARM 上对应的是 `sdot` / `udot`（ARMv8.2 的 dotprod 扩展），思路一模一样。

这台机器是 Kaby Lake，2017 年的，没有 VNNI。所以量出来就是两倍。

这个结论对选型很直接：**int8 的收益取决于 CPU 有没有那条融合乘加指令，而不是取决于"支持不支持 int8"。** 几乎所有 CPU 都"支持"int8——能算，算得对。差别在快多少，而快多少完全由那一条指令决定。买芯片的时候看"支持 int8"这句话，等于什么都没看到。


五、位宽降下去，算出来的数还对吗

吞吐只是一半。量化还有另一半：位宽降了，结果还准不准？

这个问题在推理里很要命。模型跑出来的分类结果和 GPU 对不上、概率差百分之几、偶尔出现一个明显错误的框——这些症状里有一大半最后追到累加器的位宽上。

造一个最坏的情况来量。

一百万个随机数，值都在正负一之间，正负各半，求和。真值是一个随机游走的结果，量级在几百。

为什么说这是最坏的情况？因为结果比每一项大得多（几百对零点几），但比所有项的绝对值之和又小得多（几百对几十万）。中间那些大数互相抵消掉了，剩下的那点零头，全靠低位精度撑着。神经网络里 ReLU 之后的激活、带正负的权重，都是这个样子。

换十五组不同的随机数各做一遍，取误差的中位数。为什么是十五组、为什么取中位数？因为单次测量分不开三倍的差距——同一组数据碰巧怎么排，能让两个算法谁赢谁输翻过来。取中位数才稳。

| 累加器 | 误差中位数 | 相对朴素 |
|---|---|---|
| fp16 累加 | 23.4378 | 6.6e+03x |
| fp32 朴素累加 | 0.0035 | 1x |
| fp32 八个累加器 | 0.0014 | 0.402x |
| fp32 两两合并 | 0.0001 | 0.0336x |
| fp32 Kahan 补偿 | 0.0000 | 0.00171x |
| fp64 直接累加 | 0.0000 | 0x |

第一行最刺眼。fp16 累加器的误差是 23.4，而真值本身才 164。**误差是真值的 14%。**

原因不复杂。fp16 只有 11 位尾数，能表示的相对精度大概是千分之一。累加到一百多的时候，它能表示的最小间隔是 0.0625，而每次加进去的数才 0.5 左右。加一次丢一点，加一百万次就全丢了。

这就是量化推理里那条铁律的来路：**权重可以 8 位，激活可以 8 位，累加器必须是 32 位。**

下面四行更值得看，因为它们说明"精度"不一定要拿性能换。

- 八个累加器：0.40 倍误差。改的是代码结构，不是数据类型。
- 两两合并：0.034 倍。改的是求和顺序。
- Kahan 补偿：0.0017 倍，比朴素好 585 倍。代价是每加一次多算三条指令。
- fp64 直接累加：误差归零，代价是吞吐砍一半。

**前三个都不花硬件代价。** 只有最后一个是拿性能换的，而对推理来说完全没必要——1e-16 的精度，模型根本用不到。

这里有个容易做错的地方，值得单独说。两两合并的写法是"把数组劈成两半，各自求和再相加"，听起来简单，但**必须一直劈到底**。

如果只劈一层，然后各块内部顺序累加、块之间再顺序相加，那误差还是随块数线性增长，和朴素累加没有本质区别。真跑一遍会发现它比朴素还差——不是算法错了，是实现没劈到底。

劈到底之后，误差随 log2(n) 增长而不是随 n 增长。一百万项，log2 是 20，误差降了两个数量级，和表里的 0.034 对得上。

一个实用的判断：如果模型在 CPU 上跑出来的结果和 GPU 对不上，先别怀疑算子写错了，先看累加器是不是被降到了 fp16。


六、两个写代码时会踩的坑

**第一个坑：int8 的数据不能取太大。**

`maddubs` 内部会把两两相乘的结果饱和到 int16，最大值 32767。两个 127 相乘就是 16129，再加一个就 32258 了，再来一点就截断。截断不报错，只是结果变小，而且是小得很有规律。

所以测吞吐的时候数据要取小一点。这份代码里激活取 0 到 8，权重取 -8 到 8，乘积最大 64，两两相加最大 128，离饱和线很远。

如果拿全量程的 int8 数据去测，量出来的数不是"int8 有多快"，是"饱和之后有多快"，没有意义。

**第二个坑：求和顺序会改变结果。**

浮点加法不满足结合律。`(a+b)+c` 和 `a+(b+c)` 的结果可能不同，因为每一步都要舍入，而舍入的位置不一样。

所以并行求和（SIMD、多线程、GPU）出来的结果和串行求和不一样，这是数学性质，不是 bug。要求逐位一致，只能固定求和顺序，或者干脆用整数。

这也解释了为什么同一个模型在不同后端上跑，输出会差最后几位。差的是最后几位，但如果这个模型里有个 `if (x > 0.5)` 正好卡在边界上，最后几位就能把结果翻过来。做一致性测试的时候，容差要按这个道理定，不能要求逐位相等。


七、回到开头那个 2.01

开头那个 2.01 现在可以拆开回答了，而且每一层都有数字。

指令层面：一条 `maddubs` 做 32 次乘加，是 fp32 的四倍。这一层是真的。

取数层面：一拍只能装 64 字节，所以每拍最多一条，还是四倍。这一层也是真的。

归约层面：多两条指令，掉到两倍。这一层是这台机器的答案。

有 VNNI 或者 dotprod：融合成一条，能拿回接近四倍。

四句话里，只有第三句是"你这台机器上"的结论，前三句是通用的。

所以"量化能快几倍"这个问题，正确的问法不是"支持不支持 int8"，是"这条链路上从乘加到累加一共几条指令"。答对了这个问题，快几倍是能算出来的。

而精度那一半更值得记：位宽降下去，误差不是线性变大的，是在某个点上突然崩掉的。fp16 累加器在累加值超过 64 之后开始明显丢精度，超过 100 就基本废了。这个"崩掉的点"和数据的分布有关，和模型的层数有关，唯独和"我用了几位"这件事没有简单关系。

下一篇讲怎么用 SIMD 把这些乘加组织起来。里面有一个反直觉的结果：手写向量指令，未必比让编译器自动做更快——而在某些写法下，会慢一倍多。
