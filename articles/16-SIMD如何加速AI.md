ARM64 NEON/SIMD 如何加速 AI 计算

—— 向量指令、数据并行，以及一个反直觉的结果（第 3/5 篇）


上一篇量到，一条 AVX2 的 FMA 一次做八次乘加，但每拍只有 6.7 次——因为取数跟不上了。

那么顺理成章的想法是：把矩阵乘写得更"向量化"一些，是不是就快了？

这一篇拿同一道矩阵乘做五个版本，每个版本只改一个因素，看每一步到底值多少钱。最后一个版本是手写向量指令，而它**没有跑赢编译器自动做的**。

这个结果比"向量化快 N 倍"有用得多。因为它说明"向量化"不是一个开关，是一串有先后的动作，顺序错了，力气白花。


一、先把最笨的写法写出来

矩阵乘 C = A × B，最直觉的写法是三层循环：

    for (int i = 0; i < n; i++)
        for (int j = 0; j < n; j++) {
            float s = 0.0f;

            for (int k = 0; k < n; k++)
                s += A[(size_t)i * n + k] * B[(size_t)k * n + j];
            C[(size_t)i * n + j] = s;
        }

（下面几段代码里的 `(size_t)` 是下标转无符号 64 位整数。矩阵最大 512×512，`int` 本来也装得下，写它是为了在更大的尺寸下不至于先溢出。）

读法就是数学定义：C 的第 i 行第 j 列，等于 A 的第 i 行点乘 B 的第 j 列。三个循环变量对应三个下标，一一对上，没有一处需要想。

问题在最内层那个 k。

`A[i*n+k]` 随着 k 增加是顺序读的——A 的第 i 行，一个接一个。没问题。

`B[k*n+j]` 不是。k 每加一，地址就往后跳 n 个 float。n 是 512 的时候，一次跳 2048 个字节。**内存是跨着行跳着读的。**

一个缓存行 64 字节，能装 16 个 float。这么跳着读，每读一个数就要扔掉 15 个。也就是说，从内存搬到缓存的数据，十五分之十四是白搬的。

四核 2.5 GHz 的机器上，512×512 的矩阵乘只有 0.81 GFLOPS。

这个数很难看。同样的机器，理论上能做几十 GFLOPS。0.81 意味着每拍只做了不到一次浮点运算，而 CPU 一拍能做八次乘加、十六次浮点运算。

差出来的部分，全在等内存。


二、只把最内层换掉

第一件事不是上向量指令，是换顺序。

把 k 提到 j 外面：

    memset(C, 0, (size_t)n * (size_t)n * sizeof(float));

    for (int i = 0; i < n; i++)
        for (int k = 0; k < n; k++) {
            const float a = A[(size_t)i * n + k];

            for (int j = 0; j < n; j++)
                C[(size_t)i * n + j] += a * B[(size_t)k * n + j];
        }

数学上这是同一件事。C[i][j] 等于所有 k 上 A[i][k]·B[k][j] 的和，先遍历 k 还是先遍历 j，加法的顺序不同，结果一样（浮点上差最后几位，可接受）。

但访存完全变了。

最内层现在是 j。`C[i*n+j]` 随着 j 增加顺序往后走，`B[k*n+j]` 也顺序往后走。两个都是连续读，一个缓存行十六个数全用上，一点都不浪费。

`A[i*n+k]` 呢？它在 j 循环里是不变的——所以提到循环外面读一次，存在一个变量 `a` 里，内层循环一次内存都不用为它跑。

一次乘加的取数从"一个数 + 一个跳着的数"变成了"一个寄存器里的数 + 一个顺序的数"。搬运量少了一半还多。

改成这样，n=512 时从 0.81 到 2.40，三倍。

但三倍还不够。2.40 GFLOPS 意味着每拍一次浮点运算，离十六次差得远。**因为这时候还是标量指令——一次只算一个数。**


三、让编译器自己向量化

第二步最省事：把 `-fno-tree-vectorize` 去掉，换成 `-O3 -march=native`。

`-fno-tree-vectorize` 是"别自动向量化"的开关，前面为了把两个因素分开，一直关着。现在打开它，同时告诉编译器"按这台机器支持的指令集来"（`-march=native` 会打开 AVX2 和 FMA）。

代码一个字没改，重新编译。

n=512 时，从 2.40 到 12.59，5.2 倍。

这一步的收益是实打实的：一条指令算八个数，而不是一个。编译器会把内层循环拆成"每次处理八个"的主循环加一个处理余数的尾巴，用 `vmovups` 装数、`vfmadd` 乘加。

五个版本到这里有了三个。把四个尺寸的结果摆一起看：

先看第二行随尺寸的变化：1.2、1.7、1.8、3.0。

n=64 的时候换顺序几乎没用。一步只跳 256 个字节，预取器轻松跟上——它最喜欢这种固定步长，跳多远都能算出来。而且 16 KB 的矩阵本来就在缓存里。跳着读和顺着读，代价差不多。

n 越大，两个条件同时失效：步子变成 2 KB、8 KB，预取器算不过来了；矩阵也装不进缓存了。跳着读就真的在等内存。所以换顺序才从 1.2 倍一路涨到 3.0 倍。

同一件事在第一行也有反证：教科书顺序从 2.12 一路掉到 0.81，越大的矩阵越惨。**它掉的不是算力，是缓存。** 算法没变，运算量没变，只是数据从 L1 挪到了内存。


四、手写向量指令，结果更慢了

第三步：不用编译器的自动向量化，自己写。

很多人到这一步会想"编译器肯定不如我懂"，于是手写。最自然的写法是照着原来的循环结构，把最内层换成向量指令：

    void gemm_avx2(const float *A, const float *B, float *C, int n)
    {
        memset(C, 0, (size_t)n * (size_t)n * sizeof(float));

        for (int i = 0; i < n; i++) {
            int j = 0;

            for (; j + 8 <= n; j += 8) {
                __m256 acc = _mm256_setzero_ps();

                for (int k = 0; k < n; k++) {
                    __m256 a = _mm256_set1_ps(A[(size_t)i * n + k]);
                    __m256 b = _mm256_loadu_ps(B + (size_t)k * n + j);

                    acc = _mm256_fmadd_ps(a, b, acc);
                }
                _mm256_storeu_ps(C + (size_t)i * n + j, acc);
            }

            /* 尾部不足 8 列的，退回标量 */
            for (; j < n; j++) {
                float s = 0.0f;

                for (int k = 0; k < n; k++)
                    s += A[(size_t)i * n + k] * B[(size_t)k * n + j];
                C[(size_t)i * n + j] = s;
            }
        }
    }

逐行讲。

最外面还是 i，也就是 A 的行。中间那层是 j，一次处理八列——`j += 8`。最里面是 k，就是原来的内层。

`__m256 acc = _mm256_setzero_ps()` 造一个八个通道都是 0 的累加器。它待在寄存器里，整个过程不落地，直到最后才写回内存一次。这一点比教科书版强：教科书版每算完一个输出元素就要写一次内存，这里八个元素才写一次。

`_mm256_set1_ps(A[i*n+k])` 把 A 的一个数复制到八个通道——这叫广播。八个通道现在装着同一个数，接下来一次乘加就能同时乘上 B 的八个数。**一次装载，喂给八次乘加**，这正是上一篇说的"突破取数墙"的办法。

`_mm256_loadu_ps(B + k*n + j)` 从 B 里装八个连续的 float。`u` 是 unaligned，不要求 32 字节对齐——慢一点点，但不用管内存布局。

`_mm256_fmadd_ps(a, b, acc)` 做 `a × b + acc`，八个通道各自算各自的，互不干扰。这就是数据并行：一条指令，八个独立的乘法。

`_mm256_storeu_ps` 把八个结果一次写回去。

这段代码看着挺专业。累加器留在寄存器里，广播用上了，一次八个。该做的都做了。

量出来：n=512，4.85 GFLOPS。

比编译器自动做的 12.59 慢了将近三倍。

为什么？

看 `_mm256_loadu_ps(B + k*n + j)` 这一行。它在最内层的 k 循环里，k 每加一，地址就跳 n 个 float。n=512 的时候，每装 32 个字节，跳 2048 个字节。

**这条指令装进来的 32 个字节，是从一个 64 字节的缓存行里切出来的。下一轮 k 跳到 2048 字节之外，那个缓存行的另外 32 字节永远用不上。**

也就是说，向量化把"一次装八个"做到了，但装进来的八个数据只用了半条缓存行，剩下的全扔。

编译器那版不是这么干的。它没有被"必须照着原循环结构"绑住，它在 i,k,j 那个顺序上做向量化——所以 B 是顺着读的。

**这段代码输的不是指令，是访存。**


五、把顺序改对，再手写一次

第四步：同一个手写内核，只把 k 挪到外面。

    void gemm_avx2_ikj(const float *A, const float *B, float *C, int n)
    {
        for (int i = 0; i < n; i++) {
            float *crow = C + (size_t)i * n;

            memset(crow, 0, (size_t)n * sizeof(float));

            for (int k = 0; k < n; k++) {
                const float av = A[(size_t)i * n + k];
                const __m256 a = _mm256_set1_ps(av);
                const float *brow = B + (size_t)k * n;
                int j = 0;

                for (; j + 8 <= n; j += 8) {
                    __m256 c = _mm256_loadu_ps(crow + j);

                    c = _mm256_fmadd_ps(a, _mm256_loadu_ps(brow + j), c);
                    _mm256_storeu_ps(crow + j, c);
                }
                for (; j < n; j++)
                    crow[j] += av * brow[j];
            }
        }
    }

结构变了。最外面还是 i，中间变成 k，最里面变成 j。

现在 `brow = B + k*n` 在内层 j 循环里是个常量，`brow + j` 随着 j 顺序往后走。八次连续的 float 一次装完，一个缓存行的 64 个字节全用上。

`crow + j` 也是顺序的，C 的一行也是顺着走。

但这里有个代价：`_mm256_loadu_ps(crow + j)` 和 `_mm256_storeu_ps(crow + j)` 都在最内层——也就是说，**每算一个 k，C 的一行就要从内存读回来一次、写回去一次。** n 个 k，就是 n 次读写。

上一节那版没这个问题，它的累加器一直在寄存器里。

所以这一版是"用更多的 C 访存，换更顺的 B 访存"。

量出来：n=512，13.96 GFLOPS。

比上一版 4.85 快 2.9 倍，比编译器那版 12.59 快 11%。

11% 在重复测量的波动范围里——这台虚拟机连跑几遍，同一份代码能差这么多。所以准确的说法是：**它和编译器打平。**

n=128 的时候更明显，11.78 对 11.66，几乎一模一样。

这个结果比"打平"本身更有意思：**它明明多付了 n 次 C 的读写，还是赢了 2.9 倍。** 说明 B 的访问顺序比 C 的访问次数重要得多。

原因还是缓存行。C 那 n 次读写虽然多，但每次都是顺序的、32 字节对齐的一整块，缓存行用满了，预取器也跟得上。B 那边如果跳着读，每次只用到半个缓存行，剩下的全浪费——浪费的是内存带宽，而带宽是这条链路上最贵的资源。

**所以"向量化"本身值五倍，但"向量化"和"访存顺序"是两件事，顺序错了，向量化会亏。**

正确的顺序是：先改访存，再谈向量。

反过来做，投入的力气有一大半是白费的——你花了力气把一条指令塞进八个数，然后让这八个数据在内存里跳着走。


六、换到 ARM64

上面全是在 x86 上做的。ARM64 上的 SIMD 叫 NEON，位宽不一样。

x86 的 AVX2 一条指令 256 位，装八个 float。ARM64 的 NEON 是 128 位，装四个。

同样的点积，NEON 版这样写：

    static float dot_neon(const float *a, const float *b, int n)
    {
        float32x4_t s0 = vdupq_n_f32(0.0f);
        float32x4_t s1 = vdupq_n_f32(0.0f);
        float32x4_t s2 = vdupq_n_f32(0.0f);
        float32x4_t s3 = vdupq_n_f32(0.0f);
        int i = 0;

        for (; i + 16 <= n; i += 16) {
            s0 = vfmaq_f32(s0, vld1q_f32(a + i), vld1q_f32(b + i));
            s1 = vfmaq_f32(s1, vld1q_f32(a + i + 4), vld1q_f32(b + i + 4));
            s2 = vfmaq_f32(s2, vld1q_f32(a + i + 8), vld1q_f32(b + i + 8));
            s3 = vfmaq_f32(s3, vld1q_f32(a + i + 12), vld1q_f32(b + i + 12));
        }

        float r = vaddvq_f32(vaddq_f32(vaddq_f32(s0, s1), vaddq_f32(s2, s3)));

        for (; i < n; i++)
            r += a[i] * b[i];
        return r;
    }

指令名字全变了，思路一模一样：四个累加器（FMA 延迟四拍，所以四个），一次四个 float，循环末尾把四个累加器合并成一个标量。

`vdupq_n_f32` 造一个四个通道都是 0 的向量。`vld1q_f32` 装四个 float。`vfmaq_f32` 乘加。`vaddvq_f32` 把四个通道横向加起来，变成标量——x86 上这个动作要两次 `_mm_hadd_ps`，ARM 一条指令就够。

对照表：

| x86 AVX2 | ARM64 NEON |
|---|---|
| _mm256_loadu_ps | vld1q_f32 |
| _mm256_set1_ps | vdupq_n_f32 |
| _mm256_fmadd_ps | vfmaq_f32 |
| _mm256_add_ps | vaddq_f32 |
| _mm_hadd_ps（两次） | vaddvq_f32（一条） |
| 8 个 float / 指令 | 4 个 float / 指令 |

反汇编出来，内层循环完整是这样：

    2102c4:  ldp   q4, q5, [x11, #-0x20]        从 a 装 32 字节
    2102c8:  add   x10, x10, #0x10              下标 +16
    2102cc:  cmp   x10, #0x3e1                  走完了没有
    2102d0:  ldp   q6, q7, [x12, #-0x20]        从 b 装 32 字节
    2102d4:  fmla  v0.4s, v6.4s, v4.4s          累加器 0
    2102d8:  ldp   q16, q17, [x11], #0x40       再装 32 字节，地址 +64
    2102dc:  fmla  v1.4s, v7.4s, v5.4s          累加器 1
    2102e0:  ldp   q18, q19, [x12], #0x40       再装 32 字节，地址 +64
    2102e4:  fmla  v2.4s, v18.4s, v16.4s        累加器 2
    2102e8:  fmla  v3.4s, v19.4s, v17.4s        累加器 3
    2102ec:  b.lo  2102c4                       没算完就跳回去

十一条指令，一轮处理十六个元素。

拆开数：四条 `fmla` 算十六次乘加，四条 `ldp` 一共装 128 字节（a 和 b 各 64）。剩下三条是循环控制。

`ldp` 是"一次装一对寄存器"，一条装两个 128 位寄存器就是 32 字节，装完自动把地址往后挪。x86 的 `vmovups` 一条也是 32 字节，两者一样，没有谁更省。

值得算的是另一个比例：**每做一次乘加，要搬 8 个字节。**

    NEON   128 字节 ÷ 16 次乘加 = 8 字节/次
    AVX2    64 字节 ÷  8 次乘加 = 8 字节/次

两种架构、两种指令集、两种位宽，这个比例一模一样。

因为它是硬件决定的：一次乘加要读两个 float，每个 4 字节，就是 8 字节。**只要两个操作数都得从内存读，这个比例就降不下来。**

这也解释了为什么 NEON 的吞吐是 AVX2 的一半：一条指令装四个 float 而不是八个，但搬的字节数一样，所以算的次数少一半。不是 ARM 的 SIMD 设计得差，是位宽决定的。

想打破这个比例，只有一个办法：**让一个操作数留在寄存器里重复用。** 矩阵乘里广播 A 就是在干这个——A 的一个数被八个通道共用，八次乘加只花一次装载的钱。这才是矩阵乘能跑到十几 GFLOPS、而点积只能跑到几 GFLOPS 的原因。

**这段是怎么跑起来的**

这台机器是 x86_64，没有 aarch64 的运行环境。办法是交叉编译成 ARM64 的可执行文件，再用 qemu 的用户态模拟跑：

    clang --target=aarch64-linux-gnu -O2 -march=armv8-a+simd \
          -ffreestanding -nostdlib -static -fuse-ld=lld \
          -o bin/neon.aarch64 src/neon.c

    qemu-aarch64-static ./bin/neon.aarch64
    neon=6129 scalar=6129 equal=1

两件事要说明白。

**一、`-fuse-ld=lld` 不能省。**

x86 上装的那个 GNU ld 只会链 x86 目标。给它一个 aarch64 的目标文件，它直接报"无法辨认的仿真模式"，然后把支持的模式列一遍——全是 x86 的。lld 是 LLVM 自带的多架构链接器，能出 aarch64。

**二、`-ffreestanding -nostdlib` 是因为没有 aarch64 的 libc。**

这个程序不能 `#include <stdio.h>`，因为没有可以链进来的 aarch64 版 libc。所以它自己写 `_start`，用 `svc` 指令直接发系统调用：

    static long sys_write(int fd, const void *buf, unsigned long n)
    {
        register long x8 __asm__("x8") = 64;    /* __NR_write */
        register long x0 __asm__("x0") = fd;
        register long x1 __asm__("x1") = (long)buf;
        register long x2 __asm__("x2") = (long)n;

        __asm__ __volatile__("svc #0" : "+r"(x0) : "r"(x8), "r"(x1), "r"(x2) : "memory");
        return x0;
    }

x8 放系统调用号（64 是 write），x0 放第一个参数（文件描述符），x1 放缓冲区地址，x2 放长度，然后 `svc #0` 陷入内核。这是 ARM64 调系统调用的全部约定，没有别的东西。

**qemu 跑出来的时间没有意义。** 它逐条翻译执行，比真机慢几十倍。这一段只证明"算得对"，速度那一栏全部来自 x86 上的实测。

数据取的都是小整数，乘积和累加在 float 里都是精确的，所以两种加法顺序会得到逐位相同的结果。`equal=1` 说的是这个。

顺带说一句：如果两边算出来的数不一样，那就不是"速度差一点"的问题，是向量化的边界条件写错了——比如尾巴循环的起点算错，或者 `i + 16 <= n` 写成了 `i + 16 < n`。这类错误在 x86 上可能碰巧不触发，换到 ARM 上就露出来了。


七、这些数字怎么用

如果要在 CPU 上把一个矩阵乘提速，力气该往哪使，现在有顺序了：

| 顺序 | 做什么 | 收益 |
|---|---|---|
| 先 | 看访存顺序 | 3 倍，改几行循环嵌套 |
| 再 | 让编译器向量化 | 5 倍，加一个 -O3 -march=native |
| 最后 | 才考虑手写 | 0~10%，而且写错顺序会倒亏 |

第三行不是说手写没用。是说**在编译器已经能自动向量化的今天，手写的边际收益很小，而它带来的维护成本和可移植成本很高。**

真正需要手写的场合只有两类：编译器不肯向量化的（比如带复杂分支的、数据依赖绕不过的），以及你要榨干最后 20% 的（那就得连分块、预取、寄存器分配一起做，等于自己写一个 GEMM 库）。

还有一件事值得记住：**第一步和第二步不是"1+1"的关系，是乘法关系。** 顺序对了再向量化，5.2 倍乘在 3 倍上，是 15.5 倍。顺序没改就向量化，5 倍乘在 1 倍上，还是 5 倍——这就是那个 4.85 的版本，它确实向量化了，但基数太差。

下一篇讲另一个方向：就算向量化做对了，程序还是可能很慢。慢在三个地方——分支、依赖、缓存。三个都不报错，三个都跟主频无关。
