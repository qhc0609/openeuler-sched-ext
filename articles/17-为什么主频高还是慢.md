为什么 CPU 频率很高，AI 推理仍然可能很慢

—— 流水线、分支预测、指令并行与计算瓶颈（第 4/5 篇）


2.5 GHz 的意思是：一秒钟有 25 亿个时钟周期。

如果每一拍都能完成一次乘加，那就是 25 亿次乘加每秒。这个数听起来够用了。

但前面三篇量出来的实际数字是：点积 0.66 到 2.56 GMAC/s，矩阵乘 0.81 到 14 GFLOPS。**离"每拍一次"差得很远。**

差的那些拍去哪了？这一篇把三个主要去向量出来：分支猜错、指令依赖、数据不在缓存。

三个都属于同一类问题——**主频还在跑，活没干。**


一、先把账算清楚：主频 ≠ 吞吐

CPU 每一拍能做完多少事，有个名字叫 IPC（每拍指令数）。

    吞吐 = 主频 × IPC × 每指令工作量

主频是硬件的标称值，改不了。每指令工作量是数据类型和向量宽度决定的（第二、三篇）。**IPC 是软件决定的。**

软件写得不好，IPC 可以是 0.2；写得好，能到 3 以上。十五倍的差距，全在代码里。

下面三个实验，每个都只改一个因素，看 IPC 怎么掉下去。


二、分支预测：同样的数据，只换个顺序

这是最经典的一个。数组里三万个字节，随机值，要求把大于等于 128 的加起来：

    for (int i = 0; i < n; i++)
        if (v[i] >= 128) {
            s += v[i];
            c++;
        }

然后做两遍：一遍用随机排列的数组，一遍用排序后的同一个数组。

**数据完全一样，和也一样，只有排列不同。**

    数据顺序         拍/元素         相对
    随机排列              12.95           1.0x
    升序排列               2.65           4.9x

4.9 倍。

原因在流水线。CPU 不会等一条分支判完再往下走——它先猜，猜对了就继续，猜错了就把已经做了一半的活全扔掉，从正确的地方重来。

随机数据下，`v[i] >= 128` 有一半概率为真，预测器只能瞎猜，一半都错。每次猜错要扔掉十几个拍的活。

排序之后，前面一大段全是假、后面一大段全是真，只有中间一个转折点猜错。预测器几乎全对。

**注意这个实验里没有任何"计算"的变化。** 加法的次数一样，数组一样大，缓存全命中。慢的全部原因是"猜错要重来"。

这对 AI 的意义在哪？推理代码里的分支通常不多，但**数据相关的分支**不少：ReLU 的 `if (x > 0)`、稀疏算子的 `if (w != 0)`、量化里的 clamp。这些分支的行为完全取决于数据，预测器帮不上忙。

对付它们的办法不是"让预测更准"，是**让分支消失**：把 `if (x > 0) y = x; else y = 0;` 写成 `y = x > 0 ? x : 0`（编译器会生成一条条件传送指令，没有分支），或者用 `max(x, 0)`。这就是为什么 ReLU 在实现里常常写成 `fmaxf`。


三、指令依赖：计算单元空着，因为下一个数还没算出来

第二个实验：同一个点积，只改累加器的个数。

    s0 += a[i] * b[i];                    // 一个累加器
    s0 += a[i] * b[i];  s1 += a[i+1] * b[i+1];   // 两个
    ... 四个、八个

数据、指令条数、访问模式全都一样。区别只有一个：**下一个加法要不要等上一个加法的结果。**

    累加器              GMAC/s      MAC/拍       相对
    1 个累加器            0.66         0.25         1.0x
    2 个累加器            1.30         0.50         2.0x
    4 个累加器            2.53         0.98         3.9x
    8 个累加器            2.56         0.99         3.9x

一个累加器时，每拍只能做 0.25 次乘加——也就是**每四拍才做完一次**。

因为 FMA 指令的延迟是 4 拍：结果出来之前，下一条用它的指令只能等。等的时候计算单元是空的。

拆成两个，两条链各自等，每拍能做 0.5 次。拆成四个，正好把 4 拍的延迟填满，每拍 0.98 次。

**然后就不动了。** 八个累加器和四个一样（0.99）。

因为瓶颈换了：每拍只有两次装载，而一次乘加要读两个数。**算得再快也没用，取数跟不上了。**

这个拐点很重要。它说明"加累加器"只能解决"等结果"，解决不了"等数据"。到 1 拍 1 次就到顶了，再多加只是浪费寄存器。

四、缓存：矩阵从 16 KB 长到 64 MB

第三个实验：y = A × x，A 是 n×n 的矩阵，每一行完整读一遍。

算的东西一模一样，只是矩阵越来越大：

    工作集             n         GB/s   相对最快
    16 KB   L1           64        46.28           1.0x
    256 KB  L2          256        32.71           1.4x
    4 MB    L3         1024        19.95           2.3x
    64 MB   内存     4096        14.38           3.2x

从 46 GB/s 掉到 14 GB/s，3.2 倍。

这个实验里，**主频、指令、循环结构全都没变**。变的只有一件事：数据在 L1、L2、L3、还是内存里。

第一篇量过这个代价：L1 一次访问 4.3 拍，内存 305 拍。71 倍。

矩阵小的时候，整个矩阵在 L1 里，每拍都能拿到数据；矩阵大了，每读一个数都要等七十倍的时间。

顺带说一句：这里必须用向量指令才能量出这个差别。标量版每拍只能搬 4 个字节（一次乘加要读两个数，但每拍只有两次装载，所以每拍 1 次乘加 = 4 字节），天花板是 10 GB/s 左右——**不管数据在 L1 还是内存，都是这个数，缓存的影响被掩盖了。**

五、三种"等"的共同点

把三个实验放一起看：

    分支猜错   清空流水线，白等十几拍
    依赖太长   计算单元空转，只用到四分之一
    数据太远   计算单元等内存，等三百拍

三种都不是"算得慢"，是"算的时候在等"。

而且三种都有一个反直觉的地方：

- 分支那个，**数据一样、和一样**，只换顺序就差 4.9 倍；
- 依赖那个，**指令一样、条数一样**，只换写法就差 3.9 倍；
- 缓存那个，**算法一样、运算量一样**，只换数据大小就差 3.2 倍。

**没有一个能靠"换个更快的 CPU"解决。** 换 CPU 主频涨 20%，这三种等待一点不变。

六、怎么在自己的代码里找这三种

不用每次都做实验。有几个现成的信号：

**分支猜错**——看 `perf stat` 的 `branch-misses`。不过这台虚拟机拿不到这个计数器（下一篇详细说）。没有计数器时的替代办法：把可疑的分支改成无分支写法，看时间有没有变。

**依赖太长**——看内层循环里有没有"一条累加语句"。点积、求和、求最大值这类代码，如果只有一个累加变量，基本就是被延迟卡住的。改成四个或八个累加器，几行代码的事。

**数据太远**——看工作集大小和缓存的对比。L1 32 KB、L2 256 KB、L3 几 MB。你的算子处理的数据如果超过 L2，就得考虑分块了。

三条里最容易改、收益最直接的是第二条。**它不需要改算法，不需要改数据结构，只是把一个变量拆成四个。**

七、回到场景

"这台机器 2.5 GHz，跑这个模型要多久"——这个问题没法只看主频回答。

同样 2.5 GHz：

- 数据全在 L1、四个累加器、没有分支 → 每拍接近 1 次乘加；
- 一个累加器被延迟卡住 → 每拍 0.25 次；
- 再叠上数据在内存里 → 只会更低，不会更高。

**光前两条就差四倍，把第三条加上，十倍以上很正常。**

下一篇讲怎么把这三件事看清楚：用反汇编读指令，用 perf 找热点。以及这台虚拟机上做这件事会撞到什么。
