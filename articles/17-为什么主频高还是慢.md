为什么 CPU 频率很高，AI 推理仍然可能很慢

—— 流水线、分支预测、指令并行与计算瓶颈（第 4/5 篇）


2.5 GHz 的意思是：一秒钟有 25 亿个时钟周期。

如果每一拍都能完成一次乘加，那就是 25 亿次乘加每秒。八百万参数的小模型，一次推理大约两千万次乘加，八毫秒跑完。这个数听起来够用，甚至有点富余。

前三篇量出来的实际数字是：标量点积 0.66 GMAC/s，矩阵乘 0.81 到 14 GFLOPS。

0.66 GMAC/s 意味着每拍只做了 0.25 次乘加——**四拍才做完一次。**

差的那些拍去哪了？

这一篇把三个主要去向量出来：分支猜错、指令依赖、数据不在缓存。三个都不是"算得慢"，是"算的时候在等"。而三种等待有一个共同的性质，理解了它，就知道为什么"换台更快的 CPU"往往解决不了问题。


一、先把账算清楚：主频不等于吞吐

CPU 每一拍能做完多少事，有个名字叫 IPC，每拍指令数。

    吞吐 = 主频 × IPC × 每指令工作量

主频是硬件的标称值，改不了。每指令工作量是数据类型和向量宽度决定的，第二、三篇已经量过。**IPC 是软件决定的。**

同一个 CPU，代码写得不好，IPC 可以是 0.25；写得好，能到 3 以上。十二倍，全在代码里，和硬件无关。

所以"这台机器 2.5 GHz，跑这个模型要多久"这个问题，只看主频是答不出来的。得知道它跑的时候 IPC 是多少，而 IPC 取决于三件事：分支猜得准不准、指令之间有没有互相等、数据在不在缓存。

下面三个实验，每个只改一个因素，其余全部锁死。


二、第一个实验：数据一样，只换个顺序

这是最经典的一个，也是最容易被忽略的一个。

数组里三万个字节，随机值。要求把大于等于 128 的那些加起来，顺便数一数有多少个：

    for (int i = 0; i < n; i++)
        if (v[i] >= 128) {
            s += v[i];
            c++;
        }

然后做两遍：一遍用随机排列的数组，一遍用排序后的同一个数组。

**数据完全一样，和也一样，命中的个数也一样。**

第一遍随机排列，第二遍升序排列，结果：

| 数据顺序 | 拍/元素 | 相对 |
|---|---|---|
| 随机排列 | 12.95 | 1.0x |
| 升序排列 | 2.65 | 4.9x |

4.9 倍。

两次运行的加法次数一样，比较次数一样，内存访问的字节数一样，缓存全命中。唯一不同的是那三万个字节的排列顺序。

原因在流水线。

CPU 不会等一条分支判完再往下走——等的话流水线就空了。它先猜。猜"这次会进 if"，就提前把 if 里面的指令取进来、译码、甚至执行。猜对了，什么都不用做；猜错了，把已经做了一半的活全扔掉，从正确的地方重新取指。

扔掉要多久？取决于猜错的时候流水线里塞了多少东西。十几拍是常见的数。

随机数据下，`v[i] >= 128` 有一半概率为真。预测器看到的是一个完全随机的序列，它只能瞎猜，一半都错。每次猜错扔掉十几拍，平均下来每个元素多花十拍——这就是 12.95 减去 2.65 的那部分。

排序之后就不一样了。前面一大段全是假，后面一大段全是真，只有中间一个转折点猜错。预测器几乎全对，那十几拍的浪费没有了。

**这个实验里没有任何"计算"的变化。** 加法的次数一样，数组一样大，缓存全命中。慢的全部原因是"猜错要重来"。

这对 AI 的意义在哪？

推理代码里显式的分支通常不多，但**数据相关的分支**不少：ReLU 的 `if (x > 0)`、稀疏算子的 `if (w != 0)`、量化里的 clamp、检测后处理里的 `if (score > threshold)`。这些分支的行为完全取决于输入数据，而输入数据是随机的——预测器帮不上忙。

对付它们的办法不是"让预测更准"（那是硬件的事，你改不了），是**让分支消失**。

把 `if (x > 0) y = x; else y = 0;` 写成 `y = x > 0 ? x : 0`，编译器会生成一条条件传送指令（`cmov`），没有分支，也就没有猜错。或者直接用 `max(x, 0)`——这就是为什么 ReLU 在实现里常常写成 `fmaxf(x, 0.0f)`，而不是一个 if。

这里有个写测试代码的坑，顺手记一下：这个实验必须加 `-fno-if-conversion` 编译。不加的话 GCC 一看"这个 if 两边都只是赋值"，会主动把它变成 `cmov`——**你以为在测分支，其实分支已经没了**，两遍跑出来一样快，然后你会得出"分支预测不影响性能"的错误结论。

编译器的好意，有时候正好抹掉你想量的东西。


三、第二个实验：指令一样，只换写法

第二个实验：同一个点积，只改累加器的个数。

先写最朴素的那个，一个累加器：

    static float dot1(const float *a, const float *b, int n)
    {
        float s0 = 0.0f;

        for (int i = 0; i < n; i++)
            s0 += a[i] * b[i];
        return s0;
    }

一行一句，谁都看得懂。第 i 次迭代的 `s0 += ...` 要读 `s0`，而 `s0` 是上一次写进去的。所以第 i+1 次必须等第 i 次算完。

改成四个：

    static float dot4(const float *a, const float *b, int n)
    {
        float s0 = 0.0f, s1 = 0.0f, s2 = 0.0f, s3 = 0.0f;
        int i = 0;

        for (; i + 4 <= n; i += 4) {
            s0 += a[i] * b[i];
            s1 += a[i + 1] * b[i + 1];
            s2 += a[i + 2] * b[i + 2];
            s3 += a[i + 3] * b[i + 3];
        }
        for (; i < n; i++)
            s0 += a[i] * b[i];
        return (s0 + s1) + (s2 + s3);
    }

四个变量，四条独立的链。`s0` 等的是上一次的 `s0`，不是上一句 `s1`。四条链交错着走，一条在等的时候另外三条可以开工。

最后那个 `(s0 + s1) + (s2 + s3)` 也有讲究：按树形合并，比 `((s0+s1)+s2)+s3` 少一层舍入误差。这个细节在下一篇讲精度时还会遇到。

数据一样（2048 个 float，两个数组共 16 KB，稳在 L1），指令条数一样，访问模式一样。区别只有一个：**下一个加法要不要等上一个加法的结果。**

| 累加器 | GMAC/s | MAC/拍 | 相对 |
|---|---|---|---|
| 1 个累加器 | 0.66 | 0.25 | 1.0x |
| 2 个累加器 | 1.30 | 0.50 | 2.0x |
| 4 个累加器 | 2.53 | 0.98 | 3.9x |
| 8 个累加器 | 2.56 | 0.99 | 3.9x |

一个累加器时，每拍只能做 0.25 次乘加——每四拍才做完一次。

因为 FMA 指令的延迟是四拍。结果出来之前，下一条要用它的指令只能等。等的时候计算单元是空的：它有能力每拍开工一次，但没人给它活。

拆成两个，两条链各自等各自的，每拍能做 0.5 次。拆成四个，正好把四拍的延迟填满，每拍 0.98 次——接近硬件上限。

**然后就不动了。**

八个累加器和四个一样，0.99 对 0.98，在噪声里。多加的四个累加器一点用都没有。

这个"不动了"比前面那三段增长更值得看，因为它标出了瓶颈的换岗点。

到四个累加器的时候，"等结果"这件事已经被填满了。这时候再快，卡住的就不是延迟，是取数——每拍只有两次装载，而一次乘加要读两个数（a 和 b 各一个）。两次装载刚好喂一次乘加，所以每拍一次就是天花板。

再加累加器，只是多占四个寄存器，装载能力一点没变。

**所以"拆累加器"只能解决"等结果"，解决不了"等数据"。** 这是两种不同的等待，用同一种办法治不了。

顺便说，这条规律在写推理算子时非常实用：点积、求和、求最大值这类代码，如果只有一个累加变量，基本就是被延迟卡住的。改成四个，几行代码的事，收益接近四倍，而且不改变任何数值语义（浮点上差最后几位）。


四、第三个实验：算法一样，只换数据大小

第三个实验：y = A × x。A 是 n×n 的矩阵，x 是长度 n 的向量，每一行和 x 做一次点积。

内核用 AVX2 写，两个累加器，每行算完写进 y：

    static void matvec_avx2(const float *A, const float *x, float *y, int n)
    {
        for (int i = 0; i < n; i++) {
            const float *row = A + (size_t)i * n;
            __m256 s0 = _mm256_setzero_ps(), s1 = _mm256_setzero_ps();
            __m128 lo, hi, t;
            float acc;
            int j = 0;

            for (; j + 16 <= n; j += 16) {
                s0 = _mm256_fmadd_ps(_mm256_loadu_ps(row + j), _mm256_loadu_ps(x + j), s0);
                s1 = _mm256_fmadd_ps(_mm256_loadu_ps(row + j + 8), _mm256_loadu_ps(x + j + 8), s1);
            }

            __m256 s = _mm256_add_ps(s0, s1);

            lo = _mm256_castps256_ps128(s);
            hi = _mm256_extractf128_ps(s, 1);
            t = _mm_add_ps(lo, hi);
            t = _mm_hadd_ps(t, t);
            t = _mm_hadd_ps(t, t);
            acc = _mm_cvtss_f32(t);

            for (; j < n; j++)
                acc += row[j] * x[j];
            y[i] = acc;
        }
    }

中间那几行看着吓人，其实只干一件事：把一个装八个 float 的向量（`__m256`）压成一个标量。

先把它拆成两个 `__m128`（`castps256_ps128` 取低半，`extractf128_ps` 取高半），两个一加变成四个；再 `_mm_hadd_ps` 两次，四变二、二变一。这是 AVX2 上做横向求和的固定套路，没有更短的路。

算的东西一模一样，只是矩阵越来越大：

| 工作集 | n | GB/s | 相对最快 |
|---|---|---|---|
| 16 KB　L1 | 64 | 46.28 | 1.0x |
| 256 KB　L2 | 256 | 32.71 | 1.4x |
| 4 MB　L3 | 1024 | 19.95 | 2.3x |
| 64 MB　内存 | 4096 | 14.38 | 3.2x |

从 46 GB/s 掉到 14 GB/s，3.2 倍。

这个实验里，主频、指令、循环结构全都没变。变的只有一件事：数据在 L1、L2、L3、还是内存里。

第一篇量过这个代价：L1 一次访问 4.3 拍，内存 305 拍，差七十倍。矩阵小的时候，整个矩阵在 L1 里，每拍都能拿到数据；矩阵大了，每读一个数都要等七十倍的时间。

这里有个必须说清楚的地方：**这个实验必须用向量指令才能量出差别。**

用标量写，每拍只能搬 4 个字节（一次乘加要读两个数，每拍两次装载，所以每拍一次乘加等于 4 字节），天花板是 10 GB/s 左右。而不管数据在 L1 还是内存，都是这个数——因为瓶颈根本不在带宽，在装载指令的条数。

标量版的缓存影响被完全掩盖了：数据在内存里也跑 10 GB/s，在 L1 里也跑 10 GB/s，看起来"缓存没用"。

换成 AVX2，一次装载 32 字节，天花板抬到几十 GB/s，数据一旦出了缓存，带宽才成为真正的限制，3.2 倍的差距才露出来。

这也是一个常见的误判来源：用标量代码测缓存效果，测不出来，然后得出"缓存对这个算法没影响"的结论。其实是被别的瓶颈压住了。


五、三种等待，同一个性质

把三个实验放一起看：

| 卡在哪 | 后果 |
|---|---|
| 分支猜错 | 清空流水线，白等十几拍 |
| 依赖太长 | 计算单元空转，只用到四分之一 |
| 数据太远 | 计算单元等内存，等三百拍 |

三种都不是"算得慢"，是"算的时候在等"。

而且三种都有一个反直觉的地方：

- 分支那个，**数据一样、和一样**，只换顺序就差 4.9 倍；
- 依赖那个，**指令一样、条数一样**，只换写法就差 3.9 倍；
- 缓存那个，**算法一样、运算量一样**，只换数据大小就差 3.2 倍。

三次都是"什么都没改，就是慢了"。这就是为什么性能问题难查——它不是某一行写错了，是几行之间的配合不对。

**而这三个，没有一个能靠"换个更快的 CPU"解决。**

换一颗主频高 20% 的 CPU，这三个等待一点不变：分支该猜错还是猜错，依赖该等四拍还是四拍（延迟随工艺进步很慢），内存该等三百拍还是三百拍（内存延迟这些年几乎没降）。主频涨的那 20% 只作用在"真正在算"的那部分时间上，而那部分本来就不多。

所以"这台机器慢，换台快的"这个判断，在 IPC 低的时候是错的。IPC 低说明大部分时间在等，而等待不随主频缩短。


六、怎么在自己的代码里找这三种

不用每次都做实验。有几个现成的信号。

**分支猜错**——看 `perf stat` 的 `branch-misses`。这个计数器给出"每千条指令猜错几次"，超过 10 就值得看一眼。不过这台虚拟机拿不到这个计数器（下一篇详细说为什么），没有计数器时的替代办法是：把可疑的分支改成无分支写法，看时间有没有变。变了就是它。

**依赖太长**——看内层循环里有没有"一条累加语句"。点积、求和、求最大值、前缀和，这类代码如果只有一个累加变量，基本就是被延迟卡住的。改成四个或八个累加器，几行代码的事，不用改算法也不用改数据结构。

**数据太远**——看工作集大小和缓存的对比。L1 32 KB、L2 256 KB、L3 几 MB。你的算子处理的数据如果超过 L2，就得考虑分块了：把大矩阵切成能装进 L2 的小块，一块一块算完再换下一块。

三条里最容易改、收益最直接的是第二条。它不需要动算法，不需要动数据结构，只是把一个变量拆成四个。这也是为什么很多推理框架的内核里，你会看到 `s0 s1 s2 s3` 这样的变量名连着出现——那不是随便写的，是延迟的数字。


七、回到场景

"这台机器 2.5 GHz，跑这个模型要多久"——现在可以分层回答了。

同样 2.5 GHz：

- 数据全在 L1、四个累加器、没有分支：每拍接近 1 次乘加，两千万次乘加八毫秒；
- 只有一个累加器，被四拍延迟卡住：每拍 0.25 次，三十毫秒；
- 再叠上数据在内存里、分支还在乱跳：只会更低，不会更高。

**光前两条就差四倍，把第三条加上，十倍以上很正常。**

这就是开头那个 0.66 GMAC/s 的来路：它不是硬件的极限，是一份具体代码在具体数据上的结果。换个写法，同一个 CPU 能跑到 2.5 GMAC/s；换成向量指令加四个累加器，能到 17。

下一篇讲怎么把这三件事看清楚：用反汇编读指令，用 perf 找热点。以及这台虚拟机上做这件事会撞到什么——一个所有云主机和虚拟机用户都会撞到的墙。
