如何通过汇编和性能计数器观察 CPU 的实际执行行为

—— 反汇编、PMU、热点分析，以及采样会骗人的地方（第 5/5 篇）


前四篇一直在做同一件事：写两个版本，各跑一遍，比时间。

这个办法管用，但有个前提——**你得先想到该改哪一行**。改累加器个数、改循环顺序、换数据类型，都是因为事先知道那里可能有问题。如果慢的原因压根不在你的候选清单里呢？

那就只能猜。猜"是不是缓存没命中"，猜"是不是分支太多"，猜"是不是没向量化"。猜对了也说不清为什么，下次现象一样、原因不同，还得重来。

要跳出这个循环，得直接看两样东西：**编译器到底生成了什么指令**，以及**时间花在哪几条指令上**。

这一篇就把这两件事走一遍。中间会撞一堵墙，还会遇到一个会骗人的工具——这两个坑不是这台虚拟机特有的，云主机、容器、别人的机器上都会遇到。


一、先看编译器给了什么

拿一个具体的循环开头。这一篇要观察的就是它，一个八千次乘加的点积，外面再套二十四遍：

    #define N 8192

    static float ga[N], gb[N];

    __attribute__((noinline)) static float phase_heavy(void)
    {
        float s = 0.0f;

        for (int r = 0; r < 24; r++)
            for (int i = 0; i < N; i++)
                s += ga[i] * gb[i];
        return s;
    }

代码就这样，一行乘加，一个累加器。编译，然后反汇编：

    gcc -O2 -mfma -fno-tree-vectorize -o bin/hotloop src/hotloop.c
    objdump -d --no-show-raw-insn bin/hotloop | sed -n '/<phase_heavy>:/,/ret/p'

`--no-show-raw-insn` 是不要左边那串机器码，只留地址和指令。`sed` 那段是截取从函数名到 `ret` 之间的内容。

   0000000000401330 <phase_heavy>:
     401330:  mov    $0x18,%edx
     401335:  vxorps %xmm1,%xmm1,%xmm1
     401339:  nopl   0x0(%rax)
     401340:  xor    %eax,%eax
     401342:  nopw   0x0(%rax,%rax,1)
     401348:  vmovss 0x40e060(%rax),%xmm0
     401350:  vmulss 0x406060(%rax),%xmm0,%xmm0
     401358:  add    $0x4,%rax
     40135c:  vaddss %xmm0,%xmm1,%xmm1
     401360:  cmp    $0x8000,%rax
     401366:  jne    401348 <phase_heavy+0x18>
     401368:  sub    $0x1,%edx
     40136b:  jne    401340 <phase_heavy+0x10>
     40136d:  vmovaps %xmm1,%xmm0
     401371:  ret

那两条 `nopl` / `nopw` 是编译器插的对齐填充——空指令，什么都不做，只是把循环体的起始地址凑到 16 字节边界上。读反汇编时这类填充可以整段跳过。`jne` 后面那个 `<phase_heavy+0x18>` 是跳转目标的名字，方便人看，不影响指令本身。

跳过填充，内层循环是六条：

    vmovss  从内存读一个 float 到 xmm0        ← 访存
    vmulss  乘，结果还在 xmm0                 ← 执行（自己也读一次内存）
    add     下标 +4                           ← 执行
    vaddss  累加到 xmm1                       ← 执行
    cmp/jne 循环控制                          ← 执行
    sub/jne 外层循环（重复 24 遍）

六条指令，一眼能看出三件事。

**一、用的是标量指令。** `vmulss`、`vaddss` 里的 `ss` 是 scalar single，一次只处理一个 float。同一条指令换成 `vmulps`、`vaddps` 就是一次八个。编译时加了 `-fno-tree-vectorize`，是故意把自动向量化关掉的——这一篇要看的是最基本的形态，开了就看不见了。

**二、只有一个累加器。** `vaddss %xmm0,%xmm1,%xmm1` 每次都写回 `xmm1`。这是第一篇讲过的依赖链，每四拍才能做完一次乘加。

**三、处理一个元素要六条指令。** 就算前端每拍能发 3.8 条，最快也要 1.6 拍一个元素，实际更慢——那四拍的延迟等在那里。

这三件事在源代码里一条都看不出来。源码只有一行 `s += ga[i] * gb[i]`，看着干干净净。这一行背后是一次访存、一次乘法、一次加法、两次循环控制。**你觉得它"就是一次乘加"，CPU 觉得它是六条指令、五道关、四拍延迟。**

所以"这段代码为什么慢"已经答了一半：不是算法慢，是这个循环用了标量指令、只有一个累加器。改法也很具体——加 `-O3 -march=native`，或者手动拆累加器。

另一半还没答：这六条指令里，时间到底花在哪一条上？


二、想知道时间花在哪，撞墙了

要知道"哪条指令占的时间多"，得靠硬件性能计数器，也就是 PMU。CPU 里有一组寄存器，能数"执行了多少条指令""错了多少次分支""缓存未命中多少次"。`perf stat` 就是把它们读出来：

    perf stat -e cycles,instructions,branches,branch-misses,cache-misses -- ./bin/hotloop

这台机器上，结果是这样：

| 事件 | 结果 |
|---|---|
| cycles | 不可用 |
| instructions | 不可用 |
| branches | 不可用 |
| branch-misses | 不可用 |
| cache-misses | 不可用 |

`perf stat` 的原话是 `<not supported>`。五个全部不支持。

先排除两个常见原因。不是 perf 没装——命令能跑，下面会看到软件事件是好的。也不是权限——`perf_event_paranoid` 是 2，用 root 跑不受这个限制。

**是这台虚拟机的 CPU 没有把性能计数器透传进来。**

原因不难理解。PMU 是 CPU 里的硬件寄存器，虚拟机要读到它，hypervisor 得显式支持——得在虚拟 CPU 的配置里打开对应位，还得处理"宿主和客户机都想用同一个计数器"这种冲突。VMware 默认不开，因为它对虚拟化本身没好处，只对客户机的性能分析有好处。

这不是个别现象。云主机、虚拟机、部分容器环境里都拿不到 PMU。有些云厂商默认关，有些只在特定规格上开，有些干脆不提供。

所以做性能分析之前，第一件事是确认它在不在：

    perf stat -e cycles -- /bin/true

一条命令就知道。返回一个数字就能用，返回 `<not supported>` 就得换办法。这个检查值得写进任何一份性能测试脚本的开头——不然会花半天时间调 `perf stat` 的参数，最后发现不是参数的问题。


三、退一步，用软件事件

硬件计数器没了，还有软件事件。

`task-clock` 就是一个：内核按固定频率给进程记一笔"你还在跑"。它精确不到指令，但足够回答"这个进程用了多少 CPU 时间"。

    perf stat -e task-clock,context-switches,page-faults -- ./bin/hotloop 1500

| 事件 | 值 | 备注 |
|---|---|---|
| task-clock | 1,376.18 msec | 0.918 CPUs utilized |
| context-switches | 12 | 8.720 /sec |
| page-faults | 76 | 55.225 /sec |

跑了一秒半的墙钟时间，其中 1.376 秒真的在 CPU 上跑（所以利用率 91.8%），被换出去 12 次，缺页 76 次。

只有总时间，没有指令级信息。但它能**采样**。

    perf record -e task-clock -g -o perf.data -- ./bin/hotloop 3000
    perf report --stdio -i perf.data --no-children --percent-limit 1

    62.33%  hotloop  [.] phase_heavy
    34.94%  hotloop  [.] phase_branchy
     2.42%  hotloop  [.] phase_light

**这就是热点分析。**

原理很朴素：定时器每隔一段时间打断进程一次，把当时正在执行的指令地址记下来。跑三秒，记了 3600 个样本，按函数归一下类，就是上面这张表。

到这一步得说清楚这个程序是怎么设计的，不然这三行数字没法判断真假。它有三段，每段一个函数：

    __attribute__((noinline)) static float phase_light(void)       /* 轻量，估 10% */
    __attribute__((noinline)) static float phase_heavy(void)       /* 纯计算，估 70% */
    __attribute__((noinline)) static uint64_t phase_branchy(void)  /* 分支乱跳，估 20% */

三段处理同一批数据：8192 个 float 的 `ga`、`gb`，和 8192 个字节的 `gv`。`phase_light` 把 `ga` 全加起来，8192 次加法。`phase_heavy` 就是开头那个点积，重复二十四遍——相当于 light 的二十四倍工作量。`phase_branchy` 在随机字节上做条件累加，也是二十四遍，就是第四篇那个分支实验。

`noinline` 不能省。不加的话编译器会把三个函数内联进 `main`，热点分析的时候只能看到一团 `main`，分不出谁占多少。**这是做性能分析前的第一件事：确保你要观察的东西还有名字。**

设计时估的比例是 70 / 20 / 10。测出来 62.3 / 34.9 / 2.4。有答案的测试才叫测试，没答案的只能叫观察——这三行对上了，说明工具可信，可以往下用。

`phase_heavy` 62.3% 对得上。`phase_light` 只有 2.4%，估的是 10%——因为它确实太轻，那几次浮点运算在时间上根本不算什么。`phase_branchy` 34.9%，估的是 20%，偏高了：随机数据上的条件累加，每次猜错要扔十几拍，比按代码行数估的贵。

这三行的用处不是"知道谁占得多"——这个大概也能猜到。用处是**知道谁占得没你想象的多**。`phase_light` 写了五行代码，以为它占一成，实际 2.4%。优化它等于白干。

**关键点：没有 PMU，照样能做热点分析。** 少的只是"每条指令花了多少拍"这一层，不是"哪个函数占多少时间"这一层。前者告诉你微架构细节，后者告诉你该改哪个函数。对绝大多数性能问题来说，后者更有用。


四、进到函数里，工具开始骗人

有了热点函数，再往里钻一层：

    perf annotate -s phase_heavy -i perf.data --stdio

   73.93 :   401360: cmp    $0x8000,%rax
   25.49 :   40135c: vaddss %xmm0,%xmm1,%xmm1
    0.31 :   401348: vmovss 0x40e060(%rax),%xmm0
    0.18 :   401358: add    $0x4,%rax
    0.09 :   401350: vmulss 0x406060(%rax),%xmm0,%xmm0
    0.00 :   401371: ret

左边是这一条指令占的百分比。

**73.93% 落在 `cmp` 上。** 第一反应一定是"比较指令这么慢？"

不是。`cmp` 是一条一拍就能做完的指令，它不可能占七成时间。这个数一定有问题。

问题出在采样器的工作方式上。这是个必须知道的坑，叫**采样漂移**（skid）。

定时器打断进程时，CPU 记下的是"下一条要执行的指令"的地址，不是"正在执行的那条"。因为中断发生时，流水线里的指令已经取进来了、还没提交，记录的是提交点的地址。

而 `vaddss` 因为要等上一轮的结果，会在那里停四拍。这四拍里，CPU 的状态是"`vaddss` 还没算完，下一条是 `cmp`"。

所以样本全记在了 `cmp` 头上。**`cmp` 在替 `vaddss` 背锅。**

真实的结论是：`vaddss` 才是瓶颈。它占 73.93% 加 25.49%，差不多 99%——因为它是唯一一条带循环依赖的指令，每四拍才走一条。`cmp` 那 73.93% 是它等出来的。

这个规律可以记住：**如果 80% 的样本落在一条明显很便宜的指令上（`cmp`、`add`、`nop`、跳转），去看它前面那条。** 采样漂移只会往后漂一条，不会往前。

顺便说，`vmovss` 只占 0.31%，说明访存完全不是问题。

这有点反直觉：两个数组一共 64 KB，装不进 32 KB 的 L1，实际落在 L2 里，一次访问要十几拍。为什么几乎不花时间？

因为它被别的东西盖住了。访问是顺序的，预取器跟得上，数据提前就搬过来了；而 `vaddss` 那四拍的延迟正好等在这里——CPU 在等加法结果，顺手把下一个数也读了。**两种等待可以重叠，不叠加。**

所以"数据在 L2 所以慢"这句话不成立。慢不慢取决于有没有别的地方在等，等得到不到一起去。

反汇编和采样要对着看：汇编告诉你这个循环只有一个累加器，采样告诉你时间全在那条累加指令上。两个都对上，结论才算数。只看采样，就会去优化 `cmp`。


五、ARM64 上怎么看

x86 上 `objdump -d` 就够，ARM64 也一样，只是工具名字不同。

本地编译的 aarch64 程序，`objdump` 直接用；交叉编译出来的，得用 LLVM 的工具，因为它认目标架构：

    llvm-objdump -d --mattr=+neon bin/neon.aarch64

    2102d4:  fmla  v0.4s, v6.4s, v4.4s
    2102d8:  ldp   q16, q17, [x11], #0x40
    ...

`--mattr=+neon` 是告诉反汇编器"按带 NEON 的 ARMv8 来解"。不加的话某些向量指令会显示成 `.inst` 加一串数字。

想在 ARM64 上看"实际执行了哪些指令"，可以用 qemu 的指令跟踪：

    qemu-aarch64-static -d in_asm ./bin/neon.aarch64

`-d in_asm` 会把每翻译一块就打印一块的汇编。这能看到真正跑过的路径，但它只打印"翻译过的块"，不是逐条执行轨迹——循环体只会打印一次，后面都走缓存了。要看逐条轨迹用 `-d exec`，输出非常大，只适合看几十条指令的小片段。

**ARM64 自己的性能计数器**叫 PMCCNTR_EL0（周期）、PMEVCNTRn_EL0（可编程事件），读法是：

    mrs x0, pmccntr_el0

需要先在 PMCR_EL0 里使能（设置 E 位和 C 位）。这一段在 qemu 下读不到真实值，需要真机。原理和 x86 的 PMU 一样：都是硬件寄存器，都需要 hypervisor 透传。

所以交叉编译加 qemu 这条路，能验证"算得对"和"生成了什么指令"，验证不了"跑了多少拍"。这个边界要清楚，不然很容易拿 qemu 的时间去下结论。


六、如果一定要用 PMU

这台机器是 VMware 里的虚拟机，宿主是 i5-7300HQ，本身支持硬件性能计数器。开关是有的，只是默认关着。

打开的办法：

    虚拟机关机（不是重启）
    → 虚拟机设置 → 处理器
    → 勾选「虚拟化 CPU 性能计数器」（Virtualize CPU performance counters）
    → 开机，重跑 perf stat -e cycles -- /bin/true

必须关机，因为这是在配置虚拟 CPU 的能力，热插拔改不了。勾上之后 `cycles`、`instructions` 应该就能用了。

但要有心理准备：**虚拟机里的计数器仍然不等于裸机。**

计数器统计的是 vCPU 的时间，宿主把 vCPU 切走的那段时间不算在内。所以"周期数除以时间"算出来的频率，和实际频率对不上。频率也可能被宿主调——同一台虚拟机，隔壁跑一个重负载，你的 IPC 就变了。

做精确的 IPC 分析，还是得上裸机。虚拟机上能做的是**相对比较**：同一个程序改前改后，在同一个环境里比，结论可信；跨环境比绝对值，不可信。

这也是前四篇所有结论只写倍数、不写绝对值的原因。倍数在同一个环境里比是稳的，绝对值不稳。


七、这套流程

把这一篇的步骤串起来，遇到"这段代码为什么慢"，按这个顺序走：

| 步骤 | 做什么 | 这台机器上的结果 |
|---|---|---|
| 一、反汇编 | 看生成了什么指令：标量还是向量、几个累加器 | 六条指令、一个累加器 |
| 二、perf stat | 确认计数器可用性，拿到总时间 | PMU 不可用，拿到 1.376 秒 |
| 三、perf record | 采样，找出热点函数 | heavy 62.3% |
| 四、perf annotate | 进到函数里，找热点指令（记得减一条漂移） | `cmp` 73.9% → 其实是 `vaddss` |
| 五、对照源码 | 把热点指令翻译回代码，找到该改的那一行 | `s += ga[i] * gb[i]` |

每一步都有替代方案：

| 缺什么 | 怎么办 |
|---|---|
| 没有 PMU | 用 task-clock 采样，热点照样能找到 |
| 没有 perf | 用 gprof 或者自己在函数入口打时间戳 |
| 没有真机 | 用 qemu 看指令序列，但别信它的时间 |

**唯一没有替代方案的是第一步。**

反汇编只要一个 `objdump`，任何环境都能做——不需要 root，不需要内核支持，不需要硬件配合。而它能回答的问题比很多人以为的多：编译器有没有向量化、循环里有没有多余的边界检查、那个看着很轻的函数是不是被展开了二十遍。

这一篇里，"这段代码为什么慢"有一半是在第一步就答完的。剩下的那一半，才是计数器的活。


八、回到整个系列

五篇下来，一条指令从进 CPU 到出结果，路径是这样的：

| 阶段 | 代价 |
|---|---|
| 取指译码 | 前端每拍最多喂 3.8 条 |
| 执行 | add 一拍，imul 三拍，FMA 四拍延迟 |
| 访存 | L1 四拍，内存三百拍 |
| 写回 | 不占时间，但下一条依赖要等 |

AI 推理干的活，就是把这套东西重复几千万次。所以它的速度不由"主频"决定，由这四行里哪一行先卡住决定：

- 卡在取指 → 指令太密，或者分支太多
- 卡在执行 → 依赖太长，加累加器
- 卡在访存 → 数据太远，分块、改布局、算子融合
- 卡在写回 → 其实就是依赖，同一件事

前四篇量出来的数字，每一行都能对上：

| 现象 | 数字 |
|---|---|
| 分支乱序 | 12.95 拍/元素（有序 2.65） |
| 单个累加器 | 0.25 次乘加/拍（四个累加器 0.98） |
| 数据在内存 | 14 GB/s（在 L1 是 46） |
| 手写向量化 | 13.96 GFLOPS（编译器 12.59） |

**这些数字比"我的 CPU 是 2.5 GHz"有用得多。** 因为前者告诉你下一步该改什么，后者只告诉你硬件不差。

五篇里量出来的东西，没有一条是靠猜的。每一个数都有一个程序，每个程序都能重跑，每个结论都能追到一行输出。这不是为了严谨，是因为性能这件事的直觉太不可靠——你以为最慢的地方，往往只占 2.4%。
