如何通过汇编和性能计数器观察 CPU 的实际执行行为

—— 反汇编、PMU、热点分析，以及采样会骗人的地方（第 5/5 篇）


程序慢，最没用的办法是猜。

猜"是不是缓存没命中"，猜"是不是分支太多"，猜"是不是编译器没向量化"。猜对了一次，下次还得猜，因为下一次的现象可能长得一模一样，原因完全不同。

有用的办法是看。看两样东西：**编译器到底生成了什么指令**，以及**CPU 的时间花在哪几条指令上**。

这一篇把这两件事走一遍，包括这台虚拟机上撞到的一堵墙，和采样器骗人的方式。这两个坑不是这台机器特有的——所有云主机、虚拟机、容器环境都会撞到。


一、先写一个"答案已知"的程序

要演示怎么找热点，得先有一个热点明确的程序。如果随手拿一个真项目来测，测出来一堆数字，也没法判断对不对。

所以写一个三段式的程序，每段一个函数，各占一部分时间：

    __attribute__((noinline)) static float phase_light(void)      /* 轻量，约 10% */
    __attribute__((noinline)) static float phase_heavy(void)      /* 纯计算，约 70% */
    __attribute__((noinline)) static uint64_t phase_branchy(void) /* 分支乱跳，约 20% */

三个函数处理的是同一批数据：8192 个 float 的数组 `ga`、`gb`，和 8192 个字节的数组 `gv`。

`phase_light` 把 `ga` 全部加起来，8192 次加法。`phase_heavy` 是 `ga` 和 `gb` 的点积，做完重复二十四遍——相当于 `phase_light` 的二十四倍工作量。`phase_branchy` 在 `gv` 上做条件累加，也是二十四遍，就是上一篇那个分支实验。

`noinline` 不能省。不加的话编译器会把三个函数内联进 main，热点分析的时候只能看到一团 `main`，分不出谁占了多少。**这是做性能分析前的第一件事：确保你要观察的东西还有名字。**

跑三秒，然后用工具看。

为什么是"答案已知"？因为我知道 heavy 应该占七成左右。测出来六成，说明工具可信；测出来两成，说明要么程序写错了，要么工具在骗我。有答案的测试才叫测试，没答案的只能叫观察。


二、先看编译器给了什么

第一步不是 perf，是 objdump。因为如果编译器生成了明显不该生成的指令，后面所有性能分析都是在分析一个错误的前提。

    objdump -d --no-show-raw-insn bin/hotloop | sed -n '/<phase_heavy>:/,/ret/p'

`--no-show-raw-insn` 是不要左边那串机器码，只留地址和指令，读起来干净。`sed` 那段是截取从函数名到 `ret` 之间的内容。

   0000000000401330 <phase_heavy>:
     401330:  mov    $0x18,%edx
     401335:  vxorps %xmm1,%xmm1,%xmm1
     401339:  nopl   0x0(%rax)
     401340:  xor    %eax,%eax
     401342:  nopw   0x0(%rax,%rax,1)
     401348:  vmovss 0x40e060(%rax),%xmm0
     401350:  vmulss 0x406060(%rax),%xmm0,%xmm0
     401358:  add    $0x4,%rax
     40135c:  vaddss %xmm0,%xmm1,%xmm1
     401360:  cmp    $0x8000,%rax
     401366:  jne    401348 <phase_heavy+0x18>
     401368:  sub    $0x1,%edx
     40136b:  jne    401340 <phase_heavy+0x10>
     40136d:  vmovaps %xmm1,%xmm0
     401371:  ret

那两条 `nopl` / `nopw` 是编译器插的对齐填充——空指令，什么都不做，只是把循环体的起始地址凑到 16 字节边界上。读反汇编时这类填充可以整段跳过。

`jne` 后面那个 `<phase_heavy+0x18>` 是跳转目标的名字，方便人看，不影响指令本身。

剩下的逐条看：

    vmovss  从内存读一个 float 到 xmm0        ← 访存
    vmulss  乘，结果还在 xmm0                 ← 执行（自己也读一次内存）
    add     下标 +4                           ← 执行
    vaddss  累加到 xmm1                       ← 执行
    cmp/jne 循环控制                          ← 执行
    sub/jne 外层循环（重复 24 遍）

一眼能看出三件事。

**一、用的是标量指令。** `vmulss`、`vaddss` 里的 `ss` 是 scalar single，一次只处理一个 float。同一条指令换成 `vmulps`、`vaddps` 就是一次八个。写这段代码的时候是故意关掉自动向量化的（`-fno-tree-vectorize`），为的是让问题暴露出来。

**二、只有一个累加器。** `vaddss %xmm0,%xmm1,%xmm1` 每次都写回 `xmm1`。这就是上一篇说的"依赖太长"，每四拍才能做完一次乘加。

**三、内层循环六条指令处理一个元素。** 就算前端每拍能发 3.8 条，这个循环最快也要 1.6 拍一个元素，实际更慢——因为那四拍的延迟等在那里。

**这三件事在源代码里看不出来，在汇编里一目了然。**

源码只有一行 `s += a[i] * b[i]`，看着干干净净。这一行背后是一次访存、一次乘法、一次加法、两次循环控制。你觉得它"就是一次乘加"，CPU 觉得它是六条指令、五道关、四拍延迟。

所以第一个问题的答案有了：不是"这个算法慢"，是"这个循环用了标量指令、只有一个累加器"。改法也很清楚——加 `-O3 -march=native`，或者手动拆累加器。

但第二个问题还没答：时间到底花在哪几条指令上？这需要计数器。


三、想看 CPU 花了多少拍，撞墙了

常规做法是用硬件性能计数器（PMU）。CPU 里有一组寄存器，能数"执行了多少条指令""错了多少次分支""缓存未命中多少次"。`perf stat` 就是把它们读出来：

    perf stat -e cycles,instructions,branches,branch-misses,cache-misses -- ./bin/hotloop

在这台机器上，结果是：

    cycles           不可用
    instructions     不可用
    branches         不可用
    branch-misses    不可用
    cache-misses     不可用

`perf stat` 的原话是 `<not supported>`。五个全部不支持。

先排除两个常见原因。不是 perf 没装——`perf` 命令能跑，软件事件也能读到。也不是权限——`perf_event_paranoid = 2`，root 跑不受这个限制。

**是这台虚拟机的 CPU 没有把性能计数器透传进来。**

原因不难理解。PMU 是 CPU 里的硬件寄存器，虚拟机要能读到它，需要 hypervisor 显式支持——hypervisor 得在 VMCS 里打开对应位，还得处理"宿主和客户机都想用同一个计数器"这种冲突。VMware 默认不开这个开关，因为它对虚拟化本身没好处，只对客户机的性能分析有好处。

**这不是个别现象。** 云主机、虚拟机、部分容器环境里都拿不到 PMU。有些云厂商默认关闭，有些只在特定规格上开放，有些干脆不提供。

所以做性能分析之前，第一件事是确认它有没有：

    perf stat -e cycles -- /bin/true

一条命令就知道。返回一个数字就能用，返回 `<not supported>` 就得换办法。

这个检查值得写进任何一份性能测试脚本的开头。不然你会花半天时间调 `perf stat` 的参数，最后发现不是参数的问题。


四、退一步，用软件事件

硬件计数器没了，但还有软件事件。

`task-clock` 就是一个：内核按固定频率给进程记一笔"你还在跑"。它不精确到指令，但足够回答"这个进程用了多少 CPU 时间"。

    perf stat -e task-clock,context-switches,page-faults -- ./bin/hotloop 1500

    1,376.18 msec task-clock       # 0.918 CPUs utilized
           12      context-switches
           76      page-faults

这三行说的是：跑了一秒半的墙钟时间，其中 1.376 秒真的在 CPU 上跑（所以 CPU 利用率 91.8%），被换出去 12 次，缺页 76 次。

（perf 原始输出每行右边还有一列 `# ... /sec`，是每秒发生次数，为了排版这里省掉了。）

这个只有总时间，没有指令级信息。但它能**采样**。

    perf record -e task-clock -g -o perf.data -- ./bin/hotloop 3000
    perf report --stdio -i perf.data --no-children --percent-limit 1

    62.33%  hotloop  [.] phase_heavy
    34.94%  hotloop  [.] phase_branchy
     2.42%  hotloop  [.] phase_light

（原始输出里模块名那一列重复了两次，这里去掉了一列。）

**这就是热点分析。**

原理很朴素：定时器每隔一段时间打断进程一次，把当时正在执行的指令地址记下来。跑三秒，记了 3600 个样本，按函数归一下类，就是上面这张表。

`phase_heavy` 占 62.3%，和设计时估的"约 70%"接近。`phase_light` 只有 2.4%，估的是 10%——因为它确实太轻了，那几次浮点运算在时间上根本不算什么。`phase_branchy` 34.9%，估的是 20%，偏高了：随机数据上的条件累加，每次猜错要扔十几拍，比按代码行数估的要贵。

这三行的用处不是"知道谁占得多"——这个大概猜也能猜到。用处是**知道谁占得没你想象的多**。`phase_light` 你写了五行代码，以为它占一成，实际只占 2.4%。优化它等于白干。

**关键点：没有 PMU，照样能做热点分析。**

少的是"每条指令花了多少拍"这一层，不是"哪个函数占了多少时间"这一层。前者告诉你微架构细节，后者告诉你该改哪个函数。对绝大多数性能问题来说，后者更有用，因为改一个函数比改一条指令的现实意义大得多。


五、进到函数里，遇到一个会骗人的现象

有了热点函数，再往里钻：

    perf annotate -s phase_heavy -i perf.data --stdio

    73.93 :   401360: cmp    $0x8000,%rax
    25.49 :   40135c: vaddss %xmm0,%xmm1,%xmm1
     0.31 :   401348: vmovss 0x40e060(%rax),%xmm0
     0.18 :   401358: add    $0x4,%rax
     0.09 :   401350: vmulss 0x406060(%rax),%xmm0,%xmm0

左边是这一行占的百分比。

**看到 73.93% 落在 `cmp` 上，第一反应会是"比较指令这么慢？"**

不是。`cmp` 是一条一拍就能做完的指令，它不可能占七成时间。这个数一定有问题。

问题出在采样器的工作方式上。

这是一个必须知道的坑，叫**采样漂移**（skid）。

定时器打断进程时，CPU 记下的是"下一条要执行的指令"的地址，不是"正在执行的那条"。这是硬件计数器的一个特性：中断发生时，流水线里的指令已经取进来了，但还没提交，记录的是提交点的地址。

而 `vaddss` 因为要等上一轮的结果，会在那里停四拍。这四拍里，CPU 的状态是"vaddss 还没算完，下一条是 cmp"。

所以样本全记在了 `cmp` 头上。

**`cmp` 在替 `vaddss` 背锅。**

真实的结论应该是：`vaddss` 是瓶颈。它占了 73.93% 加 25.49%，差不多 99%——因为它是唯一一条带循环依赖的指令，每四拍才能走一条。`cmp` 那 73.93% 是它等出来的。

这个规律可以记住：**如果 80% 的样本落在一条明显很便宜的指令上（cmp、add、nop、跳转），去看它前面那条。** 采样漂移只会往后漂一条，不会往前。

顺便说，`vmovss` 只占 0.31%，说明访存完全不是问题。

这有点反直觉：两个数组一共 64 KB，装不进 32 KB 的 L1，实际落在 L2 里，一次访问要十几拍。为什么几乎不花时间？

因为它被别的东西盖住了。访问是顺序的，预取器跟得上，数据提前就搬过来了；而 `vaddss` 那四拍的延迟正好等在这里——CPU 在等加法结果，顺手把下一个数也读了。**两种等待可以重叠，不叠加。**

所以"数据在 L2 所以慢"这句话不成立。慢不慢取决于你有没有别的地方在等，等得到不到一起去。

如果没有这个交叉验证，看到 73.93% 就想"是不是该优化比较指令"，方向就错了。反汇编和采样要对着看，两个都对上才算数。


六、ARM64 上怎么看

x86 上 `objdump -d` 就够，ARM64 也一样，只是工具名字不同。

如果是本地编译的 aarch64 程序，`objdump` 直接用；如果是交叉编译出来的，得用 LLVM 的工具，因为它认目标架构：

    llvm-objdump -d --mattr=+neon bin/neon.aarch64

    2102d4:  fmla  v0.4s, v6.4s, v4.4s
    2102d8:  ldp   q16, q17, [x11], #0x40
    ...

`--mattr=+neon` 是告诉反汇编器"按带 NEON 的 ARMv8 来解"。不加的话某些向量指令可能显示不出来，或者显示成 `.inst` 加一串数字。

想在 ARM64 上看"实际执行了哪些指令"，可以用 qemu 的指令跟踪：

    qemu-aarch64-static -d in_asm ./bin/neon.aarch64

`-d in_asm` 会把每翻译一块就打印一块的汇编。这能看到真正跑过的路径，但它只打印"翻译过的块"，不是逐条执行轨迹——循环体只会打印一次，后面都走缓存了。

要看逐条轨迹用 `-d exec`，输出会非常大，只适合看几十条指令的小片段。

**ARM64 自己的性能计数器**叫 PMCCNTR_EL0（周期）、PMEVCNTRn_EL0（可编程事件），读法是：

    mrs x0, pmccntr_el0

需要先在 PMCR_EL0 里使能（设置 E 位和 C 位）。这一段在 qemu 下读不到真实值，需要真机。原理和 x86 的 PMU 一样：都是硬件寄存器，都需要 hypervisor 透传。

所以交叉编译加 qemu 这条路，能验证"算得对"和"生成了什么指令"，验证不了"跑了多少拍"。这个边界要清楚，不然很容易拿 qemu 的时间去下结论。


七、如果一定要用 PMU

这台机器是 VMware 里的虚拟机，宿主是 i5-7300HQ，本身支持硬件性能计数器。开关是有的，只是默认关着。

打开的办法：

    虚拟机关机（不是重启）
    → 虚拟机设置 → 处理器
    → 勾选「虚拟化 CPU 性能计数器」（Virtualize CPU performance counters）
    → 开机，重跑 perf stat -e cycles -- /bin/true

必须关机，因为这是在配置虚拟 CPU 的能力，热插拔改不了。

勾上之后 `cycles`、`instructions` 应该就能用了。

但要有心理准备：**虚拟机里的计数器仍然不等于裸机。**

计数器统计的是 vCPU 的时间，宿主把 vCPU 切走的那段时间不算在内。所以"周期数除以时间"算出来的频率，和实际频率对不上。频率也可能被宿主调——同一台虚拟机，隔壁跑一个重负载，你的 IPC 就变了。

做精确的 IPC 分析，还是得上裸机。虚拟机上能做的是"相对比较"：同一个程序改前改后，在同一个环境里比，结论可信；跨环境比绝对值，不可信。

这也是前四篇所有结论只写倍数、不写绝对值的原因。倍数在同一个环境里比是稳的，绝对值不稳。


八、这套流程

把这一篇的步骤串起来，遇到"这段代码为什么慢"，按这个顺序走：

| 步骤 | 做什么 |
|---|---|
| 一、反汇编 | 看生成了什么指令：标量还是向量、几个累加器 |
| 二、perf stat | 确认计数器可用性，拿到总时间和上下文切换 |
| 三、perf record | 采样，找出热点函数 |
| 四、perf annotate | 进到函数里，找热点指令（记得减一条漂移） |
| 五、对照源码 | 把热点指令翻译回代码，找到该改的那一行 |

每一步都有替代方案：

| 缺什么 | 怎么办 |
|---|---|
| 没有 PMU | 用 task-clock 采样，热点照样能找到 |
| 没有 perf | 用 gprof 或者自己在函数入口打时间戳 |
| 没有真机 | 用 qemu 看指令序列，但别信它的时间 |

**唯一没有替代方案的是第一步。**

反汇编只要一个 objdump，任何环境都能做——不需要 root，不需要内核支持，不需要硬件配合。而它能回答的问题比很多人以为的多：编译器有没有向量化、循环里有没有多余的边界检查、那个看着很轻的函数是不是被展开了二十遍。

很多"性能问题"在这一步就结束了，根本走不到 perf。


九、回到整个系列

五篇下来，一条指令从进 CPU 到出结果，路径是这样的：

| 阶段 | 代价 |
|---|---|
| 取指译码 | 前端每拍最多喂 3.8 条 |
| 执行 | add 一拍，imul 三拍，FMA 四拍延迟 |
| 访存 | L1 四拍，内存三百拍 |
| 写回 | 不占时间，但下一条依赖要等 |

AI 推理干的活，就是把这套东西重复几千万次。所以它的速度不由"主频"决定，由这四行里哪一行先卡住决定：

- 卡在取指 → 指令太密，或者分支太多
- 卡在执行 → 依赖太长，加累加器
- 卡在访存 → 数据太远，分块、改布局、算子融合
- 卡在写回 → 其实就是依赖，同一件事

四篇实测加起来，每一行都能量出具体数字：

| 现象 | 数字 |
|---|---|
| 分支乱序 | 12.95 拍/元素（有序 2.65） |
| 单个累加器 | 0.25 次乘加/拍（四个累加器 0.98） |
| 数据在内存 | 14 GB/s（在 L1 是 46） |
| 手写向量化 | 13.96 GFLOPS（编译器 12.59） |

**这些数字比"我的 CPU 是 2.5 GHz"有用得多。** 因为前者告诉你下一步该改什么，后者只告诉你硬件不差。

五篇里量出来的东西，没有一条是靠猜的。每一个数都有一个程序，每个程序都能重跑，每个结论都能追到一行输出。这不是为了严谨，是因为性能这件事的直觉太不可靠——你觉得最慢的地方，往往只占 2.4%。
