一个 while(1) 装不下机器人

—— 感知、决策、规划、控制、执行，五个环节为什么必须分成两种节奏（1.1）


每个写过单片机的人都写过这个循环：

    while (1) {
        read_sensor(&s);
        if (s.dist < 300)
            stop();
        else
            forward();
    }

感知、判断、执行，三件事都在里面，跑起来也对。这就是一个完整的机器人——只要它一辈子只干这一件事。

问题出在第二件事加进来的时候。


一、"判断"长大以后叫"规划"

要绕开障碍物，得算未来 200 毫秒的轨迹；要给机械臂下发，得逐点做逆解；再往后还要跑模型。这段代码的耗时不再是几微秒，而是几毫秒到几百毫秒。

而控制那一拍不能变。伺服环 1 kHz，周期 1 毫秒，晚一点关节就开始抖。

把两件事放进同一个循环，循环的周期就由**最长的那个**决定。每 50 拍做一次 2 毫秒的规划，这一拍的实际周期就不是 1 毫秒，是 3 毫秒。


二、量一下，比说清楚有用

`robot-brain/test/naive-loop.c` 就是上面那个循环的完整版，核心只有这些：

    while (n < NSAMP) {
        int planning = (n % every == every - 1);

        next += period;
        sleep_until(next);
        t0 = now_ns();

        /* 1. 读状态 */
        float q_now = q;

        /* 2. 伺服更新——控制周期就是这一拍的长度 */
        q = control_step(q_now, 1.0f, (float)period / 1e9f, 0.02f);

        /* 3. 规划，串在同一个循环里 */
        if (planning)
            busy_us(think_us);

        t1 = now_ns();

`busy_us()` 代表一次真正要花 CPU 的计算。三件事串行，所以规划那一拍，伺服也一起被拖长。

跑三组，每组两万拍，绑核加 `SCHED_FIFO`：

    taskset -c 2 chrt -f 50 ./bin/naive-loop --hz 1000 --think-us 2000 --every 50

| 规划耗时 | 普通拍循环体 | 规划拍循环体 | 周期 p50 | 周期 p99 | 规划那拍的周期 |
|---|---|---|---|---|---|
| 0 | 0.33 µs | 0.39 µs | 991.7 µs | 1570.8 µs | 994.1 µs |
| 2 ms | 0.30 µs | 2000.36 µs | 990.9 µs | 3001.7 µs | 2992.7 µs |
| 20 ms | 0.20 µs | 20000.37 µs | 922.9 µs | 20995.1 µs | 20994.0 µs |

第三列到最后一列只差一个数：**规划那一拍的周期 = 规划耗时 + 1 毫秒**。伺服自己只用 0.3 微秒，剩下两毫秒全在等规划算完。

第二组里，超过 1.5 倍名义周期的拍子占 3.4%（680 / 20000）。这个比例不是巧合——两万拍里正好有 400 次规划。

第三组的 p50 反而降到 922.9 µs，别当成变好了。落后 20 毫秒之后 `next_tick` 早就过去了，后面十几拍的 `sleep_until` 立刻返回，周期被压成几十微秒。这叫补拍，是控制系统最不想要的东西——要么停 21 毫秒，要么连甩十几拍，没有中间态。

对伺服来说，这一拍不是"晚了一点"，是**停了 21 毫秒**。速度环的积分项在这段时间里继续按原来的方向累积，下一拍要一口气还回来。


三、五个环节，两种节奏

| 环节 | 干什么 | 时间尺度 |
|---|---|---|
| 感知 | 编码器、相机、力传感器 | 1 kHz ~ 30 Hz |
| 决策 | 走哪条路、抓不抓 | 1 ~ 20 Hz |
| 规划 | 未来 200 ms 的轨迹、逆解 | 5 ~ 20 Hz，单次 10 ~ 200 ms |
| 控制 | 插值、限幅、限位、伺服 | 1 kHz，抖动 < 100 µs |
| 执行 | 电机、减速器 | 跟着控制走 |

这张表翻译成一句话：**上面三层按"想"的节奏，下面两层按"动"的节奏，差两个数量级。**

所以问题不是哪个环节写错了。是它们本来就不该待在同一个循环里。


四、拆成两个进程

- **大脑**（Linux，20 Hz）：感知、决策、规划，输出未来 200 毫秒的轨迹
- **小脑**（1 kHz）：插值、变化率限幅、关节限位、伺服模型

两边只通过一个结构体说话，就是 `include/shm_proto.h` 里这个：

    struct rb_traj_seg {
        uint64_t t0_ns;
        uint64_t t_gen_ns;   /* 大脑做完决策的时刻，用来算端到端延迟 */
        uint32_t n;
        uint32_t seq;
        struct rb_traj_point p[RB_TRAJ_POINTS];
    };

最关键的是 `t0_ns`。大脑发出去的不是"立刻动"，是"从这一刻开始，按这条轨迹走"。小脑用自己的单调时钟判断，两边不需要同步时钟，也不需要大脑等小脑。

大脑卡了，小脑照着手里的轨迹继续走；走完了还没新轨迹，减速保持；再没有，安全停机。这套逻辑在小脑里，不在大脑里——因为出事的时候大脑正好指望不上。


五、拆开之后

同一个机器人，同样的虚拟机，把大脑的推理耗时从 0 加到 80 毫秒：

| 推理耗时 | 小脑周期 avg | 丢拍率 | 跟随误差 |
|---|---|---|---|
| 0 | 1.025 ms | 0.51% | 0.0570 rad |
| 10 ms | 1.216 ms | 2.99% | 0.0570 rad |
| 40 ms | 1.045 ms | 1.11% | 0.0570 rad |
| 80 ms | 1.086 ms | 1.87% | 0.0570 rad |

80 毫秒是什么概念：规划周期才 50 毫秒，大脑已经算不完了。

四组的周期都在 1.0 ~ 1.2 毫秒之间，和推理耗时**没有单调关系**——最差的那一组是 10 毫秒，不是 80 毫秒。这台虚拟机上主导抖动的是宿主机，不是大脑，所以周期这一列只能看量级，不能看趋势。

四组里唯一完全一致的是最后一列：**跟随误差 0.0570，一个数字都没动**。这才是要看的量——它说明小脑手里的指令没有跳变，机器人不会抽搐。

再把大脑直接 `kill -9`：

    [cereb] 状态切换 0 -> 1 @ 453 ms
    [cereb] 状态切换 1 -> 2 @ 3603 ms
    [cereb] 状态切换 2 -> 3 @ 4152 ms

0 是待机，1 是跟轨迹，2 是失联后保持，3 是安全停机。中间那 250 毫秒是看门狗的第一个阈值，后面那 800 毫秒是第二个。

轨迹缓冲从 206 毫秒掉到 103 毫秒、再掉到 9 毫秒，跟随误差还是 0.0570。大脑死透了，机器人自己停下来了，中间没有一次抖动。


六、这篇只想说明一件事

"大脑"不是算得更多的那块 CPU。它是**允许慢、允许卡、允许死的那一层**。

它的存在不是为了自己跑得快，是为了让下面那层永远准时。
