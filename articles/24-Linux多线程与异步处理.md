Linux 多线程与异步处理

—— 四件事、一个 1 kHz 的循环，和一个决定丢谁的队列（1.6）


一、一段你写过的循环

控制回路长这样，几乎所有人第一版都是这么写的：

    while (1) {
            next += PERIOD_NS;              /* 1 ms，1 kHz */
            clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL);
            read_imu(&s);                   /* 1. 接收 */
            servo(&s, &cmd);                /* 2. 控制 */
            if (tick % 100 == 0)
                    replan(&cmd);           /* 3. 决策，每 100 ms 一次 */
            log_line(&s);                   /* 4. 日志 */
    }

这段代码没有 bug。它按顺序做四件事，每 1 毫秒重来一次。

问题只有一个：**这 1 毫秒里，留给"控制"的还剩多少？**

答案是 1 毫秒减去另外三件事。这就是"阻塞"——不是死锁，不是卡住，就是排队。排在你前面的那件事做完了，才轮到你。

这一篇量的就是这个排队有多长，以及把它拆开之后，代价从"等"变成了什么。


二、五档，一件一件加上去

四件事各自的价钱：

    控制      50 us      伺服解算，一次矩阵乘加
    接收       5 us      从串口取一帧，解析 24 字节头
    决策    8000 us      每 100 ms 一次，摊到每拍是 80 us
    日志     447 us      一行 fprintf + 一次 fsync

`blocked.c` 就干一件事：从"只有控制"开始，一档一档往上加，每档跑 3000 拍，量这一拍真正花了多少时间。

| 模式 | 每拍工作量 | 1 ms 里还剩 | 占空比 | 丢拍 |
|---|---|---|---|---|
| 控制 | 52 us | +948 us | 5.2% | 38 |
| 控制 + 接收 | 57 us | +943 us | 5.7% | 64 |
| 控制 + 接收 + 决策 | 136 us | +864 us | 13.6% | 211 |
| 再加日志（每拍 fsync） | 583 us | +417 us | 58.3% | 719 |
| 日志改成攒 100 行 fsync 一次 | 170 us | +830 us | 17.0% | 331 |

前两档是加出来的：50 + 5 = 55，量到 57。第三档 55 + 80 = 135，量到 136。

**串行做四件事，工作量就是四件事相加。** 这没什么好争的，它就是加法。

真正难看的是第四行。控制算法自己只要 50 微秒，占这一拍的 5.2%。加上日志之后，占空比 58.3%——**一台 1 kHz 的机器人，93% 的时间不在算控制，在等磁盘。**

（丢拍那一列要打个折看。这台虚拟机自己会随机抢走 CPU 几毫秒，最上面那行"只跑控制"也有 38 次丢拍。所以看的是增量：38 → 719。）

第五行是个预告。同样四件事，只把日志从"每行 fsync"改成"攒 100 行 fsync 一次"，占空比从 58.3% 掉回 17.0%。这件事后面再说，它是这一篇里唯一真正省下时间的改动。


三、拆成四个线程

四件事之间没有数据依赖的先后——接收产数据，控制用它，决策偶尔插一脚，日志只管记。既然是四件独立的事，就该有四个线程。

    pthread_create(&th[0], NULL, ctl_thread, &cpus);     /* 1 kHz */
    pthread_create(&th[1], NULL, rx_thread, &cpus);      /* 2 kHz */
    pthread_create(&th[2], NULL, decide_thread, &cpus);  /* 8 ms / 100 ms */
    pthread_create(&th[3], NULL, log_thread, &cpus);     /* 有多少写多少 */

`cpus` 是绑核参数。绑到 4 个核上，控制线程的迟到——控制计算真正开始的时刻减去它该开始的时刻——中位数 0.1 微秒。

0.1 微秒。对比一下第二段里那个 583 微秒：**同一台机器，同一份控制代码，从"每拍被拖 583 微秒"变成"每拍晚 0.1 微秒"。**

但这里有一句必须说清楚的话：**拆分本身不产生并行，核才有。**

把四个线程全绑到 1 个核上，同一个程序、同一份代码：

| | 迟到 p50 | 迟到 p99 | 丢拍（5000 拍） |
|---|---|---|---|
| 四个线程，4 个核 | 0.1 us | 437 us | 32 |
| 四个线程，1 个核 | 10.5 us | 2743 us | 137 |

一个核上，四个线程还是要排队——只不过排队的地方从你的 `while` 循环里，挪到了调度器的运行队列里。区别是：在你的循环里，你知道谁排在谁前面；在调度器里，你不知道。

所以"多线程解决阻塞"这句话有个前提：**线程数不能超过你能用的核数。** 4 核跑 4 个常驻线程，刚好；4 核跑 40 个，等于没有拆。


四、队列里的数据是旧的

拆开之后，四件事之间的接口从"函数调用"变成了"队列"。

函数调用是同步的：你调用它，它返回，你拿到结果。队列是异步的：你放进去，不知道什么时候被处理；你取出来，不知道它是多久以前放进去的。

**异步的第一个后果，是你拿到的东西是旧的。**

`split.c` 里传感器跑 2 kHz，控制跑 1 kHz，中间的环形队列 64 条。控制每拍怎么取，有两种写法：

    /* 写法一：取一条 */
    got = ring_pop(&g_rx, &s);

    /* 写法二：排空，只留最新的一帧 */
    got = 0;
    while (ring_pop(&g_rx, &s)) {
            last = s;
            got = 1;
    }
    s = last;

两种写法，控制拿到的数据差 32 倍：

| | 数据龄 p50 | 传感器队列丢 | 控制没拿到新数据 |
|---|---|---|---|
| 每拍取一条 | 31994.9 us | 4942 条 | 1 次 |
| 每拍排空只留最新 | 991.8 us | 0 条 | 627 次 |

32 毫秒是怎么来的？队列 64 条，传感器每秒塞 2000 帧，64 ÷ 2000 = 32 毫秒。队列里永远排着 32 毫秒的数据，你每拍取走最前面那条，取到的就是 32 毫秒前的那条。

**一个 1 kHz 的回路，喂给它的是 31 Hz 的数据。** 你把伺服做到每秒算一千次，用的却是每秒更新 31 次的世界。剩下那 969 次，算的是同一份旧数据。

这里有个反直觉的地方：环形队列 + 满了丢旧，**并不等于**你拿到的数据是新的。

丢旧只保证队列里留的是最新的 64 条；消费者从头取，取的还是这 64 条里最旧的那条。要真的拿到新的，消费者必须**排空**——把队列里的全取出来扔掉，只留最后一帧。因为对控制回路来说，中间那些帧没有价值：32 毫秒前的三个采样点，不如现在的这一个。

排空之后数据龄回到 991.8 微秒，差不多就是一拍。

代价在最后一列：627 次（12.5%）控制没拿到新数据。因为传感器线程和控制线程的节拍都是 1 毫秒，谁先醒不定；控制先醒的时候，这一拍的新数据还没进来。所以排空之后要配一句"没拿到就用上一帧"——这叫零阶保持，一行代码的事，但不写就是空指针。


五、异步不解决吞吐

日志这边更直接。

产量：控制每拍一行，1000 行/秒；决策每 100 毫秒把 200 行轨迹倒进去，又是 2000 行/秒。合计 3000 行/秒。

消费能力：每行一次 fsync。`bench.c` 连续敲 2000 行，2614 行/秒。

**2614 是 3000 的 87%。** 差 13%，队列一定涨，而且不会自己停下来。

无界队列，跑 5 秒：

| | 日志落后 p50 | 队列最深 | 落盘的最后一条编号 |
|---|---|---|---|
| 无界链表，满了不丢 | 340896.7 us | 2077 条 | 12922 / 15000 |

日志落后 341 毫秒。控制回路那边一点没受影响——迟到还是 0.1 微秒，它不等磁盘了。**异步没有让磁盘变快，它只是把"控制回路等磁盘"换成了"日志晚一点写出来"。**

排队那 341 毫秒，看起来能接受。但看最后一列：15000 条里只落盘了 12922 条，**还有 2077 条躺在内存里**。

进程一崩，这 2077 条一起没。而这 2077 条正好是最近 341 毫秒的——也就是事故现场那一段。

日志系统最讽刺的一种失败：它忠实地记下了三分钟前一切正常，唯独没记下崩溃前那 341 毫秒。


六、满了丢谁

队列不能无界，得有个深度。满了就得丢，丢谁是一个必须做的决定。`ring.h` 里两个 push 给了两个答案：

    /* 丢最旧的：把 tail 往前推一格，腾出位置 */
    static inline int ring_push_drop_old(struct ring *r, const void *e)
    {
            size_t h = atomic_load_explicit(&r->head, memory_order_relaxed);
            size_t t = atomic_load_explicit(&r->tail, memory_order_acquire);
            int lost = 0;
            if (h - t >= r->cap) {
                    atomic_store_explicit(&r->tail, t + 1, memory_order_release);
                    atomic_fetch_add(&r->dropped, 1);
                    lost = 1;
            }
            memcpy((char *)r->buf + (h & (r->cap - 1)) * r->esz, e, r->esz);
            atomic_store_explicit(&r->head, h + 1, memory_order_release);
            return lost;
    }

    /* 丢最新的：满了就不收 */
    static inline int ring_push_drop_new(struct ring *r, const void *e)
    {
            size_t h = atomic_load_explicit(&r->head, memory_order_relaxed);
            size_t t = atomic_load_explicit(&r->tail, memory_order_acquire);
            if (h - t >= r->cap) {
                    atomic_fetch_add(&r->dropped, 1);
                    return 0;
            }
            memcpy((char *)r->buf + (h & (r->cap - 1)) * r->esz, e, r->esz);
            atomic_store_explicit(&r->head, h + 1, memory_order_release);
            return 1;
    }

两个函数只差三行：一个把 `tail` 往前推、一个直接返回 0。

把队列深度定成 512 条，两种丢法各跑 5 秒：

| | 日志落后 p50 | 丢 | 队列最深 | 落盘的最后一条编号 |
|---|---|---|---|---|
| 512 条，丢最旧 | 144414.4 us | 1849 条 | 512 | 14375 |
| 512 条，丢最新 | 158669.1 us | 1597 条 | 512 | 14413 |

两个数字很接近：丢 1849 和 1597，落后 144 毫秒和 159 毫秒，最后落盘的编号 14375 和 14413。

**争"丢旧还是丢新"，量下来几乎没有差别。** 因为它们都只做了一件事：把队列深度钉在 512，于是日志落后被钉在 512 ÷ 2614 ≈ 196 毫秒。丢谁只决定丢的是哪一段，不决定丢多少。

真正决定你落后多久的，是**队列深度**这个数：

    512 条    196 ms
    4096 条   1.6 s
    无界      内存涨到撑不住为止

所以深度不是随便填的。填 512 等于说"我允许日志落后 0.2 秒"，填 4096 等于说"1.6 秒"，填无界等于说"我不知道，反正内存够大"。写这个数的时候，得知道自己在承诺什么。


七、攒批

前面五档里第五行那个 17.0%，是这一篇唯一真正省下时间的改动。日志线程里只多了一个计数器：

    if (g_batch) {
            if (++pending >= g_batch) {
                    fflush(g_lf);
                    fsync(fileno(g_lf));
                    pending = 0;
            }
    } else {
            fflush(g_lf);
            fsync(fileno(g_lf));
    }

攒够 100 行，才 `fflush` + `fsync` 一次。同样是 512 条丢最新，跑 5 秒：

| | 日志落后 p50 | 日志落后 p99 | 丢 | 队列最深 | 落盘 |
|---|---|---|---|---|---|
| 每行 fsync | 158669.1 us | 198051.8 us | 1597 条 | 512 | 14413 |
| 攒 100 行 fsync | 508.8 us | 3667.6 us | 0 条 | 201 | 14798 |

落后从 159 毫秒掉到 0.5 毫秒，丢的从 1597 条变成 0 条，队列最深 201 条。

为什么差这么多？`fsync` 的价钱几乎和写多少字节无关。`bench.c` 量了三个尺寸：

    256 字节     342.7 us
    4096 字节    378.9 us
    65536 字节   525.9 us

从 256 字节到 64 KB，大了 256 倍，时间只涨了 1.5 倍。它买的是"让内核把这一批数据落到盘上"这件事，不是"搬这些字节"。

所以每行 fsync 一次，你为 20 个字节付了一次完整的落盘代价；攒 100 行，同样的代价摊到 100 行上。

**异步救不了吞吐，批量才能。** 把日志扔到另一个线程，只是让控制回路不再等；日志线程自己还是每秒只能写 2614 行。要让它写得动 3000 行，得减少 fsync 的次数，不是换线程。

顺带说一句 4096 那个数：它是文件系统的一个页。攒到 4 KB 左右再 fsync，是这台机器上最划算的批大小——按一行 20 字节算，大概 200 行。


八、用不用锁值多少钱

这一篇里我用了环形队列，没用"互斥锁 + 链表"。网上说无锁队列快一个数量级。量一下：

    环形队列：进一次 + 出一次     6.9 ns
    互斥锁：加锁 + 解锁（没人抢） 8.9 ns

差 2 纳秒。

同一份 `bench.c` 里，`fsync` 一次是 342700 纳秒。

**无锁省 2 纳秒，批量省 342700 纳秒。** 差五个数量级。

不是说无锁没用——网络栈每秒收发几百万次，2 纳秒乘上去就是毫秒。但一个 1 kHz 的回路每秒只进出队列 3000 次，2 纳秒乘 3000 是 6 微秒，占周期的 0.6%。

真正值钱的是另外两个决定：**队列深度**和**批量**。这两个错了，落后 341 毫秒；对了，落后 0.5 毫秒。锁的事，量完就知道可以先放下。


九、回到标题

"拆分数据接收、决策和日志任务，避免互相阻塞"，落到四个数上：

**一个循环做四件事，工作量是加法。** 52 → 57 → 136 → 583 微秒。控制算法本身只要 50 微秒，占 5.2%；加上日志之后占空比 58.3%，93% 的时间在等磁盘。

**拆成四个线程，控制回到 50 微秒。** 迟到中位数 0.1 微秒。但拆分不产生并行，核才有：四个线程挤在一个核上，p99 从 437 微秒变成 2743 微秒，丢拍从 32 次变成 137 次。

**队列把同步换成异步，第一个后果是数据变旧。** 64 条的队列、2 kHz 的传感器，每拍取一条是 32 毫秒的数据龄——1 kHz 的回路喂 31 Hz 的数据。消费者必须排空，才能回到 991.8 微秒。

**异步不解决吞吐。** 产量 3000 行/秒，消费 2614 行/秒，队列一定涨。涨起来只有三条路：丢旧、丢新、或者让消费者变快。前两条各丢 1800 条左右，第三条丢 0 条。

一句话：多线程解决的是"谁在等"，不解决"谁慢"。把慢的挪到别的线程，你的快循环就不等它了——但慢的还是那么慢，它只是开始积压。积压的那一头，你得自己决定丢什么。
