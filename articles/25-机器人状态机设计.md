机器人状态机设计

—— 六个决定，一张表（1.7）


一、先看那段 if

待机、运行、避障、停止、故障。五个状态，第一次写的时候几乎都是这样：

    static int naive_state(float d, int running, int estop)
    {
            if (estop)
                    return ST_FAULT;
            if (d < 0.45f)
                    return ST_AVOID;
            if (running)
                    return ST_RUN;
            return ST_IDLE;
    }

每拍调用一次，状态从输入重新算出来。能跑，大多数时候也对。

问题不在逻辑，在结构。看参数表：`d` 是雷达给的，`running` 是上层给的，`estop` 是按钮给的——**三个输入，没有一个是"我现在在哪"**。所以它算出来的不是"下一步去哪"，而是"现在看起来像什么"。

这两个不是一回事。前者需要记住上一步，后者不需要。这段代码选择不记，于是三件事跟着没了：

一，没有"从哪来"。于是"只能从故障复位退出"这种规则写不出来——它要判断上一条边是从哪儿来的。

二，没有地方放时间。想加一句"进了避障至少待 300 毫秒"，没有变量挂。

三，没有"允许不允许"。任何输入组合都会算出一个状态，包括那些根本不该发生的。

所以状态机要补回来的，正好是这三样：

    uint8_t state;              /* 一个变量：现在在哪 */
    const struct rule TBL[];    /* 一张表：允许走哪些边 */
    int fsm_step(...);          /* 一个函数：查表，走过去 */

一个变量、一张表、一个函数。下面六节就是把这三样东西定下来，每一节做一个决定。


二、第一步：定状态

状态怎么划，判据只有一条：**每个状态对应一个对外承诺。**

两个状态对外做的事一模一样，就该合并；有一件事只在某个状态里做，它就该独立。用这条判据过一遍：

BOOT——上电到第一次复位之间。承诺是"轮子不转，等自检"。为什么不并进 IDLE？因为 IDLE 接受"开始指令"，而自检没过的时候上层发开始指令不该被接受。分成两个状态，这条规则自动就成立了，不用写判断。

IDLE——待机。接受开始，不接受障碍事件。车没动，前方有没有东西无所谓。

RUN——运行，速度 0.30 m/s。

AVOID——避障，速度 0.10 m/s。为什么不并进 RUN、用一个速度变量表示？因为 AVOID 要接受"障碍解除"才回 RUN，RUN 不接受。**两条边的入口不同，就是一个状态。**

STOP——任务正常结束，或者上层叫停。它和 IDLE 都是停着的，但 STOP 的意思是"这一趟干完了"，下一趟要重新开始；IDLE 的意思是"还没开始"。日志和上层状态显示要区分这两件事，所以是两个状态。

FAULT——急停、驱动器报错、越界。承诺是"使能关掉，只能复位退出"。

写下来是这样：

    enum rb_state {
            ST_BOOT = 0,
            ST_IDLE,        /* 待机：上电了，还没收到开始指令 */
            ST_RUN,         /* 运行：正常执行任务 */
            ST_AVOID,       /* 避障：前方有东西，降速绕行 */
            ST_STOP,        /* 停止：任务正常结束，或者上层叫停 */
            ST_FAULT,       /* 故障：急停、驱动器报错、越界。只能复位退出 */
            ST_N
    };

五个状态加一个哨兵。哨兵 `ST_N` 不是状态，是数组长度——下面每个"每状态一个"的数组都靠它开。

注意这里没有"急停状态"和"驱动器故障状态"两个。它们在对外承诺上是同一个：关使能、等复位。分成两个，就要写两遍同样的进入动作，还要写两遍"只能复位出去"。**承诺相同的状态合并，承诺不同的状态分开**，这条判据两头都用。


三、第二步：状态里存什么

原则：**每个字段都要被一个具体功能逼出来，说不出被谁用的字段不要加。**

    struct rb_fsm {
            uint8_t state;
            uint64_t t_enter;       /* 进入当前状态的时刻 */
            uint64_t hold_until;    /* 在这之前不许走（除非 urgent） */
            uint32_t n_trans;
            uint32_t n_reject;      /* 表里没有这条边，被拒了几次 */
            float v_cmd;            /* 进入动作算出来的速度指令 */
            uint8_t n_enter[ST_N];  /* 每个状态进了几次 */
            uint16_t edge[ST_N][EV_N];      /* 每条边走过了几次 */
    };

八个字段，逐个交代来路：

`state` 是唯一必须有的——它就是第一节缺的那个"我现在在哪"。

`t_enter` 记进入时刻。用来回答"在这个状态待了多久"，日志要打这个数。

`hold_until` 记驻留截止时刻。**注意它是"到什么时候为止"，不是"已经待了多久"。** 存绝对时刻，判断就变成一次比较 `now < hold_until`，不用每拍做减法，也不用担心时钟跳变。

`n_trans` 和 `n_reject` 一对。前者是总转换次数，后者是被表拒掉的次数。`n_reject` 是给调试用的：它一直涨，说明上层在发这个状态不该收的事件——**问题在上层，不在状态机**。没有这个数，这种情况只会表现成"车不动"，查起来要好几天。

`v_cmd` 是进入动作算出来的速度指令。它是"进入动作"和"每拍计算"的分界线：速度只在转换那一刻算一次，之后每一拍读它。第七节专门讲这条。

`n_enter[ST_N]` 和 `edge[ST_N][EV_N]` 是统计。后者第九节还会用到——它不光是统计，还是一张覆盖表。


四、第三步：事件从哪来

表只认离散事件。传感器给的是浮点数。中间得有一层做翻译，这一层八行：

    int rb_event_from(float d, int state, float near, float clear)
    {
            if (state == ST_RUN && d < near)
                    return EV_OBSTACLE_NEAR;
            if (state == ST_AVOID && d > clear)
                    return EV_OBSTACLE_CLEAR;
            return EV_NONE;
    }

三个设计点，每个都值得单独说。

**第一，它要 `state` 这个参数。** 同样的距离，在 RUN 里是"有障碍"，在 AVOID 里什么都不是，在 IDLE 里也什么都不是。所以事件不是距离的函数，是（距离，当前状态）的函数。少了这个参数，就只能在表外面再补一堆判断。

**第二，两个阈值，不是一个。** 0.40 进、0.55 出，中间那十五厘米是迟滞带。为什么必须两个：距离在阈值附近抖 ±2 厘米，一个阈值就会每拍翻一次——这一条的效果在第八节有数。

**第三，迟滞放在这一层，不放进表。** 表只认离散事件，它不知道"距离"是什么，也不需要知道。换传感器——超声换激光、换视觉——只改这八行，表一行不动。

这一条是分层的全部意义：**表是业务规则，这八行是传感器适配。** 混在一起，换一个雷达就要改表，而改表就要重新想一遍"故障能不能被障碍顶掉"这种问题。


五、第四步：表怎么写

一行规则四个字段：

    struct rule {
            uint8_t from;
            uint8_t ev;
            uint8_t to;
            uint16_t hold_ms;       /* 进入 to 之后至少待这么久 */
    };

从哪来、什么事、到哪去，加一个"到了之后至少待多久"。整张表十五行：

    static const struct rule TBL[] = {
            { ST_BOOT,  EV_RESET,          ST_IDLE,    0   },
            { ST_BOOT,  EV_ESTOP,          ST_FAULT,   0   },
            { ST_IDLE,  EV_CMD_START,      ST_RUN,     100 },
            { ST_IDLE,  EV_ESTOP,          ST_FAULT,   0   },
            { ST_RUN,   EV_OBSTACLE_NEAR,  ST_AVOID,   0   },
            { ST_RUN,   EV_CMD_STOP,       ST_STOP,    0   },
            { ST_RUN,   EV_ESTOP,          ST_FAULT,   0   },
            { ST_RUN,   EV_FAULT,          ST_FAULT,   0   },
            { ST_AVOID, EV_OBSTACLE_CLEAR, ST_RUN,     0   },
            { ST_AVOID, EV_CMD_STOP,       ST_STOP,    0   },
            { ST_AVOID, EV_ESTOP,          ST_FAULT,   0   },
            { ST_AVOID, EV_FAULT,          ST_FAULT,   0   },
            { ST_STOP,  EV_CMD_START,      ST_RUN,     100 },
            { ST_STOP,  EV_ESTOP,          ST_FAULT,   0   },
            { ST_FAULT, EV_RESET,          ST_IDLE,    500 },
    };

十五行，三件事说清楚了这个设计。

**一，`hold_ms` 挂在入边，不挂在出边。** `{ ST_IDLE, EV_CMD_START, ST_RUN, 100 }` 的意思是"进 RUN 之后至少待 100 毫秒"。也可以挂在出边上——"RUN 出去的所有边都等 100 毫秒"——但那样每多一个来源状态就要重写一遍，而且容易漏。挂在入边只写一次，所有进 RUN 的路径都管住。

**二，FAULT 只有一个出口。** `from` 是 `ST_FAULT` 的行只有最后一行。没有 `EV_CMD_START`，没有 `EV_OBSTACLE_NEAR`，也没有 `EV_CMD_STOP`。所以"故障状态不会被上层重发开始指令顶掉"这句话，**不需要写任何判断代码**——它是表里没有这一行。这就是第一节说的"补回允许不允许"。

**三，为什么用静态表，不用 switch。** switch 也能写，每个 case 里一串 if。区别在可数：switch 的边散在代码里，要数"一共允许几条边"得从头读一遍；表是数据，`sizeof TBL / sizeof TBL[0]` 就是边的条数，能打印、能遍历、能拿去做测试清单。

还有一个小地方：表里的 `hold_ms` 是设计值，代码里另外留了一个 `g_hold[]` 覆盖数组，`fsm_set_hold(ST_AVOID, 300)` 就能把驻留改成 300 毫秒，不用改表重编译。**设计值留在表里，实验值走旁路**——第八节的对照全靠它。


六、第五步：查表函数

    int fsm_step(struct rb_fsm *f, int ev, uint64_t now)
    {
            int urgent = g_urgent && (ev == EV_ESTOP || ev == EV_FAULT);
            uint32_t hold;
            int i;
            if (ev <= EV_NONE || ev >= EV_N)
                    return 0;
            for (i = 0; i < NTBL; i++) {
                    const struct rule *r = &TBL[i];
                    if (r->from != f->state || r->ev != ev)
                            continue;
                    /* 驻留期没到就不许走——但安全事件不走这条 */
                    if (!urgent && now < f->hold_until)
                            return 0;
                    hold = (g_hold[r->to] >= 0) ? (uint32_t)g_hold[r->to] : r->hold_ms;
                    f->edge[f->state][ev]++;
                    f->state = r->to;
                    f->hold_until = now + (uint64_t)hold * 1000000ull;
                    on_enter(f, r->to, now);
                    f->n_trans++;
                    return 1;
            }
            f->n_reject++;
            return 0;
    }

二十五行，四个设计点。

**一，没匹配上就返回 0，不兜底。** 循环走完没找到，`n_reject++`，状态不变。这是整个设计里最重要的一处：**状态机不该有默认动作。** 一串 if 的最后一行 `return ST_IDLE;` 就是默认动作——它把所有没想到的输入组合都送进 IDLE，包括那些本该报错的。默认动作让错误变成"看起来正常的错误状态"，这是最难查的一类 bug。

**二，驻留检查夹在"匹配上"和"走过去"中间。** 位置很关键。放循环外面，等于所有事件都被拦；放到匹配之前，就分不清"没这条边"和"有边但还在驻留"——这两种情况的日志含义完全不同，一个是上层发错了，一个是上层发早了。夹在中间，语义正好是"这条边存在，但现在还不能走"。

**三，`urgent` 在函数入口算一次。** 不是每条边各自判断。因为"安全事件绕过驻留"是一条全局规则，不是某条边的属性。放在入口，以后加一个安全事件只改这一行。

**四，`on_enter()` 是单独的函数，不内联在循环里。** 下一节讲为什么。


七、第六步：进入动作

    static void on_enter(struct rb_fsm *f, int s, uint64_t now)
    {
            switch (s) {
            case ST_RUN:
                    f->v_cmd = 0.30f;
                    break;
            case ST_AVOID:
                    f->v_cmd = 0.10f;
                    break;
            default:                /* BOOT / IDLE / STOP / FAULT */
                    f->v_cmd = 0.0f;
                    break;
            }
            f->t_enter = now;
            f->n_enter[s]++;
    }

它被 `fsm_step()` 调用，位置在 `f->state = r->to;` 之后，所以它看到的是新状态。

**它是"进入动作"，不是"状态行为"。** 区别只有一条：执行次数。进入动作一次转换执行一次；状态行为每一拍执行一次。

这就是 if 链和状态机的根本差别，一句话：

**if 链只有点，状态机有边。**

一串 if 里，`if (d < 0.45f) return ST_AVOID;` 每一拍都算一次"该降速了"。于是每一拍都要重新决定一次，每一拍都可能决定得不一样。状态机里，`v_cmd = 0.10f` 只在 RUN→AVOID 那条边上执行一次，之后九百九十九拍都只是读这个值。

一次和一千次的差别，在指令条数上可以忽略。差别在**语义**：一次意味着"这个决定发生在某一刻"，可以打时间戳，可以回答"是谁、什么时候让它降速的"；每拍算一次意味着这个决定没有时刻，出了问题只能反推。

真机上进入动作还要做别的事：AVOID 要清掉上一段规划、FAULT 要关使能、IDLE 要把里程计归零。这些都必须是一次。规划每拍清一次，就永远清不干净——你会得到一辆"看着在跑、其实一步没走"的车。


八、跑起来：设计带来什么

代码在 `robot-brain/fsm/`，结果在 `robot-brain/results/fsm-run.txt`。前三个程序都用模拟时间（第 i 拍就是 i 毫秒），不读墙上时钟，所以跑多快都一样，两次跑出来的数一个不差；`bench` 量的是真耗时，取的是多次运行里稳定的那一组。

**（一）迟滞和驻留，各挡住多少**

五个 150 毫秒的坑，间隔 200 毫秒，距离噪声 ±2 厘米，1 kHz 跑 6 秒共 6000 拍。三套配置并排：

| 配置 | 状态翻转 | 进入避障 | 避障占比 | 平均速度 |
|---|---|---|---|---|
| 单阈值 0.45，无驻留 | 60 次 | 29 次 | 7.4% | 0.285 m/s |
| 双阈值 0.40/0.55，无驻留 | 12 次 | 5 次 | 8.5% | 0.283 m/s |
| 双阈值 + 驻留 300 毫秒 | 8 次 | 3 次 | 19.8% | 0.260 m/s |

第一行先说结论：单阈值翻 60 次、进避障 29 次，而实际只有五个坑——**一个坑被拆成了差不多六次**。

第二行是加了迟滞的结果。翻转从 60 降到 12，进避障从 29 降到 5，正好等于坑的个数。而平均速度几乎没变，0.285 到 0.283。迟滞没有让车变慢，它只是让车不再犹豫。

第三行又加了 300 毫秒驻留。进入次数再压到 3 次，代价是避障占比从 8.5% 涨到 19.8%，平均速度掉到 0.260。**驻留不是免费的**：它保证"进去就待够"，代价是"该出来的时候也得多待"。所以驻留时间要按最长的真实避障动作来定，不能拍脑袋。

**（二）表里没有的边，走不走得过去**

七步事件序列，两种写法并排。四个时刻不一致：

| 时刻 | 发生了什么 | 表驱动 | if 链 |
|---|---|---|---|
| 0.60 秒 | 急停松开，没人复位 | FAULT | RUN |
| 1.00 秒 | 上层重发开始 | FAULT | RUN |
| 1.50 秒 | 前方出现障碍 | FAULT | AVOID |
| 2.00 秒 | 有人按了复位 | IDLE | RUN |

每个不一致，都是 if 链多走了一步表里没有的边：FAULT→RUN、FAULT→AVOID。这些边在表里不存在，所以表驱动拒绝了 2 个事件，if 链一个都没拒——**它没有"拒绝"这个概念**。

最后一行最值得看。2.00 秒有人按复位，表驱动回到 IDLE，if 链还是 RUN。因为 `RESET` 在 if 链里根本不是一个输入，它没有地方放。这就是第一节说的"没有从哪来"：不记状态，就没有"复位"这个动作的落点。

**（三）驻留期里按了急停**

t=100 毫秒进 AVOID（驻留 300 毫秒），t=101 毫秒按下急停。

| 配置 | 进 FAULT 的时刻 | 比按下晚 |
|---|---|---|
| 安全事件绕过驻留 | 第 101 毫秒 | 0 毫秒 |
| 安全事件不绕过 | 第 400 毫秒 | 299 毫秒 |

多等的 299 毫秒里，车以 0.10 m/s 又走了 3.0 厘米，以 0.30 m/s 是 9.0 厘米。

这是整个设计里唯一一处"规则要开例外"。驻留是为了防抖，防抖的对象是传感器的犹豫，不是人的手。**急停和故障必须能穿过任何等待**——所以它在 `fsm_step()` 入口就被算成 `urgent`，一路跳过驻留检查。

**（四）查表值多少钱**

| 情形 | 耗时 |
|---|---|
| 15 条边全不匹配 | 19.0 ns |
| 第 5 条边命中（含进入动作） | 10.7 ns |
| 一串 if，从输入直接算状态 | 1.2 ns |

查表和 if 链差 19.0 − 1.2 = 17.8 ns。1 kHz 跑一秒是一千拍，加起来 17.8 微秒，占 1.8%。

这个开销不值得讨论。值得讨论的是那 1.2 ns 的 if 链——它快，是因为它什么都没记。**省下的那点时间，是用"没有状态、没有边、没有拒绝"换来的。**


九、回到标题

六个决定，一句话一个：

一，状态是一个变量，不是每拍算出来的结果。
二，每个状态对应一个对外承诺，承诺一样就合并，不一样就分开。
三，状态里每个字段都要被一个具体功能逼出来。
四，传感器到事件之间有一层翻译，迟滞住在那里，不在表里。
五，允许的边写成表，表里没有的边不许发生，也不兜底。
六，进入动作一次转换执行一次，它标记"决定发生在哪一刻"。

最后还有一个能直接用的东西：`edge[ST_N][EV_N]` 那个数组。跑完一趟打印出来，就是"哪些边走过了"。这一趟跑了 4 条，表里一共 15 条，剩下 11 条没走过。

那 11 条就是测试清单——**状态机的测试用例可以从表里生成**，一串 if 生成不出来，因为它没有表。这是表驱动在工程上最实在的好处，比"好维护"这种说法具体得多。
