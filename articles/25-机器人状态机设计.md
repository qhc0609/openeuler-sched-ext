机器人状态机设计

—— 五个状态、一张表，和两条驻留规则（1.7）


一、一串 if

待机、运行、避障、停止、故障。第一版几乎都是这么写的：

    static int naive_state(float d, int running, int estop)
    {
            if (estop)
                    return ST_FAULT;
            if (d < 0.45f)
                    return ST_AVOID;
            if (running)
                    return ST_RUN;
            return ST_IDLE;
    }

每拍调用一次，状态从输入重新算出来。

这段代码能跑，大部分时候也对。它的问题不在逻辑，在**结构**：状态不是"记住"的，是每拍现算的。于是"状态"这个词在这里其实不存在——存在的是一个从输入到输出的映射。

后果有三个，都要等出事才露出来：

1. 阈值附近，状态每毫秒翻一次。
2. 故障状态会被别的东西顶掉。
3. 你想加一条"进来之后至少待一会儿"，没有地方放。

这一篇把这三种情况各跑一遍，量出来。


二、五个状态，一张表

把状态变成真正被记住的东西：

    enum rb_state {
            ST_BOOT = 0,
            ST_IDLE,        /* 待机：上电了，还没收到开始指令 */
            ST_RUN,         /* 运行：正常执行任务 */
            ST_AVOID,       /* 避障：前方有东西，降速绕行 */
            ST_STOP,        /* 停止：任务正常结束，或者上层叫停 */
            ST_FAULT,       /* 故障：急停、驱动器报错、越界。只能复位退出 */
            ST_N
    };

转换写成一张表。每一行是"从哪、收到什么、到哪、进去之后至少待多久"：

    struct rule {
            uint8_t from;
            uint8_t ev;
            uint8_t to;
            uint16_t hold_ms;       /* 进入 to 之后至少待这么久 */
    };

表的一部分：

    { ST_AVOID, EV_OBSTACLE_CLEAR, ST_RUN,     0   },
    { ST_AVOID, EV_CMD_STOP,       ST_STOP,    0   },
    { ST_AVOID, EV_ESTOP,          ST_FAULT,   0   },
    { ST_AVOID, EV_FAULT,          ST_FAULT,   0   },
    { ST_STOP,  EV_CMD_START,      ST_RUN,     100 },
    { ST_STOP,  EV_ESTOP,          ST_FAULT,   0   },
    { ST_FAULT, EV_RESET,          ST_IDLE,    500 },

看最后一行。FAULT 这一行**只有一个出口**：`EV_RESET`。没有 `EV_CMD_START`，没有 `EV_OBSTACLE_NEAR`，没有 `EV_CMD_STOP`。

这就是这张表最重要的性质：**表里没有的边，就是不许发生的边。** 不是"没实现"，是"不许"。

查表的循环十几行：

    for (i = 0; i < NTBL; i++) {
            const struct rule *r = &TBL[i];
            if (r->from != f->state || r->ev != ev)
                    continue;
            /* 驻留期没到就不许走——但安全事件不走这条 */
            if (!urgent && now < f->hold_until)
                    return 0;
            hold = (g_hold[r->to] >= 0) ? (uint32_t)g_hold[r->to] : r->hold_ms;
            f->edge[f->state][ev]++;
            f->state = r->to;
            f->hold_until = now + (uint64_t)hold * 1000000ull;
            on_enter(f, r->to, now);
            f->n_trans++;
            return 1;
    }

走完一圈没匹配上，返回 0，状态不动。整个状态机就是这张表加这十几行。

下面三个实验，量的都是这张表带来的东西。


三、第一个坑：阈值附近，状态会翻

场景：一条直线走廊，五个人先后从车前面横穿过去。传感器报的距离是分段线性的，叠了 ±2 cm 的噪声（1 cm 分辨率加抖动）。每个坑只持续 150 ms，坑和坑之间隔 200 ms。

1 kHz，跑 6 秒，共 6000 拍。三种配置：

| 配置 | 状态翻转 | 进入避障 | 避障时间占比 | 平均速度 |
|---|---|---|---|---|
| A 单阈值 0.45 / 0.45，无驻留 | 60 次 | 29 次 | 7.4% | 0.285 m/s |
| B 双阈值 0.40 进 / 0.55 出 | 12 次 | 5 次 | 8.5% | 0.283 m/s |
| C 双阈值 + 驻留 300 ms | 8 次 | 3 次 | 19.8% | 0.260 m/s |

五个坑，A 进了 29 次避障。

原因很简单：阈值 0.45 上下，噪声 ±2 cm，信号每穿过一次阈值就进一次避障。而"进一次避障"不是改一个变量——进入动作要减速到 0.10、清掉上一段规划、把避障计时器归零。29 次就是 29 次减速、29 次清规划。

B 把间隙拉开到 0.15 米（0.40 进、0.55 出）。噪声 ±0.02 是间隙的 1/7.5，穿不过去。于是五个坑，五次，一次不多。

这叫迟滞。它解决的问题是**噪声**。

C 再往前一步：进了避障，至少待 300 毫秒。坑间距是 200 毫秒，比驻留短，于是相邻的几个坑被合成同一次避障——5 次变成 3 次。

它解决的问题不是噪声，是"**刚退出来又要进去**"。

代价在最后两列。C 的避障时间占比 19.8%，B 是 8.5%——多出来的 11 个百分点，是"明明已经安全了，但驻留期还没满，不许走"。平均速度从 0.283 掉到 0.260 m/s。

驻留不是白拿的。300 毫秒这个数，直接换成"每次避障多花多少时间"，再乘上你一秒要避多少次障。


四、第二个坑：故障会被别的东西顶掉

一段七步的事件序列，两种写法并排跑：

| 时间 | 事件 | 表驱动 | if 链 |
|---|---|---|---|
| 0.00 | RESET | IDLE | IDLE |
| 0.10 | START | RUN | RUN |
| 0.50 | ESTOP | FAULT | FAULT |
| 0.60 | 急停松开，没人复位 | FAULT | **RUN** |
| 1.00 | 上层重发 START | FAULT（拒） | RUN |
| 1.50 | 前方出现障碍 | FAULT（拒） | **AVOID** |
| 2.00 | 有人按了复位 | IDLE | **RUN** |

前三个时刻两边一模一样。从第四个开始，全部不一致。

**0.60 秒：急停一松开，if 链自己回到了运行。** 因为 `estop` 是个电平，松开就变成 0，下一拍算出来就是 `running ? RUN : IDLE`。故障状态在它那里不是一个"状态"，是一个"当且仅当急停按着时成立的条件"。急停一松，故障就消失了——不需要任何人复位。

**1.50 秒：障碍物把故障顶掉了。** `d < 0.45` 这一条排在 `running` 前面，于是只要前方有东西，`naive_state` 就返回 AVOID。车从故障里自己爬出来，还顺手进了避障模式。

**2.00 秒：复位按钮对它完全无效。** `RESET` 是个事件，而 if 链不看事件，只看电平。按下去没有任何反应，车还在 RUN。

表驱动这边，`RESET` 之外的事件全部被拒——一共拒了 2 个。

这两个数字放在一起看：**表驱动拒绝了 2 个事件，if 链在这 2 个事件上都走了。**


五、第三个坑：驻留期会把急停放过去

驻留是好东西，但它也会保护住一条本来该立刻走的边：急停。

时间线：t = 0 进运行（运行状态本身也有 100 ms 驻留），t = 100 ms 前方出现障碍，进避障，驻留到 400 ms；t = 101 ms 有人按下急停。

| | 进 FAULT 的时刻 | 比按下晚 |
|---|---|---|
| 安全事件绕过驻留 | 101 ms | 0 ms |
| 安全事件不绕过 | 400 ms | 299 ms |

差 299 毫秒。这 299 毫秒里车还在走：避障速度 0.10 m/s 是 3.0 厘米，运行速度 0.30 m/s 是 9.0 厘米。

一次急停被推迟了 0.3 秒，因为你自己写的"至少待 300 毫秒"。

所以查表循环里那一行不是可选的：

    int urgent = g_urgent && (ev == EV_ESTOP || ev == EV_FAULT);

安全事件不走驻留。这一位写漏了，测试里跑不出来——因为测试通常不会在刚进避障的 1 毫秒内按急停。它只在真实事故里出现，而且每次都出现在最不该出现的时候。


六、查表值多少钱

| | 每次 |
|---|---|
| 扫完整张表，15 条边全不匹配 | 16.9 ns |
| 第 5 条边命中（含进入动作） | 11.7 ns |
| 一串 if，从输入直接算状态 | 1.2 ns |

查表比 if 链多花 15.7 纳秒。1 kHz 的回路一秒查 1000 次，多花 15.7 微秒，占 1 毫秒周期的 1.6%。

**不值得为了这点性能选 if 链。** 这张表买的是"表以外的边不许发生"，不是速度。

（顺便说一个坑：第一版 `bench.c` 量出来两个数都不到 2 纳秒，if 链还比查表快——因为输入全是常量，`-O2` 把整段算成了常数。把输入改成 `volatile` 才量到真数。任何"快得不像话"的微基准，先怀疑这一条。）


七、回到标题

"实现待机、运行、避障、停止、故障等状态及转换条件"，落到四句话：

**状态要记住，不能每拍重算。** if 链里没有状态，只有从输入到输出的映射。所以它拦不住任何东西——急停松开车就复活，障碍物能把故障顶掉，复位按钮对它没有意义。

**转换写在表里，表外一律拒绝。** FAULT 只有一个出口 `EV_RESET`，这是写死在表里的，不是靠"我记得别处不要跳"。这一趟测试里表驱动拒了 2 个事件，if 链两个都走了。

**迟滞管噪声，驻留管"退出来又进去"。** 五个坑：单阈值进 29 次，双阈值进 5 次，加 300 ms 驻留进 3 次。代价是避障时间从 8.5% 涨到 19.8%，平均速度从 0.283 掉到 0.260 m/s。

**安全事件必须绕过驻留。** 不绕过，一次急停被推迟 299 毫秒，车多走 3.0 厘米（避障速度）到 9.0 厘米（运行速度）。

还有一条不是数字的：这张表能当测试清单用。表里一共 15 条边，这一趟测试只走了 4 条——`BOOT→IDLE`、`IDLE→RUN`、`RUN→FAULT`、`FAULT→IDLE`。剩下 11 条没测过，一条一条列得出来。

一串 if 没有这张清单。你能凭想象列测试用例，但列不全——因为"有哪些转换"这件事，在代码里根本没有被写下来。
