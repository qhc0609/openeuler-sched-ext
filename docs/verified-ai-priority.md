# 实测记录：AI 推理任务在 CPU 竞争下的调度延迟

测量时间：2026-10-25
测量机器：VMware 虚拟机，openEuler 24.03 LTS SP4 用户态 + 自编 6.12.0 内核
CPU：4 vCPU

这份记录的目的是让结论可复核。下面每个数字都来自仓库里的脚本，
命令写在最后，任何人都能在自己的机器上重跑一遍。

---

## 一、实验条件

| 项目 | 值 |
|---|---|
| 内核 | 6.12.0（kernel.org 原版，非发行版） |
| vCPU | 4 |
| 压测线程 | 8（= 2 × 核数） |
| 请求间隔 | 10 ms |
| 每轮请求数 | 1200 |
| 每组重复 | 3 轮 |
| 推理负载 | 128→256→64 MLP，每请求 16 次前向 |
| 调度器 | `scheds/ai_prio.bpf.c`，AI 时间片 20 ms，普通 3 ms |

三组：

- **A CFS** — 不挂任何调度器
- **B ai_prio 不踢** — `--kick 0`，只做队列优先
- **C ai_prio 踢** — `--kick 1`，队列优先 + 唤醒即抢占

## 六、调度器计数器（带负载，kick=1）

```
ai_enq=369   other_enq=1315   kick=369   ai_pick=369
```

三个 369 相等，说明：

- 每次推理任务入队都触发了踢核
- 每次入队都从 AI 队列被取走，没有漏进普通队列

## 七、sysfs 状态（同一次运行）

```
root/ops    = ai_prio
state       = enabled
nr_rejected = 0
```

退出后：

```
root/ops    = (空)
state       = disabled
```

即调度器注销后任务回到 CFS，不需要重启。

---

## 八、怎么读这些数字

**p50 是最可信的指标。** 两次独立运行给出的 p50 几乎相同，说明它反映的是稳定状态。
p99 在不同轮次之间差到一个数量级（CFS 组 35 ms 到 280 ms），原因是 4 vCPU 的虚拟机上
宿主调度、IO 抖动都会影响，p99 只取最差的 1%，单次事件就能把它推上去。

**结论应该写成量级，不是精确值。** 例如"p99 从几十毫秒降到十几毫秒"，
而不是"从 45 ms 降到 16 ms"。

**B 组 p50 比 CFS 还差，是必然结果。** 没有抢占时，调度器只能在一个任务用完时间片后
才拿回决策权；而 CFS 至少有唤醒抢占。队列优先级解决排序问题，不解决延迟问题。

**C 组 p99 没比 B 组好多少。** 三个原因：踢不进内核临界区、踢本身有上下文切换成本、
虚拟机时钟在宿主挂起 vCPU 时照走。想要压长尾要往隔离核和 CPU 亲和方向走，
不是换调度器能解决的。

## 九、复现

```bash
cd ai-engine
sudo ./run-demo.sh                      # 默认 3 轮，1200 请求
REPS=5 THREADS=12 REQUESTS=2000 sudo ./run-demo.sh
```

单独跑一组，不挂调度器：

```bash
cd ai-engine && make
./loadgen 8 30 &
./tiny_infer --requests 600 --interval-ms 10
```

单独挂调度器（`<pid>` 换成目标进程）：

```bash
cd scheds && make ai_prio ai_prio.bpf.o
sudo ./ai_prio ./ai_prio.bpf.o <pid> --kick 1
```
