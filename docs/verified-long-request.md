# 长请求实验记录：40 毫秒的请求，七种调度手段

这一份记录对应 `ai-engine/run-long.sh` 的一次完整运行。
它回答的问题和 `verified-scheduler-choice.md`（短请求，446 微秒）不同：

- 短请求测的是"唤醒之后多久拿到 CPU"，延迟量级在微秒，调度器是唯一变量；
- 长请求测的是"拿到 CPU 之后，别人还要等多久"，因为一个请求会连续占用一个核几十毫秒。

线上真正让人有感觉的是后者。

## 一、环境

| 项 | 值 |
|---|---|
| 内核 | 6.12.0（自建，`CONFIG_SCHED_CLASS_EXT=y`） |
| 机器 | VMware 虚拟机，4 vCPU |
| 压测线程 | 8（= 2 倍核数），每线程死循环做浮点运算 |
| 引擎请求 | 120 个，间隔 150 ms，每请求 1300 次前向（≈40 ms） |
| 旁观探针 | 400 个请求，间隔 40 ms，每请求 1 次前向（≈32 µs） |
| 重复轮数 | 3 |
| 引擎阈值 | 调度延迟 > 5000 µs 记一次超时 |
| 探针阈值 | 调度延迟 > 10000 µs 记一次超时 |

`1300` 次前向这个数是量出来的：空载下 400 次 12.2 ms、800 次 24.5 ms、1430 次 43.9 ms，
约 30.6 µs 一次前向，取 1300 得 40 ms。

## 二、七组

| 组 | 手段 | 说明 |
|---|---|---|
| `cfs` | 什么都不做 | 基线 |
| `nice` | `nice -n -20` | CFS 内部权重 88761，是 nice 0（1024）的 87 倍 |
| `fifo` | `chrt -f 50` | SCHED_FIFO，实时类，同一优先级内没有时间片 |
| `kick20` | `ai_prio --ai-slice-us 20000 --burst 0` | 分道 + 踢核，推理任务一次占 20 ms |
| `kick1` | `ai_prio --ai-slice-us 1000 --burst 0` | 同上，时间片缩到 1 ms |
| `kickb` | `ai_prio --ai-slice-us 1000 --burst 1` | 再加"连续占满 1 片必须让一次" |
| `kickbw` | 同上 + `--wake-boost 1` | 再加"普通任务唤醒时插队头并踢核" |

后四组是同一份代码，每级只改一个旋钮。

## 六、结论

1. **CFS 是真的不行，而且不只是延迟问题。** 引擎 p50 1484 µs（其它组 500 上下），
   18.3% 的请求超过 5 ms；更关键的是 `work_p50` 是 103 ms —— 40 ms 的活干了 103 ms，
   说明引擎在这台机器上只拿到约 39% 的一个核。请求一多就跟不上，
   这不是"某一次慢"，是算力被分走了。

2. **`nice -n -20` 一条命令就把两条线都拉回来了。** 引擎 4.7%、旁观 3.2%，
   是七组里唯一两边都低于 5% 的。

3. **`chrt -f 50` 的 p50 最好（497），超时反而比 nice 多（7.2%）。**
   实时类没有时间片，一个请求占住核就是 40 ms，尾部的代价补不回中位数的收益。

4. **自己写的调度器第一版把旁观任务拖坏了 10 倍。** `kick20` 引擎超时 3.1%（七组最好），
   但旁观 p50 从 542 µs 涨到 5578 µs。原因：换掉 CFS 就等于拆掉了它的唤醒抢占
   和按 vruntime 排序，普通任务只能排在压测线程后面等。

5. **缩短时间片没用，加"让一次"也没用，补上"唤醒插队头 + 踢核"才有用。**
   `kick20` → `kick1`：旁观 8.2% → 15.0%（更差）；`kick1` → `kickb`：13.0%（还是差）；
   `kickb` → `kickbw`：3.8%（回来了）。

6. **补完之后追平了 nice，但没有赢。** `kickbw` 引擎 6.1%、旁观 3.8%，
   合计 9.9%；`nice` 合计 7.9%。253 行 BPF 输给了一条 `nice` 命令。

## 七、这份数据的边界

- **虚拟机噪声。** `max` 一列里有 100 ms 以上的值，七组都出现过，
  包括 CFS。这是宿主机拖的，不是调度器。所以结论用的是"超阈值比例"和 `p50`，
  不用 `p99` —— 120 个样本的 p99 就是最大值，一个噪声点就能把排序翻过来。
- **只有一个被优待的进程。** 多线程引擎要把每个 tid 都配进去，
  这份实现只认一个 pid。
- **4 核。** 核越多，8 个压测线程的争抢越分散，绝对数值都会变；
  相对排序不一定变，但没测过的不写。
- **`nice -n -20` 需要 root。** 普通用户能用的范围是 −20 到 19 里被
  `RLIMIT_NICE` 允许的那一段，容器里通常拿不到负值。这一条会改变结论：
  拿不到负 nice 的时候，`nice` 这条路直接不成立。

## 八、附录：空载基线为什么不能用

上面所有结论都来自压满负载的七组。空载跑同一条命令，得到的是另一回事，
这一节把它记下来，免得有人拿空载数据当基线。

## 九、附录：`sleep-over.c` —— 绝对睡眠晚多少

`ai-engine/sleep-over.c` 只做一件事：`clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME)`
睡到目标时刻，醒来记 `now - target`。间隔 150 ms，单位微秒。

绑在 cpu0 上，同一台机器跑两次：

```
$ taskset -c 0 ./sleep-over 15
2433 8956 9474 8903 10423 62708 4551 2667 4235 7791 1819 10667 9829 10152 2238

$ taskset -c 0 ./loadgen 1 10 &      # cpu0 上放一个空转线程
$ taskset -c 0 ./sleep-over 15
996 625 361 892 770 1085 376 901 109 303 648 305 880 67 543
```

核空闲：2–10 ms。核上有活：0.07–1.1 ms。同一台机器、同一个程序、同一个核，
差别只在那个核睡不睡。

不绑核时也一样，8 线程压满的对照组：

```
2169 12218 146 459 155 380 372 206 1038 873 691 128 667 438 313 360 1078 442 205573 56659
```

中位数几百微秒，少数几个点被压测线程自己拖长。

**结论：这台虚拟机上，空闲 vCPU 的定时器唤醒成本是毫秒级，忙着的 vCPU 是百微秒级。**
所以「调度延迟」这个指标只能在压满负载时读；空载读到的数字是虚拟化的开销，
和内核挑哪个任务没有关系。这也是整套实验坚持七组同负载、三轮取中位数的原因。
