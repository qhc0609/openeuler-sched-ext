# 什么时候**必须**用 sched_ext：五组对照记录

这一份记录对应 `ai-engine/run-sla.sh` 的一次完整运行（3 轮）。

它回答的问题和 `verified-long-request.md` 不一样：

- 那一份问的是"能不能让推理任务快一点"，答案是 `nice -n -20` 就够了；
- 这一份问的是"**快**和**不霸占**能不能同时要"，答案是只有 sched_ext 能。

区别在于多了一个观测量：**单次连续占核时长**。
调度延迟是"该跑 → 真跑"，占核时长是"真跑 → 被换下"。
前者是引擎自己的体感，后者是同核上别人的体感。
把优先级往上推，前一个降下去，后一个必然涨上来 —— 这两个量是互相拉扯的。

## 一、环境

| 项 | 值 |
|---|---|
| 内核 | 6.12.0（自建，`CONFIG_SCHED_CLASS_EXT=y`，ftrace 可用） |
| 机器 | VMware 虚拟机，4 vCPU |
| 压测线程 | 8（= 2 倍核数），每线程死循环做浮点运算 |
| 引擎请求 | 120 个，间隔 150 ms，每请求 1300 次前向（≈40 ms） |
| 旁观探针 | 400 个请求，间隔 40 ms，每请求 1 次前向（≈32 µs） |
| 重复轮数 | 3 |
| 引擎阈值 | 调度延迟 > 5000 µs 记一次超时 |
| 探针阈值 | 调度延迟 > 10000 µs 记一次超时 |

## 二、五组

| 组 | 手段 | 说明 |
|---|---|---|
| `cfs` | 什么都不做 | 基线 |
| `nice` | `nice -n -20` | CFS 内部权重 88761，是 nice 0 的 87 倍 |
| `fifo` | `chrt -f 50` | SCHED_FIFO，实时类，同一优先级内没有时间片 |
| `scx20` | `ai_prio --ai-slice-us 20000 --burst 0` | 分道 + 踢核，一次占 20 ms |
| `scxbw` | `--ai-slice-us 1000 --burst 1 --wake-boost 1` | 1 ms 时间片，占满让一次，唤醒插队头并踢核 |

`scx20` 和 `scxbw` 是同一份代码，只差三个参数。

## 三、占核时长是怎么量出来的

用 ftrace 的 `sched_switch`，只过滤引擎的 pid：

```
echo "prev_pid == $PID || next_pid == $PID" > \
    /sys/kernel/debug/tracing/events/sched/sched_switch/filter
```

`prev_pid` 和 `next_pid` 两个字段都要写。只写 `prev_pid` 只能拿到"被换下去"，
拿不到"被换上来"，配对就配不上。

引擎被换上来记 `t_in`，被换下去记 `t_out`，`t_out - t_in` 就是一次连续占核。

这个量引擎自己测不了：引擎只知道自己什么时候在算，不知道内核什么时候把它换下去。
它也没法从 `/proc/<pid>/schedstat` 里读出来 —— 那里只有累计运行时间，
没有"这一次跑了多久"。

## 五、引擎侧：单次连续占核时长（微秒）

| 组 | p50 | p90 | p99 | max | 超过 5 ms |
|---|---|---|---|---|---|
| `cfs` | 2990 | 3988 | 11060 | 158999 | 571/6988 8.2% |
| `nice` | 21382 | 46598 | 87085 | 228029 | 608/998 60.9% |
| `fifo` | 43599 | 52274 | 95755 | 274464 | 512/518 98.8% |
| `scx20` | 20219 | 22435 | 46934 | 151244 | 1167/1348 86.6% |
| `scxbw` | 1975 | 2131 | 8843 | 188161 | 502/11612 4.3% |

这张表是这一份记录的核心。

`cfs` 的 p50 是 2990 微秒 —— 这就是 CFS 时间片的量级，一个任务跑 3 毫秒换人。
`nice` 涨到 21382，`fifo` 涨到 43599。**优先级越高，内核越不愿意把你换下去**，
这不是副作用，是同一件事的两面。

`scx20` 是 20219，因为它的时间片就是 20 毫秒。
`scxbw` 把时间片压到 1 毫秒，占核回到 1975。

## 八、应用自己动手会怎样

在非 root、`RLIMIT_NICE=0` 的条件下（容器的默认状态），同一条命令的结果：

```
root    nice -n -20   -> nice=-20
root    chrt -f 50    -> policy=1
nobody  nice -n -20   -> nice=0   nice: 无法设置优先级: Permission denied
nobody  chrt -f 50    -> chrt: 设置 pid 0 的策略失败: Operation not permitted
```

`nice` 那一行要注意：它**没有失败退出**。`nice` 设不上优先级时照样把命令跑起来，
只是优先级没变。所以判断它有没有生效，不能看退出码，要看 `/proc/self/stat`
第 19 字段（nice）—— 上面那个 `nice=0` 才是实情。

`chrt` 会失败退出，退出码 1。

## 九、结论

按四条判据（调度延迟 p90 ≤ 5 ms、占核 p90 ≤ 5 ms、旁观 p50 ≤ 1.2 倍 CFS、吞吐 ≥ 95%）：

| 组 | 延迟 p90 | 占核 p90 | 旁观 p50 | 吞吐 | 全过 |
|---|---|---|---|---|---|
| `cfs` | 24287 ✗ | 3988 ✓ | 598 ✓ | 100% ✓ | ✗ |
| `nice` | 5684 ✗ | 46598 ✗ | 593 ✓ | 100% ✓ | ✗ |
| `fifo` | 5714 ✗ | 52274 ✗ | 597 ✓ | 99% ✓ | ✗ |
| `scx20` | 6788 ✗ | 22435 ✗ | 5796 ✗ | 96% ✓ | ✗ |
| `scxbw` | 3295 ✓ | 2131 ✓ | 631 ✓ | 95% ✓ | **✓** |

五组里只有 `scxbw` 全过。

1. **CFS 慢。** 引擎 p50 1499 微秒，其余四组 552–626；`work_p50` 102 毫秒，
   说明它只拿到 39% 的一个核。
2. **`nice` 和 `chrt` 用"霸占"换"快"。** 延迟下来了（626 / 558），
   占核涨到 21 / 44 毫秒，60.9% / 98.8% 的单次占核超过 5 毫秒。
3. **`scx20` 证明"分道"不够。** 它把引擎捞到了队头，但时间片 20 毫秒，
   旁观 p50 从 598 涨到 5796。
4. **`scxbw` 是唯一同时压住两头的。** 延迟 p90 3295、占核 p90 2131，
   两个都在 5 毫秒以内，旁观 p50 631（CFS 是 598）。
5. **应用自己拿不到权限。** 容器里 `nice` 和 `chrt` 都是 EPERM，
   所以"用 nice 调一下"这个方案在部署形态上就不成立。

## 十、这份数据的边界

- **虚拟机噪声。** 这一轮比 `verified-long-request.md` 那一轮吵：同一台机器上
  `cfs` 的旁观超时率从 4.3% 涨到 10.6%，`nice` 的引擎超时率从 4.7% 涨到 11.9%。
  宿主机负载不一样。所以判据用 p50 / p90 和中位数，跨轮只比相对关系，不比绝对值。
- **开了 trace。** 占核时长必须开 ftrace 才拿得到，trace 本身有开销。
  另跑了一轮关 trace 的对照：`nice` 633、`fifo` 494，和开 trace 的 626 / 558
  在噪声范围内，说明 trace 对延迟数据没有可测量的影响。
  那一轮的 `cfs` 组被宿主机负载污染（p50 236 毫秒），不参与比较。
- **4 核。** 核越多，8 个压测线程越分散，占核时长的绝对值会变。
- **单线程引擎。** 多线程引擎要按 tid 逐个配，这份实现只认一个 pid。
- **`scxbw` 的 1 毫秒时间片实测占核约 2 毫秒。** 名义值和实测值差一倍，
  机制没有查到底，只记录现象。
