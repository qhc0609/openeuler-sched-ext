# 实测记录：五组调度手段，AI 引擎侧与系统侧

测量时间：2026-10-25

测量机器：VMware 虚拟机，openEuler 24.03 LTS SP4 用户态 + 自编 6.12.0 内核，4 vCPU


这份记录回答两个问题，而且必须一起回答：

1. 哪种调度手段能让推理任务更快开始跑
2. 为了让某一个任务更快，别的任务和整台机器付出了什么

只回答第一个问题的实验，得出的结论一定是"给得越多越好"。

---

## 一、五组

| 组 | 手段 | 怎么做的 | 需要写代码 |
|---|---|---|---|
| cfs | CFS 默认 | 什么都不做 | 否 |
| nice | `nice -n -20` | 调 CFS 权重 | 否 |
| fifo | `chrt -f 50` | 换实时调度类 | 否 |
| nokick | `ai_prio --kick 0` | 自定义调度器，只分道 | 是 |
| kick | `ai_prio --kick 1` | 自定义调度器，分道 + 唤醒抢占 | 是 |

前三组是内核里现成的手段，后两组是本项目的 sched_ext 调度器。
把现成手段放进同一张表，才能回答"值不值得自己写一个"。

## 二、实验条件

| 项目 | 值 |
|---|---|
| 内核 | 6.12.0（kernel.org 原版） |
| vCPU | 4 |
| 压测线程 | 8（= 2 × 核数），纯计算死循环 |
| 引擎请求 | 800 个，间隔 10 ms |
| 探针请求 | 200 个，间隔 40 ms，`--passes 1`，不交给任何调度器 |
| 每组重复 | 3 轮 |
| 调度器参数 | AI 时间片 20 ms，普通任务 3 ms |

**探针是什么**：第二个 `tiny_infer` 进程，每次只算一次前向（约 32 µs），
每 40 ms 醒一次。它没有被任何调度器优待，代表"机器上其他普通任务"。
它的延迟就是系统侧代价的度量。

## 六、两条曲线的交叉

把中位数排一下（AI 引擎 p50 / 普通任务 p50，单位微秒）：

```
fifo     273  /   339
kick     314  /  4930
nice     341  /   299
cfs      768  /   378
nokick   923  /  5002
```

**AI 侧**：fifo < kick < nice < cfs < nokick。
**系统侧**：nice < fifo < cfs < kick < nokick。

两条排序不一样，而且差距不是一点：

- `nice` 把 AI 从 768 压到 341（快 2.25 倍），同时把普通任务从 378 改善到 299。
  一条 `nice -n -20`，两边都是正收益。
- `fifo` 把 AI 压到 273（快 2.8 倍），普通任务 339，和 CFS 基本持平。
- `kick` 把 AI 压到 314，但普通任务从 378 掉到 4930，**慢了 13 倍**。
- `nokick` 两边都差：AI 923，普通任务 5002。

也就是说：**在这个需求下，自定义调度器在 AI 侧没有赢过 `chrt -f 50`，
在系统侧输了 13 倍。**

## 七、为什么自定义调度器会把普通任务搞坏

不是实现 bug，是设计上就漏了一块。

CFS 有两个机制在保护交互式任务：

1. **vruntime 补偿**。任务睡了一段时间，它的虚拟运行时间就落后于一直在跑的
   任务，醒来时排得很靠前。探针每 40 ms 醒一次，醒来时永远是"最该跑"的那个。
2. **唤醒抢占**。新唤醒任务如果领先得够多，允许它插队，不用等当前任务跑完。

`ai_prio` 里这两件事都没做。非 AI 任务全部进 `SHARED_DSQ`，队列是先进先出，
时间片统一 3 ms，而且只有目标 pid 才触发 `scx_bpf_kick_cpu`。
于是探针醒来时，前面排着几个正在跑 3 ms 时间片的压测线程，它只能等。

5 ms 的中位数正好对上这个账：4 个核上跑着 8 个压测线程，探针前面通常有
1～2 个没跑完的时间片。

**这就是"换掉调度器"的真实含义**：你不是只换掉了"谁先跑"，
你把一整套公平性机制也一起换掉了，而公平性机制同时承担着保护交互式任务的职责。
没补上，普通任务就退化。

## 八、吞吐为什么没掉

压测吞吐五组在 231755～247862 之间，差 6% 以内，而且 CFS 是最低的那个。

按预期，被优待的 AI 任务会抢走压测的 CPU，吞吐应该下降。实际没有，原因是
AI 任务本身占的 CPU 很少：每 10 ms 干 446 µs 的活，约 4.5% 的单核占用。
它被提前调度，只是把 4.5% 挪了个位置，总量几乎不变。

CFS 反而最低，一个可能的解释是它在竞争激烈时上下文切换更多、迁移更多，
但这一条没有单独验证，只能当观察，不能当结论。

**结论**：在这个负载下，"让一个任务优先"对总算力的影响在噪声量级。
真正被牺牲的不是吞吐，是**别的任务的响应延迟**。

## 九、局限

1. 单机、4 vCPU、虚拟机。宿主机抖动会污染 p99，所以只看 p50 和量级。
2. 只有一种负载形态：纯计算死循环 + 一个周期性任务。
   真实系统里有 IO、锁、内存压力，结论未必平移。
3. `ai_prio` 是本项目的教学实现，不是生产调度器。它把普通任务搞坏，
   恰恰说明生产级 sched_ext 调度器要补多少东西。
4. 探针的 work 是 32 µs，比引擎的 446 µs 轻一个数量级，
   所以它更容易被"队列位置"影响，绝对延迟不能和引擎直接比。

## 十、复现

```bash
cd ai-engine
sudo ./run-demo.sh                          # 5 组 × 3 轮 × 800 请求
REPS=5 REQUESTS=1200 THREADS=12 sudo ./run-demo.sh
```

只看单组（例如 nice）：

```bash
cd ai-engine && make && make -C ../scheds ai_prio ai_prio.bpf.o
./loadgen 8 120 &
./tiny_infer --requests 800 --interval-ms 10 --json &
nice -n -20 ./tiny_infer --requests 800 --interval-ms 10 --json
```

原始文件都在 `/tmp`：`res-<组>-<轮>.json`（引擎）、`probe-<组>-<轮>.json`（探针）、
`lg-<组>-<轮>.log`（吞吐）、`ctxt-<组>-<轮>.txt`（上下文切换）、
`pol-<组>-<轮>.txt`（调度策略与 nice）。
